## Décisions prises au code

- Lecture : un type racine absent n'est jamais créé (`racinePresente`), ni à l'ouverture ni à la lecture ; seules les écritures, sur un document reconnu, appellent `getMap`. Un document refusé ne reçoit donc rien, même après une écriture refusée (testé).
- `lire()` après `fermer()` rend la dernière table lue, comme `DocumentEspace` ; toute opération lève `facade-fermee` avant le refus du document.
- `-0` : écrit `0` (via `valeurConforme`), et lu `0` quand un pair l'a écrit (normalisation à la lecture plutôt que cellule vide, valeur finie conforme).
- Unité UTF-16 isolée (nom, libellé, texte de cellule) : la façade écrit la forme normalisée (`exigerNom`, `exigerLibelle` et `valeurAdmise` la rendent), le format la lit normalisée ; les limites 200/100/2 000 se mesurent avant normalisation, qui ne change pas la longueur. Réécrire la même chaîne non normalisée n'émet rien (la table lue ne changerait pas).
- Position : à la création, `undefined` vaut « en dernier » ; au déplacement, une position manquante est refusée par `position-invalide` (jamais lue comme « en dernier »).
- Opération sans effet (même nom, même libellé, même position, même valeur lue) : aucune transaction. Écrire `null` dans une cellule lue vide mais qui garde une valeur brute non conforme n'écrit rien (la table lue ne changerait pas).
- `creerLigne` : toutes les colonnes des valeurs initiales sont vérifiées avant toute valeur ; une valeur `null` ne crée aucune clé.
- Colonne `selection` dont la carte `options` manque : ignorée (champ manquant) ; carte `options` sur une autre colonne : tolérée, sans effet.

## Dette et limites

- Dette créée (réelle, à numéroter par l'orchestrateur) : un identifiant (clé de colonne, d'option ou de ligne) à unité UTF-16 isolée, forgé par un pair qui contourne le module, n'est pas normalisé : la réplique d'origine lit la clé brute, les autres `U+FFFD` (constaté sur Yjs 13.6.33). Le module n'écrit que des UUID ; normaliser les clés demanderait de reproduire le départage de Yjs entre deux clés brutes qui se normalisent pareil. Même défaut pour les titres de page du document d'espace (F-001), hors de F-017.
- Règle `document-coeur-pur` étendue à `table.ts` : commitée par le dev (`02f2a72`) avant le commit de code ; CONTRATS passe avec elle, et `table-contrat.test.ts` (F-017-AC24) tient la même pureté par test.
- `rang-indisponible` est inatteignable par la façade de table à la borne de 1 024 (pas d'entrée à borne abaissée) : le signalement est éprouvé sur `insertionParmi` à borne 1 (`table-rang.test.ts`, F-029-AC10).
- F-017-AC25, « et ses tests » : NON couvert à la lettre. La couture énumère les dépendants de `@notionlike/document` (`apps/server`, `apps/web`) et lance la vérification de types de chacun (délai 60 s), mais pour les tests elle ne vérifie que leur `vitest.config.ts` et leur inclusion dans la configuration racine : elle ne peut pas échouer quand un test de `apps/web` ou de `apps/server` échoue. Ces tests tournent dans le même `pnpm test` (et dans `controles.sh`), qui échoue alors, mais pas la couture elle-même (conception, écart 2). Lancer leurs suites depuis la couture a été écarté par l'orchestrateur (trop lourd) : à accepter par dérogation du dev, ou F-017-AC25 à amender.
- À surveiller pour F-018 : `apresTransaction` relit et compare la table entière à chaque transaction, donc à chaque frappe (sans objectif chiffré, H8) ; à mesurer pour quelques milliers de lignes. Les états transitoires d'une livraison dans le désordre (veille, constat 5) sont notifiés, conformément à F-017-AC9.
- ADR-0016 est au statut « proposé » et, avec l'écart 1 de la conception et la table des codes, décrit encore le refus des chaînes à unité isolée : fichiers d'agent-architecte-conception, hors du périmètre d'agent-frontend, texte de remplacement transmis à l'orchestrateur. Statut à passer à « accepté » à la fusion.
