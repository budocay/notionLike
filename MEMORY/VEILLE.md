## Yjs — conception d'un arbre de pages — vérifié le 2026-10-08 — source : web

- Version courante recommandée : sans objet (voir section Yjs 13). Types : `Y.Map` utilisable en type racine ou imbriqué, « nested types can be included as content into any other shared type » ; `observe` ne voit pas les changements des enfants, `observeDeep` oui, et un observateur qui modifie le type est rappelé après son retour [https://docs.yjs.dev/api/shared-types/y.map]. Un `Y.Array` n'offre que insert, push, unshift, delete, get, slice : aucune primitive de déplacement ; le README ne cite pour les arbres déplaçables que la bibliothèque tierce `yjs-orderedtree` (non évaluée, hors périmètre `yjs` seule dépendance) [https://github.com/yjs/yjs]
- Dépréciations / breaking changes récents : aucun relevé concernant ces API en 13.6.x [https://github.com/yjs/yjs/releases]. Conséquence sourcée : un déplacement fait par suppression puis insertion peut dupliquer l'élément quand deux répliques le font en parallèle ; des déplacements concurrents peuvent former un cycle ; l'approche de la littérature les évite en annulant/rejouant les déplacements dans l'ordre des horodatages [https://martin.kleppmann.com/papers/move-op.pdf] (A highly-available move operation for replicated trees, Kleppmann et al. ; PDF illisible en texte brut, résumé obtenu via un extrait : NON VÉRIFIÉ au détail). Aucune primitive Yjs ne fait cela : la résolution de cycle de F-001-AC9 doit être écrite par le module, à la lecture ou à l'écriture (H5).
- CVE ouvertes pertinentes : aucune propre à ces fonctions (voir section Yjs 13).
- Bonnes pratiques officielles à appliquer : (a) modèle « parent + rang par nœud » : Figma décrit un arbre où chaque objet porte son parent et un index, et un index fractionnaire (nombre réel entre 0 et 1 exclus, moyenne des deux voisins) ; la collision de deux insertions entre les mêmes voisins est le cas connu où « averaging between two identical indices doesn't work » ; Figma l'évite avec un serveur central qui n'attribue jamais deux positions identiques, ce que Yjs en pair-à-pair n'offre pas [https://www.figma.com/blog/realtime-editing-of-ordered-sequences/] (l'extrait obtenu ne détaillait pas la gestion des cycles : NON VÉRIFIÉ). Conséquence pour F-001-AC8 : prévoir un départage déterministe des rangs égaux (par exemple l'identifiant de page) et conserver les deux pages ; Evan Wallace (auteur de Figma) décrit la même idée de départage par identifiant d'objet et signale que l'indexation en arbre garde les suppressions pour toujours [https://madebyevan.com/algos/crdt-tree-based-indexing/]. (b) « Dernier écrivain gagne » sur une clé de `Y.Map` : « the last inserted entry for each key is used » et les doublons antérieurs sont marqués supprimés ; la règle qui départage deux écritures concurrentes n'est pas documentée à cet endroit [https://github.com/yjs/yjs/blob/main/INTERNALS.md] : NON VÉRIFIÉ, le test AC10 doit seulement exiger « un des deux titres, identique partout ». Écrire un titre en chaîne simple dans la `Y.Map` de la page (pas de `Y.Text`) correspond à H3. (c) Tombes : une suppression est un drapeau d'état sur l'élément, sans horodatage ni auteur ; avec `gc` actif, le contenu supprimé est remplacé par un objet `GC` qui ne garde que la longueur, mais « we can't garbage collect deleted structs (tombstones) while ensuring a unique order of the structs » ; `doc.gc = false` permet de retrouver l'ancien contenu [https://github.com/yjs/yjs/blob/main/INTERNALS.md] [https://github.com/yjs/yjs] [https://docs.yjs.dev/api/y.doc]. Pour la corbeille (H2), un drapeau `corbeille` sur l'entrée de page évite d'effacer et garde le contenu récupérable (F-007) ; l'impact mémoire de la suppression réelle n'est pas chiffré par les sources : NON VÉRIFIÉ. (d) Déduction non sourcée, à confirmer par test de convergence : deux répliques qui remplacent concurremment une même clé de `Y.Map` portant un `Y.Map` imbriqué n'en gardent qu'un ; préférer créer l'entrée de page une seule fois (identifiant unique) et ne modifier ensuite que ses champs.

## Yjs — versionnage du format et encodage — vérifié le 2026-10-08 — source : web

- Version courante recommandée : sans objet. `Y.encodeStateAsUpdate(doc, [vecteurÉtatCible])` encode l'état en un seul message, avec ou sans vecteur d'état cible (seulement les différences manquantes) ; `Y.applyUpdate(doc, update, [origine])` l'applique, l'origine étant lue sur `transaction.origin` ; `Y.encodeStateVector(doc)` ; `Y.mergeUpdates([...])` fusionne en retirant les doublons [https://docs.yjs.dev/api/document-updates] (F-001-AC12 = `encodeStateAsUpdate` puis `applyUpdate` sur un `Y.Doc` vierge).
- Dépréciations / breaking changes récents : Yjs a deux formats de mise à jour, V1 par défaut ; V2 « provides much better compression » mais « is not yet used by all providers » (événements `updateV2`) [https://github.com/yjs/yjs]. NON VÉRIFIÉ : noms exacts et interopérabilité V1/V2 (`encodeStateAsUpdateV2`, `applyUpdateV2` ne figurent pas dans la page de documentation consultée) ; ne pas mélanger les deux formats sur un même flux et imposer V1 tant que `y-indexeddb` et Hocuspocus (F-002, F-008) ne sont pas vérifiés.
- CVE ouvertes pertinentes : aucune (voir section Yjs 13).
- Bonnes pratiques officielles à appliquer : Yjs n'a pas de mécanisme officiel de version de schéma applicatif ; les sources consultées ne disent rien sur un champ de version, NON VÉRIFIÉ. Pratique à décider par la conception, hors source : un champ scalaire dans une `Y.Map` « méta » (F-001-AC1 : valeur 1). Contrainte vérifiable dans le modèle : deux répliques de versions différentes échangent des mises à jour commutatives sans négociation, donc AC18 ne peut que refuser à la lecture/écriture, jamais empêcher la fusion d'un champ inconnu [https://docs.yjs.dev/api/document-updates].
