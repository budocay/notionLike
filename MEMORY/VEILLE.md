## Yjs — conception d'un arbre de pages — vérifié le 2026-10-08 — source : web

- Version courante recommandée : sans objet (voir section Yjs 13). Types : `Y.Map` utilisable en type racine ou imbriqué, « nested types can be included as content into any other shared type » ; `observe` ne voit pas les changements des enfants, `observeDeep` oui, et un observateur qui modifie le type est rappelé après son retour [https://docs.yjs.dev/api/shared-types/y.map]. Un `Y.Array` n'offre que insert, push, unshift, delete, get, slice : aucune primitive de déplacement ; le README ne cite pour les arbres déplaçables que la bibliothèque tierce `yjs-orderedtree` (non évaluée, hors périmètre `yjs` seule dépendance) [https://github.com/yjs/yjs]
- Dépréciations / breaking changes récents : aucun relevé concernant ces API en 13.6.x [https://github.com/yjs/yjs/releases]. Conséquence sourcée : un déplacement fait par suppression puis insertion peut dupliquer l'élément quand deux répliques le font en parallèle ; des déplacements concurrents peuvent former un cycle ; l'approche de la littérature les évite en annulant/rejouant les déplacements dans l'ordre des horodatages [https://martin.kleppmann.com/papers/move-op.pdf] (A highly-available move operation for replicated trees, Kleppmann et al. ; PDF illisible en texte brut, résumé obtenu via un extrait : NON VÉRIFIÉ au détail). Aucune primitive Yjs ne fait cela : la résolution de cycle de F-001-AC9 doit être écrite par le module, à la lecture ou à l'écriture (H5).
- CVE ouvertes pertinentes : aucune propre à ces fonctions (voir section Yjs 13).
- Bonnes pratiques officielles à appliquer : (a) modèle « parent + rang par nœud » : Figma décrit un arbre où chaque objet porte son parent et un index, et un index fractionnaire (nombre réel entre 0 et 1 exclus, moyenne des deux voisins) ; la collision de deux insertions entre les mêmes voisins est le cas connu où « averaging between two identical indices doesn't work » ; Figma l'évite avec un serveur central qui n'attribue jamais deux positions identiques, ce que Yjs en pair-à-pair n'offre pas [https://www.figma.com/blog/realtime-editing-of-ordered-sequences/] (l'extrait obtenu ne détaillait pas la gestion des cycles : NON VÉRIFIÉ). Conséquence pour F-001-AC8 : prévoir un départage déterministe des rangs égaux (par exemple l'identifiant de page) et conserver les deux pages ; Evan Wallace (auteur de Figma) décrit la même idée de départage par identifiant d'objet et signale que l'indexation en arbre garde les suppressions pour toujours [https://madebyevan.com/algos/crdt-tree-based-indexing/]. (b) « Dernier écrivain gagne » sur une clé de `Y.Map` : « the last inserted entry for each key is used » et les doublons antérieurs sont marqués supprimés ; la règle qui départage deux écritures concurrentes n'est pas documentée à cet endroit [https://github.com/yjs/yjs/blob/main/INTERNALS.md] : NON VÉRIFIÉ, le test AC10 doit seulement exiger « un des deux titres, identique partout ». Écrire un titre en chaîne simple dans la `Y.Map` de la page (pas de `Y.Text`) correspond à H3. (c) Tombes : une suppression est un drapeau d'état sur l'élément, sans horodatage ni auteur ; avec `gc` actif, le contenu supprimé est remplacé par un objet `GC` qui ne garde que la longueur, mais « we can't garbage collect deleted structs (tombstones) while ensuring a unique order of the structs » ; `doc.gc = false` permet de retrouver l'ancien contenu [https://github.com/yjs/yjs/blob/main/INTERNALS.md] [https://github.com/yjs/yjs] [https://docs.yjs.dev/api/y.doc]. Pour la corbeille (H2), un drapeau `corbeille` sur l'entrée de page évite d'effacer et garde le contenu récupérable (F-007) ; l'impact mémoire de la suppression réelle n'est pas chiffré par les sources : NON VÉRIFIÉ. (d) Déduction non sourcée, à confirmer par test de convergence : deux répliques qui remplacent concurremment une même clé de `Y.Map` portant un `Y.Map` imbriqué n'en gardent qu'un ; préférer créer l'entrée de page une seule fois (identifiant unique) et ne modifier ensuite que ses champs.

Constaté avec deux répliques hors ligne partant de « one|two|three » : A déplace « one » à la fin, B tape « X » à la fin de « one » ; après fusion, les deux répliques lisent « two|three|one » et le « X » de B est PERDU. ## y-indexeddb 9.0.12 et IndexedDB — effacement d'une base et compactage du journal (F-007 AC11, AC12, AC21, AC26) — vérifié le 2026-10-08 — source : web

- Version courante recommandée : `y-indexeddb@9.0.12` (voir la section y-indexeddb), `lib0@0.2.119`, `fake-indexeddb@6.2.5` (Apache-2.0). Sources lues : fichiers du tarball `y-indexeddb@9.0.12` (`src/y-indexeddb.js`) et de `lib0@0.2.119` (`indexeddb.js`) [https://registry.npmjs.org/y-indexeddb/-/y-indexeddb-9.0.12.tgz] (lus le 2026-10-08) ; essais EXÉCUTÉS hors dépôt dans `/tmp/veille-yjs` : `node c.mjs`, `node d.mjs`, `node e.mjs` (Node 26.11.0, `import 'fake-indexeddb/auto'`).
- Comportement de `indexedDB.deleteDatabase` : les autres connexions ouvertes reçoivent `versionchange` ; si l'une reste ouverte, `blocked` est émis sur la requête, `success` n'est pas émis et la suppression reste en attente jusqu'à la fermeture de toutes les connexions [https://developer.mozilla.org/en-US/docs/Web/API/IDBFactory/deleteDatabase] (consulté le 2026-10-08). Constaté sous `fake-indexeddb@6.2.5` : connexion ouverte sans fermeture : événements de la requête `['blocked(old=1,new=null)']`, connexion qui a reçu `versionchange(old=1,new=null)`, base toujours listée par `indexedDB.databases()` ; après `db.close()` : `['blocked…','success']`, base disparue ; connexion qui se ferme dans son gestionnaire `versionchange` : seul `success`, pas de `blocked`. Fidélité de `fake-indexeddb` à Chromium sur ce point : NON VÉRIFIÉ (aucun navigateur lancé).
- Ce que fait `clearData()` (code lu) : `destroy()` (retire les observateurs, ferme SA connexion), puis, dans un `.then`, `idb.deleteDB(this.name)` sans `return` : (1) la promesse de `clearData()` se résout avant la fin de la suppression (constaté : `await p.clearData()` rend la main alors que `indexedDB.databases()` liste encore la base ; 50 ms plus tard elle a disparu) ; (2) la suppression bloquée n'est PAS observable : `lib0.deleteDB` ne traite que `onsuccess` et `onerror`, jamais `onblocked` (constaté : avec une connexion brute tierce ouverte, `clearData()` se résout quand même, la base reste listée, aucun rejet ; elle disparaît quand la connexion tierce est fermée) ; (3) un échec de suppression (`error`) serait un rejet de promesse non rattrapé (promesse non retournée) : lecture du code, jamais déclenché sous `fake-indexeddb`, NON VÉRIFIÉ à l'exécution. Conséquence pour F-007-AC21 et AC26 : `clearData()` ne peut ni signaler un échec ni dépasser le délai de 10 secondes ; le module de persistance doit appeler `indexedDB.deleteDatabase` lui-même (ou `clearDocument(name)` = `idb.deleteDB(name)`, qui renvoie une promesse mais ne gère pas `blocked`) avec ses propres `onblocked`, `onerror` et délai ; `clearDocument` est exporté par `y-indexeddb@9.0.12`.
- Connexions de `y-indexeddb` : `lib0.openDB` pose `db.onversionchange = () => { db.close() }` sur chaque connexion qu'il ouvre (code lu). Donc une autre instance (autre onglet) de `y-indexeddb` ne bloque PAS la suppression : constaté, `clearData()` d'une instance alors qu'une seconde instance est synchronisée sur la même base : base supprimée sans `blocked`. Seule une connexion ouverte par un autre code (ou sans ce gestionnaire) bloque, ce qui est le cas du test de F-007-AC21 (« base tenue ouverte par une autre connexion ») : à construire avec `indexedDB.open(nom)` brut sans gestionnaire `versionchange`, sous `fake-indexeddb` (constaté : produit `blocked` puis attente).
- Effets sur l'instance dont la connexion a été fermée par `versionchange` (autre onglet, ou même onglet si un second `IndexeddbPersistence` existe) : la suivante modification du `Y.Doc` lève `InvalidStateError` DEPUIS l'observateur `update` de `y-indexeddb`, donc dans l'appel qui a écrit dans le document (constaté : `d2.getMap('m').set(...)` lève `InvalidStateError`, la modification reste appliquée en mémoire). Autre piège constaté : rouvrir une persistance sur le même `Y.Doc` resté en mémoire réécrit tout son état dans la base recréée (`{"y":"apres","x":"avant"}` relu par une troisième instance) : le contenu « supprimé » revient. Retouche de F-007-AC11/AC21 : avant d'effacer la base d'une page, détruire la persistance ET le `Y.Doc` de cette page dans l'appareil ; AC21 doit prouver qu'une écriture ultérieure sur une instance restée ouverte ne produit pas d'exception non interceptée.
- Compactage du journal : `PREFERRED_TRIM_SIZE = 500` (code lu et constaté). Une mise à jour ajoute un enregistrement au magasin `updates` ; quand le compteur d'enregistrements atteint 500 (`++_dbsize >= 500`), un minuteur de 1000 ms (`_storeTimeout`) lance `storeState` : relit, ajoute un enregistrement `Y.encodeStateAsUpdate(doc)` complet puis supprime tous les enregistrements antérieurs. Constaté : une entrée créée puis retirée = 3 enregistrements, titre LISIBLE dans le journal avant compactage ; après 520 mises à jour : 523 enregistrements à 300 ms, puis 1 seul enregistrement après plus d'une seconde (4632 octets), titre NON lisible, relecture par une nouvelle instance correcte (`pages` vide, `compteur` intact) ; avec 495 mises à jour : 496 enregistrements, pas de compactage. L'ouverture ajoute elle-même un enregistrement (l'état du document en mémoire) : une relecture a porté le journal de 1 à 2 enregistrements. Conclusion : F-007-H1 (« les mises à jour antérieures restent dans le journal jusqu'à son prochain compactage ») CONFIRMÉE ; le compactage dépend du nombre de mises à jour, pas du temps : un journal court n'est jamais compacté seul. Un appel direct `storeState(persistance, true)` (exporté) compacte à la demande : lu, NON ESSAYÉ.
