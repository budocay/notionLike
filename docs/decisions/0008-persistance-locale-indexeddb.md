## Contexte et problème

Le document d'espace doit être enregistré sur l'appareil et relu à chaque ouverture (F-002-AC2), sans jamais bloquer l'écran (AC3, AC16, AC24), sans mêler les espaces d'un même appareil (AC25), sans qu'un identifiant de forme inattendue n'entre dans un nom de base (AC28), et sans qu'aucune erreur de stockage ne s'échappe (AC16). La spec retient `y-indexeddb@9.0.12` (H2), dont la veille et la lecture du source montrent les limites :

- aucune gestion d'erreur : ouverture refusée, lecture ou écriture en échec deviennent des rejets de promesse que personne ne peut attacher ; `indexedDB` absent donne un rejet non géré et une promesse `whenSynced` qui ne se résout jamais ;
- aucun délai ;
- à l'ouverture, elle écrit l'état du document reçu avant d'appliquer ce qui est stocké ;
- chaque mise à jour est écrite dans une transaction qu'elle laisse le navigateur valider seul ;
- le nom de la base est celui passé au constructeur.

Ce qui se défait mal : le nom des bases et le format stocké (migration sur chaque appareil).

## Options étudiées

- **A. `y-indexeddb` derrière un module qui porte ce qu'elle ne fait pas** (retenue).
- B. Écrire la persistance sur IndexedDB sans bibliothèque. Écartée pour F-002 : la spec et la fiche retiennent `y-indexeddb`, et le compactage du journal serait à réécrire. Le module de l'option A rend ce remplacement local s'il devient nécessaire.
- C. `y-indexeddb` appelée directement par la session. Écartée : F-002-AC22 l'interdit, et F-003, F-007, F-013 et F-018 ont besoin du même délai et des mêmes échecs.

Pour l'identifiant de l'espace local (spec H1 : « conservé sur l'appareil », sans dire où) :

- **A. Une base IndexedDB de l'appareil, lue et écrite dans une seule transaction** (retenue).
- B. `localStorage`. Écartée : lecture puis écriture n'y sont pas atomiques entre onglets ; deux onglets lancés ensemble au premier lancement retiendraient deux identifiants, et l'un perdrait sa page au rechargement (F-002-AC4).
- C. Déduire l'espace de l'énumération des bases. Écartée : ambiguë dès F-014, et sujette à la même course.

## Décision

**Un module, une interface.** `apps/web/src/persistance/` ; le reste de l'application n'importe que `persistance/index.ts`, qui n'expose aucun type de `y-indexeddb` :

```ts
type DesignationDocument =
  | { readonly type: "espace"; readonly idEspace: string }
  | { readonly type: "page"; readonly idEspace: string; readonly idPage: string }
  | { readonly type: "table"; readonly idEspace: string; readonly idTable: string };

type EtatPersistance = "relecture" | "active" | "coupee" | "fermee";

interface Persistance {
  lireEtat(): EtatPersistance;
  abonner(rappel: () => void): () => void;
  fermer(): void;
  // Les cinq membres ajoutés par F-030 :
  reessayer(): void;
  aDesModificationsNonEnregistrees(): boolean;
  aReluLaBase(): boolean;
  aLaisseDesBasesNonRattachees(): boolean;
  soumettreLEtatRelu(juge: (temoin: Y.Doc) => boolean): void;
}

function ouvrirPersistance(doc: Y.Doc, designation: DesignationDocument): Persistance;
function ouvrirEspaceLocal(doc: Y.Doc, idCandidat: string): Persistance;
class ErreurPersistance extends Error {} // code "identifiant-invalide"
```

`y-indexeddb` n'est importée que par `persistance/indexeddb.ts` (contrat `web-y-indexeddb-confinee`, tests compris). `indexedDB` n'est nommé que dans ce module (ESLint). Le module n'importe ni React ni `@notionlike/document` ; hors de lui-même, il n'importe que `yjs`, `y-indexeddb` et la fonction de forme d'`identifiants/` (ADR-0007).

**Nom des bases (difficile à défaire).** Une seule fonction, interne au module, dans un fichier qui ne fait que calculer (`nom-de-base.ts` : aucun accès à IndexedDB, aucun import hors d'`identifiants/`, tenu par le contrat `web-formes-pures` et par une règle ESLint sur les globales, ADR-0007), produit le nom à partir d'une désignation : `notionlike:espace:<idEspace>`, `notionlike:page:<idEspace>:<idPage>`, `notionlike:table:<idEspace>:<idTable>` (spec H3). Le type `DesignationDocument` rend l'identifiant d'espace obligatoire pour une page ou une table. Cette fonction applique `estUuidCanonique` (ADR-0007 : 36 caractères, `8-4-4-4-12` en hexadécimal minuscule, longueur comparée d'abord) à chacun des identifiants qu'elle reçoit, espace, page ou table ; un seul identifiant refusé lève `ErreurPersistance` (code `identifiant-invalide`) avant toute ouverture, donc sans base ouverte ni créée (F-002-AC25, AC28). Le message de l'erreur ne cite pas l'identifiant. Deux garanties s'additionnent : l'isolation entre espaces tient au préfixe, de longueur fixe et sans autre `:`, fixé par l'identifiant d'espace ; le contrôle de l'identifiant de page ou de table écarte en plus toute chaîne qui n'a pas la forme produite par l'application, `:` compris. Tout littéral contenant `notionlike:` est interdit par ESLint dans `apps/web/src`, hors de deux fichiers du module : `nom-de-base.ts`, et `espace-local.ts` pour le nom de la base de l'appareil. Depuis F-030, `nom-de-base.ts` porte aussi la fonction inverse, pour la seule base d'espace : `espaceDeLaBase(nom)` rend l'identifiant d'un nom de la forme `notionlike:espace:<UUID canonique>`, jugé par `estUuidCanonique`, et `undefined` pour tout autre nom. La réparation de l'identifiant d'espace s'en sert pour reconnaître les bases d'espace de l'appareil (F-030-AC23) ; elle ne sort pas du module.

**Identifiant de l'espace local (amendé par F-030).** Il vit dans la base `notionlike:appareil` (magasin `reglages`, clé `espace-local`), qui n'est pas une base de document. Cette base naît à la version 1 avec son magasin ; la version 2 est celle d'une base réparée, à laquelle le magasin manquait ; l'application n'en connaît pas d'autre. `ouvrirEspaceLocal` contrôle le candidat par la fonction de nommage, puis, à l'ouverture comme à chaque tentative de reprise, lit la clé et, si elle manque, y inscrit le candidat, dans une seule transaction en écriture : IndexedDB sérialise les transactions d'un même magasin entre onglets, deux onglets lancés ensemble retiennent donc le même identifiant (essayé dans Chromium, essai B2). Le candidat est tiré par la session (`crypto.randomUUID()`), jamais par le module, et c'est celui de l'ouverture à chaque tentative, aucun autre (F-030-AC9). Si un identifiant lisible est déjà inscrit, c'est la base de cet espace-là qui est relue et fusionnée, et aucune base n'est ouverte ni créée au nom du candidat. Ce qui est relu sur l'appareil n'entre dans un nom de base qu'une fois admis par la fonction de forme : une chaîne, UUID canonique (F-002-AC28). Seule l'absence de la clé (`undefined`) dans une base saine vaut premier lancement et fait inscrire le candidat : une valeur nulle est une valeur relue, illisible comme toute autre. La prendre pour une absence ferait ouvrir la base du candidat sans l'inscrire : chaque lancement tirerait un autre espace et perdrait les pages du précédent (F-002-AC2), ce que faisait le code de l'archive. Le module ne tient une connexion à la base de l'appareil que le temps d'une transaction, et la ferme à la réception de `versionchange` : il ne bloque pas la réparation qu'un autre onglet lance.

**Réparation de la base de l'appareil (F-030-AC23, AC24 ; se défait mal).** Le code de F-002 ne réparait rien : une valeur illisible ou une base sans son magasin coupaient la persistance à chaque lancement, jusqu'à l'effacement des données du site. Retenter une valeur illisible ne la rend pas lisible ; le module la remplace donc, sans effacer, renommer, lire ni fusionner aucune base de document (`espace-local.ts`).

- Valeur illisible (valeur nulle, valeur qui n'est pas une chaîne, chaîne d'une autre forme) : le module énumère les bases de l'appareil (`indexedDB.databases()`, dont la présence est testée avant l'appel ; un appel qui lève ou qui rejette vaut énumération indisponible) et ne retient que les noms qu'`espaceDeLaBase` reconnaît. Une seule base d'espace : son identifiant est inscrit. Aucune : le candidat. Plusieurs, ou énumération indisponible : le candidat, et la persistance le signale par `aLaisseDesBasesNonRattachees()`, qui reste vrai jusqu'au rechargement. L'inscription se fait dans une transaction en écriture qui relit la valeur et ne la remplace que si elle est encore illisible : deux onglets lancés ensemble retiennent le même identifiant.
- Magasin `reglages` absent d'une base de version 1 : il est recréé par une montée à la version 2 (`reparation.ts`, `creerLesMagasinsManquants`, qui ne crée que les magasins qui manquent et ne touche à rien d'autre), puis l'identifiant absent est traité comme une valeur illisible, énumération comprise, et non comme un premier lancement. « Réparée » se lit sur la version de la base, non sur ce que la tentative en cours a fait : une base de version 2 dont le magasin ne porte pas d'identifiant, parce qu'une tentative a été interrompue entre la montée et l'inscription, est traitée de même par la tentative suivante, jamais comme un premier lancement.
- Une montée de version qui échoue, qui reste en attente derrière la connexion d'un autre onglet (`blocked`) ou qui dépasse l'échéance de la tentative est une coupure, retentée. Si elle aboutit après l'abandon de sa tentative, sa transaction est annulée : aucun magasin n'est créé hors d'une tentative en cours.
- Ce qui n'est pas réparé, coupure retentée à chaque fois : une base de l'appareil d'une version supérieure à 2, qui n'est ni abaissée ni supprimée ; une base de version 2 à laquelle le magasin manque encore, la réparer demandant de dépasser la version connue ; une ouverture refusée ou une transaction annulée.

Ce qui se défait mal : un identifiant inscrit par la réparation devient celui de l'espace de l'appareil, et une base de l'appareil montée à la version 2 ne redescend pas. Quand plusieurs bases d'espace existent, les pages d'avant restent sur l'appareil sans être rattachées, et aucun écran ne permet de les rattacher (limite acceptée, F-030 H10).

L'identifiant retenu n'est pas exposé par l'interface du module : rien ne le lit en production (l'état de la session ne le porte pas, ADR-0007) et aucun critère ne le demande ; les tests le constatent par le nom de la base d'espace qu'ils énumèrent (`indexedDB.databases()`). F-003, premier lecteur, ajoutera l'accesseur avec son appelant. F-013 ajoutera son registre à cette base.

**États, tentatives et délai (amendé par F-030).** Quatre états : `relecture` à l'ouverture ; `active` une fois la preuve d'écriture faite (plus bas), jamais au seul évènement `synced` de la bibliothèque ; `coupee` sur tout échec ou à l'échéance ; `fermee` après `fermer()`. Seul `fermee` est définitif. `coupee` ne l'est plus, alors que F-002 le tenait pour définitif jusqu'au rechargement : une persistance coupée retente, et redevient `active` quand une tentative aboutit. L'état et la cadence sont tenus par la classe `Suivi` (`suivi.ts`), qui ne nomme ni IndexedDB ni la bibliothèque : elle reçoit à sa construction la fonction qui mène une tentative, lance aussitôt la première, et est seule à en lancer (aucun lancement n'est exposé hors de `reessayer`) ; elle passe à cette fonction de quoi dire son issue (`Tentative` : `attendue`, `echouer`, `tenirPourCoupee`, `noterLaRelecture`, `aboutir`, `aLArret`).

- Tentative : une ouverture complète, de la base de l'appareil s'il y a lieu jusqu'à la preuve d'écriture, sous une échéance de 10 secondes (`ECHEANCE_D_UNE_TENTATIVE_MS`) armée à son lancement. La première est l'ouverture elle-même, lancée par l'appel d'`ouvrirPersistance` ou d'`ouvrirEspaceLocal`. Une persistance n'en a jamais deux en cours.
- Cadence : après une tentative qui échoue ou qui est abandonnée à son échéance, la suivante part 2 secondes plus tard (`PREMIERE_ATTENTE_MS`), puis l'attente double (4, 8, 16, 32 secondes) jusqu'au plafond de 60 (`ATTENTE_PLAFOND_MS`), comptée depuis la fin de la précédente, sans limite de nombre. Une reprise remet l'attente à 2 secondes. Ces valeurs sont des constantes de `suivi.ts` : elles se défont sans coût.
- Tentative immédiate : `reessayer()` en lance une aussitôt si la persistance est coupée, n'en a pas en cours, et que la dernière a été lancée depuis une seconde au moins (`INTERVALLE_MINIMAL_MS`) ; sinon l'appel est sans effet. Son échec ne remet pas la cadence à 2 secondes : l'attente qui le suit est le double de celle qu'il a interrompue, dans la limite du plafond.
- Rien n'est retenu d'une tentative à l'autre : chacune refait tout le chemin, et le module ne garde aucune liste de bases tenues pour coupées (F-030-AC3).
- Instance neuve à chaque tentative : la bibliothèque est construite de nouveau sur le document resté en mémoire, et l'instance d'une tentative qui a échoué, ou d'une persistance tombée en panne, est détruite et jamais réutilisée. Une instance en panne se croit active et ne rejoue rien : seul l'état complet, écrit par une instance neuve, comble ce qui manque à la base (F-030 H12).
- Arrêt : chaque étape d'une tentative inscrit de quoi s'arrêter (`aLArret` : abandon d'une lecture brute, `destroy()` de l'instance). Une tentative qui échoue ou qui est abandonnée, une panne après la reprise et `fermer()` les appellent tous. L'instance détruite se désabonne du document et, son drapeau de destruction levé, n'applique ni n'écrit plus rien, même si sa base s'ouvre plus tard (essai E9) ; le rejet éventuel de `destroy()` est absorbé. Le document reste utilisable en mémoire.
- `fermer()` désarme l'échéance et l'attente, abandonne la tentative en cours et ne laisse aucune minuterie armée ; une persistance fermée ne retente plus, ni par la cadence ni par `reessayer()` (F-030-AC11).

Les minuteries sont `setTimeout` et `Date.now` du navigateur, que les tests remplacent par l'horloge simulée de Vitest. Limite, non mesurée : un navigateur ralentit ou gèle les minuteries d'un onglet masqué, où les tentatives peuvent s'espacer au-delà de ces valeurs ou s'arrêter jusqu'au retour de l'onglet (F-030 H1).

**Lecture brute et juge avant toute construction (F-030-AC10, AC28).** La bibliothèque écrit l'état du document reçu avant d'appliquer ce qui est stocké, et ne laisse attacher aucun traitement à l'échec de sa propre ouverture. Le module lit donc d'abord la base lui-même (`lecture-brute.ts`, `lireLaBase`) : ouverture sans numéro de version, création annulée si la base n'existe pas, de sorte qu'elle reste absente, lecture du magasin `updates`, connexion refermée, et fermée aussi à la réception de `versionchange`. Cette lecture n'écrit aucun octet ; elle remplace la sonde de F-002. Quatre issues :

- échec (exception, erreur de la demande, transaction annulée, ou enregistrement du magasin qui n'est pas un tableau d'octets) : la tentative échoue. Chaque enregistrement lu est contrôlé par son étiquette de type (`Object.prototype.toString`, qui doit rendre `[object Uint8Array]`) et non par `instanceof` : un tableau d'octets cloné par le stockage peut venir d'un autre domaine d'exécution que celui du module, où `instanceof` le refuserait ;
- base absente : la bibliothèque est construite, et c'est elle qui crée la base ;
- base présente sans son magasin `updates` : la bibliothèque n'y est pas construite, où elle rejetterait sa relecture et lèverait dans chaque modification du document. La persistance est tenue pour coupée, la tentative continue : les magasins `updates` (clé auto-incrémentée) et `custom` sont recréés par une montée de version de cette base, à la version lue plus un, tels que la bibliothèque les crée, puis l'instance est construite. Une montée qui échoue, reste en attente ou dépasse l'échéance est une coupure, comme pour la base de l'appareil. Cette montée et sa relecture par la bibliothèque n'ont été jouées que sous `fake-indexeddb`, par les tests de F-030-AC28 : aucun navigateur réel ne les a exécutées (F-030 H14) ;
- enregistrements lus : ils sont appliqués à un document témoin, un `Y.Doc` que rien n'affiche ni n'enregistre (`temoin.ts`, `temoinDe` : un calcul sur Yjs, séparé de l'entrée-sortie de la lecture brute). Si l'un d'eux ne s'applique pas, c'est une lecture en échec : coupure retentée, sans instance, sans réparation, sans rien écrire. Sinon le témoin est soumis au juge.

Le juge est une fonction de l'appelant, posée par `soumettreLEtatRelu` ; sans juge posé, tout est admis. Le module ne sait rien du format du document : c'est la session qui juge la version (ADR-0007). Si le juge refuse, la persistance se ferme, sans instance construite, sans rien avoir écrit dans la base ni appliqué au document : pas même l'enregistrement vide de deux octets que F-002-AC17 admettait. S'il admet, l'instance est construite. S'il lève, il n'a rien admis : la tentative échoue aussitôt, sans instance et sans rien d'écrit, et la suivante le consulte de nouveau. Le témoin est détruit dans les trois cas. Le juge n'est consulté ni sur une base absente ni sur une base dont les magasins viennent d'être recréés. `soumettreLEtatRelu` n'a d'effet qu'appelé de façon synchrone après l'ouverture, avant que la première lecture brute ait répondu : un état relu plus tôt n'est pas rejugé. Limite acceptée (F-030 H3) : la lecture brute et la construction de l'instance ne sont pas atomiques ; un autre onglet qui élève la version de la base entre les deux n'est pas vu par le juge, et l'instance écrit alors l'état de la mémoire avant d'appliquer ce qu'elle lit.

**Preuve d'écriture, à la place de `synced` (F-030-AC26).** La bibliothèque émet `synced` dès qu'elle a appliqué ce qu'elle a relu, sans attendre que l'ajout de l'état complet du document soit validé, donc même quand il échoue. `active` ne suit plus cet évènement. À `synced`, le module note que la base a été relue (`aReluLaBase()`), donc avant la preuve, puis :

1. il encode l'état que le document porte à cet instant ;
2. il ouvre sur la connexion de l'instance une transaction de barrière, en lecture seule sur le magasin `updates`, qui ne finit qu'après les écritures déjà demandées, dont celle de l'état complet. Elle ne tient que l'ordre : elle finit sans erreur même quand cette écriture a été annulée ;
3. il refait une lecture brute de la base, remplit un document témoin, et lui applique l'état encodé à l'étape 1 : la preuve est faite si le témoin n'émet alors aucune mise à jour (`porteTout`). Les suppressions, qu'un vecteur d'état ne porte pas, sont ainsi couvertes.

L'autre moitié de la preuve est tenue par la garde de la connexion (parade 3) : un évènement `error`, `abort` ou `close` reçu depuis la construction de l'instance a déjà fait échouer la tentative. Tant que la preuve n'est pas faite, une ouverture reste en `relecture` (ou en `coupee`, pour une base trouvée sans son magasin) et une tentative en `coupee`, sous la même échéance, qui couvre la preuve. Une preuve qui échoue, ou une lecture brute sans réponse, est une coupure. Ce qui est modifié pendant la preuve est écrit par l'instance et n'entre pas dans la comparaison. Coût accepté : deux lectures brutes complètes de la base par ouverture comme par tentative, celle qui précède la construction et celle de la preuve, et un enregistrement de l'état complet ajouté par la bibliothèque à chaque reprise, même quand la mémoire égale la base (F-030 H2, H13).

**Modifications non enregistrées (F-030-AC16).** `aDesModificationsNonEnregistrees()` devient vrai dès que le document reçoit une mise à jour hors de l'état `active`, ou qu'une panne survenue après la reprise est celle d'une écriture (évènement `error` ou `abort` de la connexion, exception de la fonction d'écriture ; pas l'évènement `close`) ; il redevient faux à la preuve d'écriture. Ce que la bibliothèque applique au document en relisant la base n'est pas compté : elle signe ses transactions de son instance, et le module écarte les mises à jour dont l'origine est une instance de la bibliothèque. Il reste vrai après `fermer()`, et c'est voulu : la session le lit après une fermeture par refus de version pour dire que des modifications sont perdues (F-030-AC10). Un appelant qui décide d'après lui lit donc aussi l'état : la garde d'onglet ne demande plus confirmation pour une persistance `fermee` (ADR-0007).

**Abonnés sous garde (F-030-AC25).** `abonner` garde sa signature. Les abonnés sont appelés à chaque changement d'état, et quand `aDesModificationsNonEnregistrees()` ou `aReluLaBase()` change sans que l'état change. Sont appelés ceux qui étaient inscrits au début de la diffusion et le sont encore à leur tour, dans l'ordre d'inscription. Un rappel qui lève ne prive pas les suivants ; son exception est passée à `console.error` (une phrase fixe, puis l'exception), une fois par rappel fautif, et ne remonte ni dans un gestionnaire d'IndexedDB, ni dans une minuterie, ni par `fermer()`, ni par `reessayer()`. La tentative suivante est armée avant la diffusion d'une coupure : un rappel fautif n'interrompt pas la cadence, et un abonné qui ferme la persistance pendant cette diffusion la désarme.

**Échecs, sans rejet non géré (amendé par F-030).** Quatre parades. Celles de F-002 ont été essayées à sa conception (essais E5 à E9, B3, B4) ; ce que F-030 y change est tenu par ses tests (`reprise-echecs.test.ts`, F-030-AC18).

1. `indexedDB` absent : le module ne teste plus la globale à part. Chacune de ses demandes d'ouverture (`indexedDB.open`, dans `lecture-brute.ts`, `espace-local.ts` et `reparation.ts`) est faite sous garde, et l'absence de la globale y est une ouverture refusée parmi d'autres : la bibliothèque n'est pas construite, l'état est `coupee` dès le retour de l'appel d'ouverture, et le cas est retenté comme les autres, bien qu'il ne se répare pas en cours de session (F-030 H1).
2. Ouverture refusée (exception ou erreur de la demande) : la lecture brute, faite par le module sous ses propres gestionnaires, la voit avant toute construction. La bibliothèque n'est construite qu'après une lecture brute qui a lu la base ou l'a trouvée absente, ou après la réparation de ses magasins.
3. Lecture ou écriture en échec après l'ouverture : le module pose sur la connexion de la bibliothèque un écouteur `error` en phase de capture, qui arrête la propagation. La demande fautive ne reçoit pas l'événement, la promesse de la bibliothèque ne se règle donc jamais et aucun rejet n'est émis. Des écouteurs `abort` (transaction annulée, quota) et `close` (fermeture anormale) s'y ajoutent, et le rejet de la promesse de connexion est traité de même. Tant que la tentative court, c'est son échec ; une fois la persistance active, c'est une coupure. Une exception levée par la fonction d'écriture de la bibliothèque pendant une modification du document (connexion fermée sans événement) est rattrapée par l'enveloppe d'écriture : elle n'atteint pas l'appelant de la modification, et c'est une coupure (F-030-AC18).
4. Ni succès ni échec : l'échéance de la tentative, montée de version en attente comprise.

**Validation de chaque écriture.** La bibliothèque laisse le navigateur valider seul la transaction de chaque mise à jour, un aller-retour plus tard : un rechargement lancé entre-temps annule la transaction, et la dernière écriture est perdue (le producteur l'a relevé une fois sur quatre dans Chromium sur un titre validé puis rechargé aussitôt ; relevé du code, non rejoué par cette conception). Le module enveloppe donc la fonction d'écriture de la bibliothèque : la transaction qu'elle ouvre pendant cet appel synchrone, et elle seule, est validée par `commit()` dès que la demande d'ajout est posée. La relecture et le compactage gardent la validation automatique, dont leurs étapes successives ont besoin. Un navigateur sans `commit()` garde le comportement de la bibliothèque ; un `commit()` qui lève parce que le moteur a déjà terminé la transaction est absorbé, l'annulation arrivant par l'écouteur `abort`. Le format stocké ne change pas : mêmes magasins, mêmes enregistrements (F-002-AC20, tests de `persistance-validation.test.ts`). L'enveloppe est posée sur chaque instance neuve : après une reprise, chaque écriture est validée sans attendre, comme après une ouverture (F-030-AC6).

**Ce que le module tient de la bibliothèque (liste fermée, F-030-AC20).** La version est figée (`9.0.12`, sans intervalle) ; toute montée de version de `y-indexeddb` repasse par les tests nommés ici. Le module tient d'elle, et rien d'autre :

### Amendement F-013 (2026-10-16) : registre de l'appareil, effacements, bases ouvertes par la synchronisation

Contexte : la décision annonçait « F-013 ajoutera son registre à cette base » et le remplacement de la réparation par énumération (D-009) par ce registre. F-013 (`0d04c60`) a livré le registre sans amender cet ADR (mode économe, D-024).

- **Registre** (`apps/web/src/persistance/registre.ts`) : dans `notionlike:appareil`, magasin `reglages`, une clé `registre:<idEspace>` par espace adopté, à côté de la clé `espace-local`, sans montée de version de la base. Valeur : un objet de deux champs exactement, `rattachement` (`"adopte"`) et `droit` (`"ecriture"` ou `"lecture"`). Une entrée absente vaut « local » et rien n'inscrit jamais « local ». Lecture, inscription et retrait ne sont jamais rejetés et ont une échéance de 10 secondes ; une valeur d'une autre forme, une base absente ou d'une version supérieure à 2, ou tout échec rendent la lecture `illisible`. Le registre n'ouvre la base que pour une transaction sur `reglages`, ne la crée ni ne la répare. `espace-local.ts` exporte pour lui `BASE_APPAREIL`, `MAGASIN_REGLAGES` et `CLE_ESPACE_LOCAL`.
- **D-009 n'est pas levée** : la réparation de l'identifiant de l'espace local énumère toujours les bases d'espace de l'appareil (`espace-local.ts`), sans lire le registre.
- **Effacements** : `effacerBaseDeDocument` (`effacement.ts`) efface la base d'un document désigné, dans les mêmes conditions que `effacerBaseDePage` (amendement F-007), et sert à la base du document d'espace. `retirerDuRegistre(idEspace, oublierLEspaceLocal)` retire l'entrée et, sur demande, l'identifiant de l'espace local s'il est celui-là, dans la même transaction : le lancement suivant est un premier lancement. L'interface du module exporte désormais `nomDeBase`, lue par la synchronisation pour faire correspondre nom de base et nom de document.
- **Bases ouvertes hors des sessions** : la synchronisation ouvre des persistances par `ouvrirPersistance`, sans juge, pour les pages qu'elle échange hors de l'écran (passe de fond) et pour la réplique d'une page affichée dont la version est refusée (`apps/web/src/synchronisation/stockage.ts`, seul fichier du module qui atteint la persistance). Ce qu'elles relisent est appliqué tel quel ; la version est jugée à l'ouverture de la page par sa session.
- **Pages effacées sur un autre appareil** : une suppression définitive reçue efface les bases de ces pages sur l'appareil qui la reçoit (ADR-0001, amendement du 2026-10-16), par `effacerBaseDePage`.
- **Dette D-010 inchangée** : la lecture brute reste sans borne ; ni F-029 ni F-012 ne l'ont bornée.

### Amendement F-032 (2026-10-21, accepté par le dev le 2026-10-23 ; écarts au code corrigés le 2026-10-23, d'après `cac2c2e` puis `01c7020`) : ce que l'appareil retient de chaque espace, bases d'un espace, levée de D-009

Contexte : avec F-032, un appareil détient plusieurs espaces (`specs/F-032.md`). Il doit retenir, hors ligne, le dernier nom de chacun, une marque de première synchronisation et l'espace à rouvrir au lancement (AC3, AC8, AC17, AC19, H3) ; il doit pouvoir effacer toutes les bases d'un espace et aucune autre (AC20, H8) ; et la réparation de l'identifiant de l'espace local ne peut plus adopter n'importe quelle base d'espace (AC23, H7, D-009). Détail dans `docs/decisions/F-032-conception.md`.

Options étudiées pour ce que l'appareil retient :

- A. Un champ de plus dans la valeur `registre:<idEspace>`. Écartée par la spec (H3) : le code de F-013 lirait l'entrée `illisible` et tiendrait l'espace pour local (ADR-0014).
- B. Une base IndexedDB de plus, ou le `localStorage`. Écartée : un second lieu à ouvrir, réparer et effacer, sans gain ; le `localStorage` est interdit dans `apps/web/src` hors d'un fichier de F-018.
- C. D'autres clés dans le magasin `reglages` de `notionlike:appareil`, sans montée de version. Retenue.

Décision :

- **Clés nouvelles** du magasin `reglages`, à côté de `espace-local` et de `registre:<idEspace>`, dont ni la clé ni la valeur ne changent : `nom:<idEspace>`, une chaîne, le dernier nom connu ; `premiere-synchronisation:<idEspace>`, la valeur `true`, posée à l'ajout et retirée au premier « Synchronisé » ; `espace-retenu`, un UUID canonique, l'espace ajouté à rouvrir au lancement, **absente pour l'espace de l'appareil**. Leurs formes sont écrites dans un seul fichier, `persistance/cles-de-l-appareil.ts`, qui reçoit aussi, sans changement, la clé et la forme d'une entrée du registre (déplacées de `registre.ts`, pour que la réparation les lise sans cycle d'import). Aucun courriel, nom ni identifiant de compte, aucun jeton.
- **Fonctions** (`persistance/memoire-de-l-appareil.ts`), toutes sous une échéance de 10 secondes, jamais rejetées, sans créer ni réparer la base : `lireLAppareil()`, une transaction en lecture qui rend l'identifiant de l'espace local, les entrées, les noms, les marques et l'espace retenu (une clé inconnue est ignorée) ; `ajouterALAppareil(idEspace, entree, nom)`, entrée, nom et marque dans une seule transaction, annulée si l'échéance tombe avant sa fin ; l'inscription d'un nom, le retrait d'une marque, l'inscription ou le retrait de l'espace retenu (`noterLesNoms`, qui n'inscrit le nom que d'un espace dont l'entrée se relit dans sa transaction, `retirerLaMarque`, `inscrireLEspaceRetenu`). `retirerDuRegistre` retire en plus, dans sa transaction, le nom, la marque et l'espace retenu s'il désigne cet espace. Toutes, et depuis F-032 celles du registre, passent par une même fonction de transaction sous échéance, `operer`, interne au module (précisé le 2026-10-23), dans son propre fichier, `persistance/transaction-de-l-appareil.ts` (déplacée de `memoire-de-l-appareil.ts` le 2026-10-23, `de85521`).
- **Bases d'un espace** : `designationDeLaBase(nom)` (`nom-de-base.ts`, calcul pur) fait le chemin inverse de `nomDeBase` pour les trois formes ; `basesDeLEspace(idEspace)` (`persistance/enumeration.ts`) rend les désignations des bases énumérées par `indexedDB.databases()` dont l'identifiant d'espace est exactement celui-là, ou `undefined` sans énumération (présence testée avant l'appel, appel qui lève ou rejette traité de même). Une base dont le nom n'est pas reconnu n'est jamais désignée, donc jamais effacée. L'énumération de la réparation passe par le même fichier (`enumererLesBases`, interne au module).
- **Espace inscrit et relevé d'une base** (précisé le 2026-10-23, d'après le code) : `ouvrirEspaceInscrit(doc, idEspace)` (`espace-local.ts`) rend la persistance du document d'un espace ajouté, ouverte telle quelle par `ouvrirPersistance`, sous un `idEspace()` constant, sans réparation ; `releverLaBase(designation)` (`persistance/releve.ts`) rend un document témoin de ce que porte une base, lu par la lecture brute sans rien écrire, ou `undefined` (absente, illisible, 10 secondes) : c'est le repli du retrait sans énumération (ADR-0014, amendement F-032).
- **D-009 levée pour le cas qui la motivait** : quand l'identifiant de l'espace local est illisible, une transaction en lecture lit les entrées du registre des espaces énumérés, et n'en garde que ceux qui n'ont pas d'entrée ; la transaction qui relit et inscrit l'identifiant suit, sur la même connexion (corrigé le 2026-10-23 : l'amendement les réunissait en une seule transaction). Une seule base restante : son identifiant est inscrit ; aucune : le candidat, sans avertissement ; plusieurs, énumération indisponible ou registre illisible (transaction en échec, ou valeur d'une autre forme sous la clé d'un espace énuméré) : le candidat et l'avertissement de F-030-AC23. Aucune base n'est effacée, renommée ni fusionnée. La phrase « D-009 n'est pas levée » de l'amendement F-013 ne vaut plus une fois F-032 livrée.

Conséquences de l'amendement :

- La base de l'appareil porte un troisième format : les clés nouvelles sont à relire telles quelles par toute version suivante. La version de F-013 les ignore (elle ne lit que des clés nommées) ; un retour à cette version garde la synchronisation de chaque espace et perd seulement l'accès aux espaces ajoutés, dont les bases restent.
- Un magasin recréé vide par F-030-AC24 perd noms, marques et espace retenu : les espaces sont alors affichés « Nom inconnu sur cet appareil », le lancement rouvre l'espace de l'appareil, et une première synchronisation inachevée n'est plus signalée. Il perd aussi le registre, ce que la réparation ne distingue pas d'un registre vide (limite d'H7).
- Qui écrit dans l'IndexedDB de l'origine peut encore inscrire une entrée au registre pour une base qu'il a posée, et la faire écarter de la réparation ; il ne peut plus faire adopter comme espace de l'appareil une base inscrite. Le reste de D-009 (registre illisible, deux bases non inscrites, énumération indisponible) est la limite que F-030 H10 accepte déjà.
- Le registre a désormais deux écrivains : `synchronisation/stockage.ts`, par les fonctions de `registre.ts`, et `espace/appareil.ts`, par `ajouterALAppareil`, qui écrit l'entrée avec le nom et la marque ; les listes fermées de `test/reprise-coutures.test.tsx` les énumèrent (corrigé le 2026-10-23 : l'amendement disait `espace/appareil.ts` appelant du registre).

## Conséquences

- Remplacer `y-indexeddb` ne touche qu'`indexeddb.ts` ; le format stocké (magasins `updates` et `custom`, mises à jour V1) resterait à relire ou à migrer. La lecture brute et la réparation, qui lisent et recréent ces magasins sans la bibliothèque, dépendent du même format.
- Chaque ouverture, et chaque tentative, coûte deux lectures brutes complètes de la base en plus de celle de la bibliothèque : une avant la construction de l'instance, une pour la preuve (F-030-AC26, H13). F-002-AC16 nomme les trois cas couverts sans rejet non géré (`indexedDB` absent, ouverture refusée, lecture ou écriture en échec après l'ouverture : parades 1 à 3) et écrit comme limite acceptée la fenêtre que le contrôle préalable laisse : une ouverture qui réussit pour la lecture brute puis échoue aussitôt après pour la bibliothèque donnerait un rejet émis par celle-ci. L'échéance rend quand même la main, comme le critère l'exige, et la limite vaut pour chaque tentative (F-030-AC18) ; aucun test ne couvre ce cas.
- La bibliothèque ajoute à la base un enregistrement de l'état complet du document à chaque construction, avant de relire : deux octets (`0, 0`) pour un document vide, l'état entier à une reprise, même quand la mémoire égale la base. La base grossit donc d'un état complet par reprise, jusqu'au compactage de la bibliothèque (F-030 H2). Sur une base de version non prise en charge, rien n'est écrit : le juge la refuse avant la construction (F-030-AC10), alors que F-002-AC17 admettait l'enregistrement vide.
- `active` ne suit plus `synced` mais la preuve d'écriture. La moitié de cette preuve qui repose sur les évènements `error`, `abort` et `close` n'est vérifiée que sous `fake-indexeddb`, qui simule l'échec d'une écriture par l'annulation de sa transaction : leur émission par un navigateur réel dans ces cas n'est pas vérifiée (F-030 H8). L'autre moitié, la relecture de la base, ne dépend d'aucun évènement.
- Après l'échéance d'une tentative, si l'ouverture aboutit tard, la bibliothèque termine la lecture qu'elle avait lancée. F-002-AC24 l'admet et porte sur les effets, que F-030-AC7 étend à chaque tentative abandonnée : rien de ce qu'elle lit n'est appliqué au document ni affiché, et rien n'est écrit (essai E9) ; la tentative suivante, elle, lit et écrit.
- Le module dépend de deux champs internes et de six autres points d'une bibliothèque dont la maintenance est incertaine (spec F-002 H2) : c'est le prix du rechargement immédiat sans perte et de la reprise sans seconde bibliothèque. Remplacer la bibliothèque (option B) les ferait disparaître.
- Un identifiant inscrit par la réparation, une base de l'appareil ou de document montée d'une version : aucun des trois ne se défait. Le code de F-002 demande la version 1 de la base de l'appareil (`indexedDB.open(nom, 1)`, lu sur `main`) : servi de nouveau sur un appareil dont la base a été montée à la version 2, il se verrait refuser l'ouverture et resterait coupé, sans rien abîmer (déduit du code et du comportement d'IndexedDB relevé par la veille, non essayé). Revenir en arrière après une réparation n'est donc pas neutre.
- Hors de `fake-indexeddb`, la réparation n'a été jouée que pour la base de l'appareil : le scénario de bout en bout de F-030-AC22 y éprouve dans Chromium une montée de version laissée en attente (`blocked`) puis aboutie. La montée de version d'une base de document et sa relecture par la bibliothèque n'ont été exécutées dans aucun navigateur réel (F-030 H14). Que l'instance de la bibliothèque d'un autre onglet ferme sa connexion à la réception de `versionchange` n'est pas établi : elle tiendrait la montée d'une base de document en attente, coupure retentée jusqu'à sa fermeture.
- Ce que le magasin `updates` rend n'est tenu pour une mise à jour que si c'est un tableau d'octets ; un tableau d'octets qui ne s'applique pas à un document fait lever `Y.applyUpdate` sur le témoin, ce qui est rattrapé. Dans les deux cas : lecture en échec, coupure retentée sans fin, sans réparation (tests de F-030-AC28).
- Dette D-010 : la lecture brute charge le magasin entier par `getAll()`, sans borne de nombre ni de taille, deux fois par tentative, à côté de la lecture de la bibliothèque, et le nombre de tentatives n'est pas borné non plus. Une base très grosse coûte cette mémoire à chaque tentative. À borner avec F-029 et F-012.
- Dette D-009 : la réparation adopte l'unique base d'espace que l'appareil énumère. Qui peut écrire dans l'IndexedDB de l'origine peut donc substituer l'espace de l'appareil, en abîmant l'identifiant et en ne laissant qu'une base d'espace de son choix. À remplacer par le registre de F-013 avant F-014, où un appareil porte plusieurs espaces.
- Un identifiant de page ou de table qui n'est pas un UUID canonique ne peut pas avoir de base : F-003 et F-018 créent leurs identifiants par `crypto.randomUUID`, comme F-001 le fait pour les pages. Un identifiant de page de forme inattendue, inscrit dans une arborescence reçue (cas laissé à F-012 par la spec), donnera à F-003 un refus à l'ouverture de sa base, à traiter par son écran.
- F-003 et F-018 ouvrent leurs documents par `ouvrirPersistance` avec une désignation `page` ou `table` : même délai, mêmes échecs, même reprise ; F-030-AC21 est sans objet tant que F-003 n'est pas fusionnée, et aucun code de production n'appelle `ouvrirPersistance`. F-007 ajoutera l'effacement d'une base au module ; la fermeture d'une connexion par un autre onglet (F-007-AC33) est vue par l'écouteur `close`, et les connexions que le module ouvre lui-même se ferment sur `versionchange` ; celle que tient la bibliothèque reste à la charge de F-007.
- La base `notionlike:appareil` s'ajoute à ce qu'énumère un test qui liste les bases de l'appareil (F-014).
- Amendement F-007 : la persistance sait effacer une base de page, sur l'appareil et pour l'onglet qui suppriment seulement. Un autre onglet resté ouvert sur la page peut recréer une base orpheline ; une base que l'échéance laisse en place reste orpheline, signalée par l'écran, à balayer par F-025. Rien ne prouve l'effacement d'une base bloquée dans un vrai navigateur (F-007 H19).
- Amendement F-013 : la base de l'appareil porte un second format, le registre ; une version suivante qui y ajoute un champ fera lire `illisible` à cette version, qui tiendra l'espace pour local sans proposer l'adoption. Effacer la copie locale d'un espace détaché ou jamais adopté touche la base de l'appareil (entrée du registre, et identifiant de l'espace local s'il est celui-là) ; celle d'un espace adopté garde son entrée.
