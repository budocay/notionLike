# SPEC F-005 — Bloc code et commandes slash

Statut : brouillon
Tier : structurel
Revue : reviewer-frontend
Retouche du 2026-10-19 (agent-planif, décisions du dev) : F-005-AC1 (sauts de ligne remplacés par des espaces à la conversion), F-005-AC11 et AC18 (Entrée sans effet dans un menu slash sans commande), F-005-AC6, AC11 et AC21 (barre de blocs flottante, affichée dans un bloc code sans sélection), H11 et H13 mises à jour, H16 ajoutée ; spec repassée en brouillon, à revalider par le dev.

- Objectif (une phrase, côté métier) : une personne insère dans une page un bloc de code, dont le texte est gardé tel quel, et choisit le type d'un bloc sans quitter le clavier, en tapant `/` puis quelques lettres, sans compte ni réseau.
- Vocabulaire :
  - « bloc code » : un bloc dont le contenu est du texte brut, sauts de ligne compris, sans marque ni bloc imbriqué, et qui porte un langage facultatif.
  - « langage » : l'attribut du bloc code qui nomme le langage de son texte. « liste des langages » : la liste fermée des identifiants que l'application propose (H5) ; « Texte brut » désigne l'absence de langage.
  - « commande de bloc » : une commande qui donne un type au bloc courant. Sept dans cette feature : « Paragraphe », « Titre 1 », « Titre 2 », « Titre 3 », « Liste à puces », « Liste numérotée », « Bloc code ». « liste des commandes » : leur déclaration unique (libellé, mots-clés, type de bloc), dont la barre de blocs et le menu slash tirent tous deux leur contenu.
  - « menu slash » : la liste de commandes de bloc ouverte par la frappe de `/` dans l'éditeur. « séquence » : le `/` et le texte saisi à sa suite tant que le menu est ouvert. « commande active » : celle que la touche Entrée appliquerait.
  - « commande indisponible » : une commande que le schéma ne permet pas d'appliquer au bloc courant, ce que l'éditeur juge à blanc, sans rien modifier, avant toute activation (F-005-AC11) ; dans la barre de blocs elle est affichée, désactivée et annoncée comme indisponible ; dans le menu slash elle n'est pas listée ; dans les deux cas elle est sans effet. « commande disponible » : toute autre commande de bloc.
  - « Mod » : la touche Ctrl sous Windows et Linux, la touche Cmd sous macOS.
  - « version du document de page » : l'entier défini par F-003 (AC23, H4) ; un document sans version écrite est de version 1. « version lue », « élever la version », « forme stockée de la version » : définis par `specs/F-003.md`, qui livre la lecture et l'opération d'élévation (F-003-AC23, AC31).
  - « table des versions » : définie par `specs/F-003.md` (F-003-AC22) : la liste, tenue en un seul endroit, qui donne pour chaque version du document de page les nœuds, les attributs et les marques du schéma, ainsi que les types partagés du document de page ajoutés à côté du fragment (les commentaires de F-016) ; chaque ligne contient la précédente. « version d'un élément » : la ligne qui introduit ce nœud, cet attribut, cette marque ou ce type partagé. « version prise en charge » : le numéro de la dernière ligne.
  - « éditeur », « bloc », « schéma », « contenu lu », « barre de blocs », « document de page » : définis par `specs/F-003.md`. Le contenu lu comprend désormais le texte et le langage de chaque bloc code.
- Critères d'acceptation :
  - Bloc code
    - F-005-AC1 : QUAND l'utilisateur active « Bloc code » sur un paragraphe ou un titre, LE SYSTÈME DOIT en faire un bloc code sans langage qui conserve son texte ; QUAND il active « Paragraphe » ou un titre sur un bloc code, LE SYSTÈME DOIT lui donner ce type en remplaçant chaque saut de ligne de son texte par une espace, dans le document de page et dans la même transaction que le changement de type, tous les autres caractères étant conservés : aucun saut de ligne NE DOIT rester dans le texte d'un paragraphe ou d'un titre (le schéma n'en a pas hors du bloc code, H16) ; une frappe ultérieure dans ce bloc NE DOIT alors modifier aucun caractère autre que celui qu'elle inscrit ; un test, dans un DOM ou de bout en bout, DOIT donner à un bloc code « aaa\nbbb » le type « Paragraphe », puis à un autre le type « Titre 1 », lire par `yjs` seul le texte « aaa bbb », saisir « X » juste après l'espace qui remplace l'ancien saut de ligne, puis constater que le texte lu par `yjs` seul et le texte affiché sont tous deux « aaa Xbbb » ; la barre de blocs DOIT marquer « Bloc code » quand elle est affichée dans un bloc code (F-005-AC6).
    - F-005-AC2 : QUAND l'utilisateur saisit en tête d'un paragraphe vide trois accents graves suivis d'une espace, LE SYSTÈME DOIT transformer ce paragraphe en bloc code sans langage, sans conserver la séquence ; QUAND un identifiant de la liste des langages est saisi entre les accents graves et l'espace, LE SYSTÈME DOIT donner ce langage au bloc ; SI l'identifiant saisi n'est pas dans la liste, ALORS LE SYSTÈME DOIT créer le bloc code sans langage.
    - F-005-AC3 : QUAND l'utilisateur presse Entrée dans un bloc code, LE SYSTÈME DOIT insérer un saut de ligne dans ce bloc, sans créer de bloc, y compris quand le bloc se termine déjà par deux sauts de ligne (la sortie par Entrée répétée que l'extension apporte est désactivée : H6).
    - F-005-AC4 : QUAND l'utilisateur presse Mod+Entrée dans un bloc code, ou Flèche bas à la fin d'un bloc code qui est le dernier bloc de la page, LE SYSTÈME DOIT créer un paragraphe à la suite et y placer le curseur ; QUAND il presse Retour arrière en tête d'un bloc code vide, LE SYSTÈME DOIT en faire un paragraphe vide.
    - F-005-AC5 : TANT QUE le curseur est dans un bloc code, LE SYSTÈME DOIT inscrire tel quel tout ce qui est saisi : aucune règle de saisie de F-003-AC9 ni d'une autre feature NE DOIT s'y déclencher, la frappe de `/` NE DOIT PAS ouvrir le menu slash, et la touche Tab NE DOIT rien modifier dans le document.
    - F-005-AC6 : TANT QUE l'éditeur a le focus et que la sélection, vide ou non, est entièrement dans un même bloc code, LE SYSTÈME DOIT afficher la barre de blocs flottante, même sans sélection (seule exception à la règle de F-003-AC41 qui ne l'affiche que sur une sélection non vide, H11), à la place et sous les conditions que F-003-AC41 prescrit (près du curseur, sans recouvrir sa ligne, sans sortir de la fenêtre, sans mise à jour Yjs ni déplacement du contenu), et la garder affichée tant que le focus est dans l'éditeur ou dans la barre, sélecteur compris ; la barre DOIT alors présenter un sélecteur « Langage du bloc code » qui propose « Texte brut » et la liste des langages et montre celui du bloc ; QUAND l'utilisateur en choisit un, LE SYSTÈME DOIT l'enregistrer dans le bloc (« Texte brut » : aucun langage) sans modifier son texte ; SI la sélection n'est pas entièrement dans un même bloc code, ALORS le sélecteur NE DOIT PAS être proposé et la barre suit F-003-AC41 seule : affichée sur une sélection non vide, et plus dans un bloc vide (F-003-AC40, AC41, le menu slash étant livré) ; un test DOIT placer le curseur, sans sélection, dans un bloc code et constater la barre et le sélecteur, puis le placer sans sélection dans un paragraphe rempli et dans un paragraphe vide et constater l'absence de barre, le tout sans aucune mise à jour Yjs du fait de l'apparition ou de la disparition de la barre.
    - F-005-AC7 : QUAND l'utilisateur colle un contenu dans un bloc code, LE SYSTÈME DOIT n'en inscrire que le texte, sauts de ligne conservés, dans ce seul bloc ; QUAND il colle hors d'un bloc code un contenu riche qui contient un élément `pre`, LE SYSTÈME DOIT en faire un bloc code sans langage qui en porte le texte ; le langage NE DOIT jamais être tiré du presse-papiers.
    - F-005-AC8 : LE SYSTÈME DOIT rendre un bloc code par un élément `pre` qui contient un élément `code`, dans une police à chasse fixe, espaces et sauts de ligne conservés, sans coloration du texte.
  - Erreurs et limites du bloc code
    - F-005-AC9 (langage hors liste, à la lecture) : SI un bloc code du document porte, à l'ouverture ou après une mise à jour Yjs appliquée pendant l'affichage, un langage absent de la liste des langages ou qui n'est pas une chaîne, ALORS LE SYSTÈME DOIT afficher son texte, montrer « Texte brut » dans le sélecteur, n'émettre aucune mise à jour Yjs de ce fait, et ne dériver de cette valeur aucune classe, aucun attribut ni aucun texte du DOM : le langage est comparé à la liste des langages au rendu, et seul un identifiant de la liste peut donner une classe à l'élément `code` (l'extension de bloc code, non modifiée, dérive cette classe de la valeur sans la valider : H7) ; un test DOIT écrire par `yjs` seul les valeurs `x fixed inset-0`, `"><script>alert(1)</script>`, une chaîne de 10 000 caractères et un nombre, puis constater qu'aucune n'apparaît dans un attribut d'un élément de l'éditeur.
    - F-005-AC10 : SI le texte d'un bloc code contient du balisage HTML ou un script, ALORS LE SYSTÈME DOIT l'afficher comme du texte sans l'interpréter ; le test de F-003-AC20 DOIT couvrir les fichiers de cette feature.
    - F-005-AC35 (langage hors liste, à l'écriture) : LE SYSTÈME NE DOIT inscrire dans le langage d'un bloc code, par aucun chemin (règle de saisie de F-005-AC2, sélecteur, commande, collage, y compris depuis un éditeur de code, dépôt), une valeur absente de la liste des langages : SI la valeur proposée n'est pas un identifiant de la liste, ALORS LE SYSTÈME DOIT inscrire le bloc code sans langage ; un test DOIT soumettre à chacun de ces chemins les valeurs `x fixed inset-0`, `zz` et un identifiant de la liste, puis lire le fragment par `yjs` seul et constater qu'aucun bloc code ne porte une valeur hors liste.
    - F-005-AC36 (collage depuis un éditeur de code) : QUAND l'utilisateur colle hors d'un bloc code un contenu dont le presse-papiers porte les données propres à un éditeur de code (type `vscode-editor-data`), LE SYSTÈME DOIT en faire un bloc code sans langage qui en porte le texte, quel que soit le langage que ces données annoncent, de la liste ou non (F-005-AC7) ; SI ces données sont malformées (JSON invalide, ou valeur qui n'est pas un objet), ALORS LE SYSTÈME DOIT traiter le collage comme un collage de texte (F-005-AC7, F-003-AC13), sans exception levée ni collage perdu ; un test DOIT coller un presse-papiers construit avec un langage `x fixed inset-0`, avec un langage de la liste, puis avec des données malformées, et constater dans les trois cas le texte inscrit, l'absence de langage et l'absence d'exception (H7).
    - F-005-AC11 (commande indisponible) : LE SYSTÈME DOIT juger la disponibilité de chaque commande de bloc sur l'état courant de l'éditeur, à blanc et sans rien modifier, avant de l'afficher et de nouveau avant de l'appliquer ; SI le schéma ne permet pas de donner au bloc courant le type d'une commande de bloc, ALORS LE SYSTÈME DOIT l'exposer comme indisponible (désactivée) dans la barre de blocs flottante chaque fois que celle-ci est affichée (F-003-AC41, F-005-AC6), ne pas la lister dans le menu slash, et aucune voie d'activation (clic dans la barre, touche Entrée dans le menu, raccourci clavier que l'extension de bloc code apporte d'elle-même) NE DOIT émettre de mise à jour Yjs ni changer la structure du document ; cela vaut aussi quand le menu slash est ouvert sans aucune commande listée, toutes celles qui correspondent à la séquence étant indisponibles (« /code » dans le premier paragraphe d'un élément de liste) : la touche Entrée n'y fait alors rien, ni coupure de l'élément, ni mise à jour Yjs (F-005-AC18 ; ce critère l'emporte) ; un test DOIT, dans le premier paragraphe d'un élément de liste, poser une sélection non vide et constater que la barre est affichée et que « Bloc code » y est indisponible, ouvrir le menu slash et constater que « Bloc code » n'y figure pas, saisir `code` à la suite du `/` et constater « Aucune commande », tenter l'activation par chacune de ces voies (clic sur « Bloc code » dans la barre, Entrée dans le menu sans commande, raccourci de l'extension), et constater qu'aucune mise à jour Yjs n'est émise du fait de ces tentatives, que l'élément est toujours dans sa liste, non coupé, et que la séquence `/code` est toujours dans son texte ; puis, dans le deuxième paragraphe d'un élément de liste, constater que « Bloc code » est disponible dans la barre affichée sur une sélection non vide et dans le menu slash, et donne un bloc code à l'intérieur de l'élément (H7).
  - Menu slash
    - F-005-AC12 : QUAND l'utilisateur saisit `/` en tête d'un paragraphe, d'un titre ou du paragraphe d'un élément de liste, ou juste après une espace, LE SYSTÈME DOIT inscrire le `/` dans le texte et ouvrir le menu slash, qui liste les commandes de bloc disponibles dans le bloc courant (les sept dans un paragraphe ou un titre de premier niveau ; F-005-AC11 ailleurs), dans l'ordre du vocabulaire, la première étant la commande active.
    - F-005-AC13 : SI le `/` est saisi juste après un caractère qui n'est pas une espace, ou dans un bloc code, ALORS LE SYSTÈME NE DOIT PAS ouvrir le menu slash.
    - F-005-AC14 : TANT QUE le menu slash est ouvert, QUAND l'utilisateur saisit ou efface du texte à la suite du `/`, LE SYSTÈME DOIT ne lister que les commandes disponibles dont le libellé ou un mot-clé contient ce texte, sans tenir compte de la casse ni des accents, dans l'ordre d'origine, la première restant la commande active.
    - F-005-AC15 : TANT QUE le menu slash est ouvert, QUAND l'utilisateur presse Flèche bas ou Flèche haut, LE SYSTÈME DOIT rendre active la commande listée suivante ou précédente, en bouclant de la dernière à la première et inversement ; ces touches, et Entrée, NE DOIVENT alors ni déplacer le curseur ni modifier le document par elles-mêmes.
    - F-005-AC16 : QUAND l'utilisateur presse Entrée, ou clique sur une commande, menu slash ouvert, LE SYSTÈME DOIT retirer la séquence du texte, donner au bloc courant le type de la commande en conservant le reste de son texte, fermer le menu et laisser le curseur dans ce bloc, le tout en une seule transaction de l'éditeur et une seule mise à jour Yjs ; SI la commande n'est plus disponible à cet instant, ALORS F-005-AC11 s'applique : le menu se ferme et rien n'est modifié.
    - F-005-AC17 : QUAND l'utilisateur presse Échap, efface le `/`, déplace le curseur hors de la séquence, clique hors du menu ou change de page, LE SYSTÈME DOIT fermer le menu slash en laissant le texte tel qu'il est ; après Échap, le menu NE DOIT PAS se rouvrir pour ce même `/`.
    - F-005-AC18 : SI aucune commande disponible ne correspond au texte saisi, ALORS LE SYSTÈME DOIT afficher « Aucune commande » dans le menu ; la touche Entrée NE DOIT alors rien faire : ni coupure du bloc ou de l'élément de liste, ni nouveau bloc, ni changement de type, ni mise à jour Yjs, le menu restant ouvert et la séquence restant dans le texte (F-005-AC11 l'emporte sur F-003-AC7 et AC10 tant que le menu est ouvert ; pour couper le bloc, l'utilisateur ferme le menu, par Échap par exemple, F-005-AC17, puis presse Entrée) ; un test DOIT le constater dans un paragraphe de premier niveau (`/zzz`) et dans le premier paragraphe d'un élément de liste (`/code`, F-005-AC11).
    - F-005-AC19 : SI une mise à jour Yjs appliquée pendant que le menu slash est ouvert modifie ou retire la séquence, ALORS LE SYSTÈME DOIT fermer le menu, sans exception levée et sans perdre le texte que l'utilisateur a saisi ailleurs ; SI cette mise à jour insère du texte avant la séquence sans la toucher, ALORS le menu DOIT rester ouvert et la commande appliquée ensuite DOIT retirer la séquence à sa nouvelle place, et elle seule.
    - F-005-AC20 : LE SYSTÈME NE DOIT émettre, du fait de l'ouverture, du filtrage, de la navigation ou de la fermeture du menu slash, aucune mise à jour Yjs autre que celles du texte saisi : l'état du menu ne vit pas dans le document de page.
    - F-005-AC21 (une seule liste de commandes) : LE SYSTÈME DOIT tirer la barre de blocs et le menu slash de la même liste des commandes ; un test DOIT énumérer les types de bloc de la dernière ligne de la table des versions et échouer si l'un d'eux n'a pas de commande dans la barre flottante affichée sur une sélection non vide d'un paragraphe de premier niveau (F-003-AC41) et dans le menu slash ouvert dans un paragraphe de premier niveau, ou si une commande donne un type absent du schéma.
  - Accessibilité
    - F-005-AC22 : LE SYSTÈME DOIT exposer le menu slash comme une liste d'options nommée « Commandes de bloc », chaque commande listée comme une option qui porte un identifiant, un nom accessible en français et son état (active ou non) ; une commande indisponible n'y figure pas, et reste lisible comme indisponible dans la barre de blocs (F-005-AC11) ; TANT QUE le menu est ouvert, l'éditeur DOIT garder le focus et désigner le menu et la commande active par `aria-controls` et `aria-activedescendant`, retirés à la fermeture ; le nombre de commandes listées, ou « Aucune commande », DOIT être annoncé aux technologies d'assistance à chaque changement du filtre ; le sélecteur de langage DOIT être atteignable et utilisable au clavier seul, avec son nom accessible ; l'éditeur DOIT rester la zone de texte multiligne « Contenu de la page » de F-003-AC16.
  - Version du format et montée de version
    - F-005-AC23 (numéro de version) : LE SYSTÈME DOIT ajouter à la table des versions une ligne dont le numéro est la version prise en charge par `main` au premier commit de code de cette feature, plus un (3 dans l'ordre recommandé, où F-028 est livrée avant ; 2 si F-005 est la première feature livrée qui étend le schéma ; voir H1), et qui ajoute à la ligne précédente le nœud `codeBlock` et son attribut `language` ; un test DOIT vérifier que les numéros de la table se suivent depuis 1 sans trou, que chaque ligne contient la précédente, que le schéma de l'éditeur est exactement la dernière ligne et que la version prise en charge par `@notionlike/document` est son numéro.
    - F-005-AC24 (lecture d'une version antérieure) : QUAND un document de page d'une version antérieure prise en charge est ouvert, LE SYSTÈME DOIT afficher tout son contenu, n'émettre aucune mise à jour Yjs à l'ouverture et laisser sa version inchangée ; TANT QUE l'utilisateur n'y inscrit aucun élément d'une version supérieure à celle du document, LE SYSTÈME NE DOIT PAS écrire de version ; un test DOIT le prouver pour chaque ligne antérieure de la table, sur un document rempli selon cette ligne puis modifié par une frappe dans un paragraphe et par une commande de bloc autre que « Bloc code ».
    - F-005-AC25 (écriture de la version) : QUAND une modification locale inscrit pour la première fois dans un document un élément dont la version dépasse celle du document, LE SYSTÈME DOIT élever la version du document à celle de cet élément avant, ou dans, la transaction Yjs qui inscrit cet élément, quel que soit le chemin (barre de blocs, menu slash, règle de saisie, collage, dépôt) ; un test DOIT, pour chaque chemin, écouter l'événement `update` du document et constater qu'aucune mise à jour portant un bloc code n'est émise avant celle qui porte la version. L'inscription de l'élément DOIT rester annulable comme toute modification faite par l'éditeur : SI l'élévation et l'inscription partagent une transaction Yjs, ALORS cette transaction DOIT porter l'origine de la liaison de l'éditeur ; l'élévation NE DOIT jamais englober l'inscription dans une transaction qui ne la porte pas (une modification faite dans une telle transaction n'entre pas dans l'historique d'annulation, H3) ; le même test DOIT, pour chaque chemin, annuler une fois et constater que le bloc code est retiré du contenu lu.
    - F-005-AC26 (la version ne baisse jamais) : QUAND deux répliques élèvent en même temps la version d'un même document à deux valeurs différentes puis convergent, quel que soit l'ordre d'application des mises à jour, LE SYSTÈME DOIT lire sur les deux la plus haute des deux valeurs : la version lue est la plus haute jamais inscrite (F-003-AC23), ce que F-003-AC31 garantit et prouve pour la forme stockée et que cette feature ne réécrit pas, de sorte qu'une application qui ne prend en charge qu'une version inférieure refuse le document (F-003-AC19) ; une annulation (Mod+Z) NE DOIT PAS abaisser la version. Cela tient à une condition, que cette feature NE DOIT PAS rompre : la forme stockée de la version reste dans un type racine hors du fragment du contenu (F-003 H4), et aucun historique d'annulation de l'application n'a ce type dans sa portée (H3). Ce volet annulation est entièrement à la charge de cette feature, F-003 ne pouvant pas le prouver (F-003-AC32, F-003 H4) : un test DOIT insérer un bloc code par l'éditeur dans un document de version antérieure, annuler jusqu'à épuiser l'historique, puis constater que le bloc code n'est plus dans le contenu lu et que la version lue est toujours celle du bloc code, sur ce document et sur un document vierge qui en reçoit les mises à jour.
    - F-005-AC27 (refus d'une version supérieure) : SI la version d'un document de page dépasse la version prise en charge, ALORS LE SYSTÈME DOIT se comporter comme F-003-AC19 et F-003-AC29 le prescrivent ; un test DOIT ouvrir un document de la version prise en charge plus un, qui contient un nœud et une marque absents du schéma, et constater qu'aucun éditeur n'est créé, qu'aucun événement `update` n'est émis et que l'état encodé du document est le même, octet pour octet, qu'avant l'ouverture.
    - F-005-AC28 (couture du format) : LE SYSTÈME DOIT enregistrer un bloc code dans le fragment XML du document de page comme un nœud `codeBlock` qui ne contient que du texte, sans marque, avec le seul attribut `language` (omis ou nul quand il n'y a pas de langage), sans nouveau type racine ; un test DOIT énumérer les appelants du format du document de page (le module d'édition, le module de persistance, la façade de `@notionlike/document` et tout autre module d'`apps/web` ou du serveur qui lit le fragment ou la version) et échouer si l'un d'eux n'est couvert par aucun test qui ouvre un document de chaque ligne de la table ; un document qui contient un bloc code de plusieurs lignes avec langage, enregistré par le module de persistance puis relu dans un document Yjs vierge, DOIT donner le même contenu lu.
    - F-005-AC29 : SI le schéma contient des marques (F-028 livrée), ALORS LE SYSTÈME DOIT les retirer du texte d'un bloc transformé en bloc code, en conservant ce texte, et n'en accepter aucune dans un bloc code, par aucun chemin (commande, raccourci, règle de saisie, collage).
  - Convergence
    - F-005-AC30 : QUAND deux répliques d'un même document de page ont été modifiées séparément (l'une saisit du texte dans un bloc code pendant que l'autre en change le langage ; les deux saisissent du texte en deux endroits du même bloc code) puis convergent, quel que soit l'ordre d'application des mises à jour, LE SYSTÈME DOIT lire sur les deux le même contenu, où figurent les textes saisis et le langage choisi.
    - F-005-AC31 (changement de type concurrent d'une saisie, limite acceptée : saisie perdue) : QUAND une réplique change le type d'un bloc (commande de bloc ou menu slash) pendant que l'autre saisit du texte dans ce même bloc, puis qu'elles convergent, quel que soit l'ordre d'application des mises à jour, LE SYSTÈME DOIT lire sur les deux le même contenu, où le bloc figure une seule fois, avec son nouveau type et le texte qu'il avait sur la réplique qui a changé le type ; la saisie de l'autre réplique n'y figure pas. Ce comportement est une perte de saisie, acceptée (H8) ; un test DOIT le constater tel quel (« abc|zzz », l'une donne au premier bloc le type « Titre 1 », puis « Bloc code », l'autre y saisit « X » au début, au milieu, puis à la fin : « abc|zzz » avec le nouveau type et sans « X » sur les deux), pour qu'un changement de la liaison soit vu.
  - Structure et coutures
    - F-005-AC32 (couture de la version prise en charge de `@notionlike/document`) : LE SYSTÈME DOIT relever la version prise en charge par `@notionlike/document` au numéro de la ligne de F-005-AC23, ajouter cette ligne à la table des versions sans retoucher les lignes précédentes, et élever la version d'un document par la seule opération de F-003-AC31, sans la modifier ni la doubler, sans changer la forme stockée de la version ni sa lecture (F-003-AC23), sans nouveau type racine et sans nouvel export ; les exports déjà livrés DOIVENT rester inchangés (mêmes noms, mêmes signatures, mêmes codes d'erreur pour les mêmes refus) et les tests de couture des exports (F-003-AC24 et ceux des features livrées) DOIVENT passer sans que leurs listes attendues changent ; un test DOIT énumérer les appelants de la lecture de la version, de la vérification de version et de l'opération d'élévation (le module d'édition, et tout autre module d'`apps/web` ou du serveur qui s'en sert) et échouer si l'un d'eux n'est couvert par aucun test qui lui présente un document de chaque ligne de la table et un document de la version prise en charge plus un ; le paquet DOIT rester exécutable sous Node sans DOM avec `yjs` pour seule dépendance d'exécution.
    - F-005-AC33 : LE SYSTÈME DOIT garder vrais F-003-AC21 (aucune requête réseau du fait de l'éditeur, menu slash compris), F-003-AC26 (une seule instance de `yjs`, manifestes et fichier de verrou relus après l'ajout des dépendances de cette feature), F-003-AC27 (Tiptap, ProseMirror, leur liaison, l'utilitaire de suggestion et la bibliothèque de positionnement `@floating-ui/dom` importés par le seul module d'édition, dont l'interface n'expose aucun de leurs types ; `pnpm contrats` sans violation, avec une règle qui interdit l'importation de `@tiptap/suggestion` et de `@floating-ui/*` partout ailleurs, et un fichier de verrou qui ne résout qu'une seule version de `@floating-ui/dom`) et F-003-AC30 (`prosemirror-view` à 1.42.3 au moins).
  - Bout en bout
    - F-005-AC34 : QUAND la commande de test de bout en bout est lancée, LE SYSTÈME DOIT dérouler dans un navigateur réel, par des frappes réelles, le scénario : dans une page vide, taper `/`, constater le menu affiché près du curseur et entièrement dans la fenêtre, taper `cod`, valider par Entrée, saisir deux lignes de code dont une contient `<b>` et `# `, choisir un langage, sortir par Mod+Entrée, taper `/tit`, descendre d'une commande par Flèche bas, valider, saisir un titre, recharger, constater le même contenu, le bloc code rendu par `pre` et le langage choisi.

- Hypothèses tranchées par agent-planif en l'absence du dev, que la validation de cette spec entérine :
  - H1 — Règle d'incrément de la version, commune à F-005, F-016, F-022 et F-028, indépendante de l'ordre de livraison : la version qu'une feature introduit est la version prise en charge par `main` au moment de son premier commit de code, plus un ; `agent-architecte-conception` l'inscrit dans sa conception et dans la table des versions. Les versions sont cumulatives : la ligne N contient la ligne N-1, et une application qui prend en charge N ouvre toutes les versions de 1 à N. Ordre recommandé, non imposé : F-028 (version 2), puis F-005 (version 3), puis F-016 et F-022 (versions 4 et 5, dans l'ordre de leur livraison). F-016 incrémente la version sans étendre le schéma : sa ligne ajoute un type partagé du document de page, les commentaires, et non un nœud, un attribut ou une marque (F-016-AC27, F-003-AC22). Tranché ainsi plutôt que par un ordre fixe parce que la ROADMAP laisse ces quatre features libres entre elles et qu'un numéro réservé d'avance serait faux dès qu'une livraison s'inverse. Garde-fou : deux branches qui prendraient le même numéro modifient la même ligne de la table, tenue en un seul endroit, et une branche ne fusionne qu'une à la fois (`AGENTS.md`) ; la seconde prend le numéro suivant, et F-005-AC23 échoue tant que ce n'est pas fait. Un numéro de version livré ne change plus jamais de sens : difficile à défaire.
  - H2 — Montée de version paresseuse, écrite par le client qui inscrit le premier élément nouveau, jamais à l'ouverture. Lire un document de version antérieure ne l'écrit pas (F-005-AC24, qui prolonge F-003-AC2 et H7). La version n'est élevée que par la modification qui inscrit le premier bloc code (F-005-AC25), à la version de cet élément et non à la plus haute que le client connaît : un document sans bloc code reste lisible par une application plus ancienne. Conséquence acceptée : dès qu'un bloc code est inséré, une application plus ancienne refuse la page entière (F-003-AC19), sans mode lecture seule. Deux clients de versions différentes sur la même page : dans cette feature, ils ne se voient pas en direct (deux onglets ne se voient qu'après rechargement, F-002 H7) ; l'onglet ancien resté ouvert ne reçoit pas le contenu nouveau et ne peut donc pas le détruire, et à son rechargement il lit la version élevée avant de créer l'éditeur et refuse (F-003-AC19). Avec la synchronisation, le client ancien reçoit la version dans une mise à jour : si elle précède le contenu, F-003-AC29 détruit sa liaison à temps ; si elle arrive dans la même mise à jour que le contenu, F-003-AC29 le couvre aussi, à la condition que la veille a établie par exécution (`MEMORY/VEILLE.md`, « Tiptap 3.31.4 et Yjs — changement de type concurrent d'une saisie ; version et nœud inconnu dans une même mise à jour ») : la garde de version est un observateur simple du type qui porte la version, ou un point antérieur à tous les observateurs ; c'est F-003 qui la livre, pas cette feature. Reste sans garantie : un contenu nouveau qui arrive dans une mise à jour AVANT celle qui porte la version : le premier message ne porte aucune version, et la liaison du client ancien a retiré le contenu avant qu'elle ne soit connue. Ce cas n'est garanti par aucun critère d'aucune spec : ni F-003-AC29, ni F-013-AC34, ni la réplique de F-013 H8, qui ne lit que la version et laisse donc passer ce premier message vers le document lié. Il ne peut venir que d'un client qui enfreint la règle d'écriture (la version est élevée au plus tard dans la transaction qui inscrit le premier élément nouveau : F-003 H4, F-028-AC21, F-005-AC25, que cette feature respecte), ou d'un maillon (fournisseur, serveur, canal entre onglets) qui scinderait une transaction en deux messages, ou qui ferait appliquer la mise à jour du contenu avant celle, émise plus tôt, qui porte la version : non vérifié par la veille. Les deux barrières réelles, et ce que chacune couvre : la garde par observateur simple de F-003-AC29 (version et contenu dans la même mise à jour, ou version d'abord) ; la réplique de F-013 H8 (version supérieure connue avant l'application d'une mise à jour ultérieure). Risque résiduel accepté, écrit comme tel : un client défectueux ou malveillant qui a le droit d'écriture peut faire perdre à tous le contenu qu'un client plus ancien ne connaît pas ; c'est du même ordre que ce qu'un membre en écriture peut déjà faire en supprimant ce contenu. Une parade complète (vérifier le contenu de chaque mise à jour contre le schéma avant de la remettre à la liaison) toucherait l'interface de `@notionlike/document` et le coût de chaque mise à jour : elle est notée comme durcissement possible, à décider par le dev, et n'est pas retenue (F-003 H4, cas (a)). Cette spec ne réduit pas ce risque et ne le déclare pas couvert.
  - H3 — La version ne doit jamais baisser, y compris quand deux clients l'élèvent en même temps à deux valeurs différentes. C'est F-003 qui le garantit et le livre, pas cette feature : la version lue est la plus haute jamais inscrite (F-003-AC23), l'opération d'élévation et sa convergence sont dans `@notionlike/document` (F-003-AC31), et la forme stockée de la version, hors du fragment du contenu, est consignée par un ADR de la conception de F-003 (F-003 H4). Il n'y a pas de valeur unique dont la dernière écriture gagnerait, ni rien à écrire à côté d'elle : avec une telle valeur, un client de version 2 et un client de version 3 qui élèvent ensemble un document pourraient le laisser à 2 alors qu'il contient un élément de la version 3, que le client de version 2 supprimerait ensuite pour tous. Une application limitée à la version 1 a la même lecture, puisqu'elle vient de F-003 : elle lit la version élevée et refuse le document (F-003-AC19). Cette feature ne change donc ni la forme stockée, ni la lecture, et n'ajoute ni type racine ni export : elle relève la version prise en charge, ajoute sa ligne à la table des versions et appelle l'opération de F-003 (F-005-AC23, AC25, AC32). Ce qui reste entièrement à sa charge : prouver qu'une annulation n'abaisse pas la version (F-005-AC26), ce que F-003 ne peut pas faire, toute élévation y détruisant l'éditeur avec son historique (F-003-AC32). Constat de la veille, par exécution (`MEMORY/VEILLE.md`, « Tiptap 3.31.4 et Yjs — portée de l'historique d'annulation ») : l'historique d'annulation de la liaison n'a en portée que le fragment du contenu ; une écriture dans un type racine voisin n'entre jamais dans sa pile et n'est jamais défaite, qu'elle parte d'une transaction voisine, de la même transaction que la frappe ou avec l'origine de la liaison. F-005-AC26 est donc tenable, à une condition que cette spec écrit : la forme stockée de la version reste dans un type racine hors du fragment (ce que F-003 H4 impose), et l'application n'étend jamais la portée de cet historique à ce type (la liaison ne le fait pas d'elle-même) ; une version inscrite dans le fragment serait, elle, défaite par Mod+Z. Piège constaté par la même veille, que F-005-AC25 interdit : une modification faite dans une transaction englobante qui ne porte pas l'origine de la liaison n'entre pas dans la pile et n'est pas annulable ; l'élévation de version n'englobe donc jamais l'inscription du bloc code dans une telle transaction : elle part avant, dans sa propre transaction, ou dans la même transaction portant l'origine de la liaison (cas exécuté : une seule étape d'annulation, le contenu est défait, la version reste). Conséquence acceptée : après une annulation, le document garde sa version élevée sans plus contenir de bloc code ; sans danger pour le contenu, il reste seulement refusé par une application plus ancienne. Si la forme stockée devait un jour changer, F-005-AC26 le dirait : à remonter au dev avant toute retouche, la forme stockée appartenant à F-003 et se défaisant mal.
  - H4 — La coloration syntaxique est exclue de cette feature. Elle demande une dépendance directe de plus (la veille relève un paquet `@tiptap/extension-code-block-lowlight`, sous licence MIT, sans en avoir étudié ni les dépendances ni le poids), un jeu de couleurs à soumettre aux contrôles de F-004 (contraste, jetons), et n'est demandée ni par la fiche ni par la ROADMAP. Le langage est pourtant enregistré dès maintenant (F-005-AC6), pour que la coloration, le jour où elle vient, ne soit ni un changement de format ni un incrément de version : elle ne ferait que lire un attribut déjà présent. Elle n'a pas de ligne dans la ROADMAP : le dev décide si elle en reçoit une.
  - H5 — Liste des langages, fermée : `bash`, `css`, `html`, `javascript`, `json`, `markdown`, `python`, `sql`, `typescript`, `yaml`. Le format accepte n'importe quelle chaîne dans `language` ; la liste est une règle de l'application, pas du format : l'allonger n'incrémente pas la version, parce qu'une application qui ne connaît pas un langage affiche le bloc comme du texte brut sans rien écrire (F-005-AC9). Une valeur hors liste n'est jamais recopiée dans le DOM : un autre client peut écrire n'importe quoi dans le fragment, et une valeur comme `x fixed inset-0`, recopiée dans une classe, habillerait le bloc avec les classes utilitaires de l'application. Les identifiants devront coïncider avec ceux de la bibliothèque de coloration le jour où elle est choisie : à confirmer par la veille à ce moment-là ; d'ici là ils n'engagent que le sélecteur.
  - H6 — La touche Tab n'est pas capturée dans un bloc code : elle reste la touche de navigation au clavier, pour qu'on puisse toujours quitter l'éditeur sans souris (F-003-AC11 ne la capture que dans une liste). L'indentation se fait à l'espace. Choix d'accessibilité contre confort de saisie ; il se défait sans coût (aucun format touché). Les sorties de F-005-AC4 existent pour qu'un bloc code en fin de page ne soit jamais une impasse. Constats de la veille, par exécution (`MEMORY/VEILLE.md`, « Tiptap 3.31.4 — bloc code ») : la touche Tab n'est pas capturée par défaut par l'extension (F-005-AC5 tient sans rien écrire) ; les trois sorties de F-005-AC4 sont natives (Mod+Entrée, Flèche bas à la fin d'un bloc code dernier de la page, Retour arrière en tête d'un bloc vide) : le module d'édition n'a rien à ajouter. L'extension apporte deux comportements de plus, tranchés ainsi : la sortie par Entrée répétée (une troisième Entrée à la fin d'un bloc qui se termine par deux sauts de ligne retire ces sauts et sort) est DÉSACTIVÉE, parce qu'elle contredirait F-005-AC3 et retirerait des lignes vides que du code porte légitimement en fin ; l'ajout d'un paragraphe avant un bloc code premier de la page, par Flèche haut à son début, est gardé tel quel, sans critère (symétrique de F-005-AC4, il évite l'impasse en tête de page). Les deux se défont sans coût.
  - H7 — Le bloc code s'appuie sur l'extension unitaire de Tiptap, au numéro commun des paquets `@tiptap/*` (`3.31.4`). Constats de la veille du 2026-10-08 (`MEMORY/VEILLE.md`, « Tiptap 3.31.4 — bloc code » ; exécutés hors dépôt par un script Node avec jsdom, sans Vitest ni React, sauf mention « lu ») : (a) paquet `@tiptap/extension-code-block`, en `3.31.4`, sous licence MIT, sans dépendance propre ; nœud `codeBlock`, contenu de texte seul, un seul attribut `language`, nul par défaut et absent du fragment quand il est nul (F-005-AC28). (b) Rendu : `pre` qui contient `code` ; la classe de l'élément `code` est dérivée du langage SANS validation (un langage forgé `x fixed inset-0` donne ces classes à l'élément) : le rendu est donc réécrit pour comparer le langage à la liste (F-005-AC9). (c) Règle de saisie (F-005-AC2) : confirmée en tête de bloc ; elle accepte toute suite de lettres minuscules comme langage, même hors liste : le filtre à l'écriture s'y applique (F-005-AC35) ; elle se déclenche aussi sur trois tildes, variante gardée telle quelle, sans critère, sous le même filtre. (d) Collage depuis un éditeur de code : un greffon de l'extension crée un bloc code quand le presse-papiers porte le type `vscode-editor-data`, y lit le langage sans validation et lève une exception non interceptée sur un JSON malformé, le collage n'étant alors pas traité. Tranché : la création du bloc code est gardée (c'est ce qu'on attend en collant du code), le langage n'est jamais repris (F-005-AC7 l'interdisait déjà : le presse-papiers n'est pas une source de confiance, et un seul cas est plus simple à prouver que deux), l'exception est interceptée (F-005-AC36) ; que cela passe par un enrobage du greffon ou par sa réécriture relève de la conception. (e) Marques (F-005-AC29) : confirmé, le bloc code les refuse et la transformation d'un paragraphe en bloc code les retire en gardant le texte. (f) Placement : la règle de contenu d'un élément de liste est « un paragraphe, puis des blocs » (lu) ; un bloc code est donc accepté à partir du DEUXIÈME enfant d'un élément de liste, jamais en premier ; un contenu HTML collé qui le place en premier est réparé à l'analyse (un paragraphe vide reste dans l'élément, le bloc code sort de la liste). Non vérifié par la veille : ce que la liaison fait d'un document REÇU dont un élément de liste commence par un bloc code (F-003-AC17 s'y applique : affichage sans exception, conservation non garantie). Tranché, et confirmé : un bloc code est accepté partout où le schéma de F-003 accepte un bloc, sans modifier la règle de contenu des éléments de liste. (g) Piège constaté, qui fonde F-005-AC11 : dans le PREMIER paragraphe d'un élément de liste, la commande de conversion de Tiptap ne se refuse pas ; elle retombe sur un repli qui sort l'élément de sa liste et en fait un bloc code de premier niveau, en rendant « vrai », alors que la vérification à blanc de l'éditeur (`can()`) rend « faux ». Tranché : la disponibilité de toute commande de bloc est jugée par cette vérification à blanc avant activation, et la commande de conversion n'est jamais appelée sans elle, raccourci natif de l'extension compris (`Mod-Alt-c`, lu) ; une commande indisponible est désactivée dans la barre et absente du menu slash, parce qu'une option de menu qu'on ne peut pas choisir encombre une liste que l'on parcourt au clavier, alors qu'un bouton de barre qui disparaîtrait ferait bouger les autres. Le même repli vaut pour les commandes de titre d'après le code lu, sans exécution : non vérifié ; le test de F-005-AC21 et celui de F-005-AC11, qui portent sur toutes les commandes de bloc, le constateront.
  - H8 — Changer le type d'un bloc pendant qu'un autre client y écrit. Dans le fragment Yjs, le nom d'un élément ne se change pas : donner un autre type à un bloc revient à supprimer l'élément et à en insérer un autre, comme pour un déplacement (F-003 H1). Constat de la veille, par exécution sur deux répliques hors ligne (`MEMORY/VEILLE.md`, « Tiptap 3.31.4 et Yjs — changement de type concurrent d'une saisie ; version et nœud inconnu dans une même mise à jour ») : la saisie concurrente est PERDUE ; les deux répliques convergent vers le bloc au nouveau type, avec le texte de la réplique qui a changé le type, sans le caractère saisi par l'autre (essayé vers un titre de niveau 1, de niveau 2 et vers un bloc code, saisie au début, au milieu et à la fin). F-003-AC15 ne couvre que deux blocs différents. F-005 multiplie les changements de type (menu slash) sans rien y changer : elle exige la convergence et fige ce constat dans un test (F-005-AC31), pour qu'il soit connu avant F-013 et qu'un changement de la liaison soit vu. La perte est acceptée, aucune parade n'est promise : en éviter la cause demanderait de ne plus remplacer l'élément, ce que le fragment Yjs ne permet pas. Elle devient réelle dès cette feature avec deux onglets ouverts sur la même page (fusion au rechargement, F-002 H7), puis plus souvent avec la synchronisation.
  - H9 — Le menu slash s'appuie sur l'utilitaire de suggestion de Tiptap (`@tiptap/suggestion`, relevé par la veille au numéro `3.31.4` sous licence MIT), comme F-003 (H1) l'annonçait : il porte ce qu'un menu maison devrait réécrire dans l'éditeur (repérer le caractère déclencheur et l'étendue de la séquence, intercepter les touches avant l'éditeur, suivre la séquence quand le texte change). Constats de la veille du 2026-10-08 (`MEMORY/VEILLE.md`, « Tiptap 3.31.4 — @tiptap/suggestion et menu slash » ; exécutés hors dépôt par un script Node avec jsdom et un éditeur relié à un document Yjs, sans Vitest ni React) : l'utilitaire s'exécute sous jsdom sans erreur ; il n'écrit RIEN dans le document (quatre caractères saisis, quatre mises à jour Yjs, toutes de la frappe : F-005-AC20) ; une insertion reçue avant la séquence la décale et il la suit, une suppression reçue de la séquence ferme le menu sans erreur (F-005-AC19) ; la commande, écrite par l'application, retire la séquence et change le type en une seule transaction et une seule mise à jour Yjs (F-005-AC16). `@tiptap/suggestion` est donc retenu, et le repli « écrit avec le seul noyau » abandonné. Non vérifié par la veille : une mise à jour reçue qui modifie l'intérieur de la séquence (le test de F-005-AC19 le porte) ; le tout sous Vitest. Correction de cette spec : elle écrivait « aucune bibliothèque de positionnement », ce qui était faux. `@tiptap/suggestion` déclare `@floating-ui/dom` comme dépendance de pair obligatoire et l'importe dès son chargement ; pnpm ne la laisse pas manquante. Tranché : `@floating-ui/dom` (résolue en `1.8.0`, licence MIT) devient une dépendance directe d'`apps/web`, confinée au module d'édition par une règle de dépendances (F-005-AC33), plutôt que de réécrire le repérage de la séquence pour éviter une bibliothèque de 3 paquets sans avis de sécurité connu ; F-006 en a besoin de son côté (poignée de bloc). Puisqu'elle est là, c'est elle qui place le menu (sous le curseur, retourné au-dessus s'il sortirait de la fenêtre), à partir de la position du curseur que l'utilitaire fournit, au lieu d'un calcul maison : le comportement attendu ne change pas (F-005-AC34). La liste affichée reste un composant de l'application : aucune bibliothèque de menu n'est ajoutée. Non vérifié par la veille : le positionnement lui-même (jsdom n'a ni mise en page ni `ResizeObserver`), prouvé seulement de bout en bout ; et que l'empaqueteur élimine le code de positionnement inutilisé.
  - H10 — Le `/` est inscrit dans le texte à la frappe et retiré à l'application d'une commande (F-005-AC12, AC16). Il traverse donc la persistance, et la synchronisation plus tard : un autre appareil peut voir passer `/tit`. Accepté : c'est le fonctionnement de l'utilitaire de suggestion, et le texte de l'utilisateur n'est jamais retenu hors du document. Le menu ne s'ouvre pas au milieu d'un mot (F-005-AC13), pour qu'une adresse ou une fraction ne le déclenche pas. Retirer la séquence et changer le type en une seule mise à jour (F-005-AC16) évite qu'un autre appareil voie le bloc dans un état intermédiaire et donne une seule étape d'annulation : confirmé par la veille, par exécution (`MEMORY/VEILLE.md`, « Tiptap 3.31.4 — @tiptap/suggestion et menu slash » : une transaction de l'éditeur à deux pas, une seule mise à jour Yjs), à la condition que le retrait et le changement de type soient enchaînés dans la commande que l'application fournit à l'utilitaire, et nulle part ailleurs.
  - H11 — La barre de blocs de F-003 reste (F-003 H8) et reçoit « Bloc code » et le sélecteur de langage. Renvoi mis à jour le 2026-10-09 : cette barre est flottante dès F-003 (F-003-AC41, AC42 ; les critères d'éditeur de F-004 y ont été déplacés), et non plus permanente. Report porté le 2026-10-19 sur décision du dev : F-005-AC6, AC11 et AC21 sont reformulés pour la barre flottante, et la barre s'affiche aussi quand le curseur est dans un bloc code, même sans sélection, pour qu'on puisse changer le langage sans sélectionner de texte (F-005-AC6) ; c'est la seule exception à F-003-AC41, qui reste sinon inchangé ; à la livraison de cette feature, l'invite devient « Écris, ou tape / pour insérer un bloc » et la barre ne s'affiche plus dans un bloc vide (F-003-AC40, AC41), ce que cette feature doit livrer avec la couture de F-003-AC43. Le sélecteur vit dans la barre et non dans le bloc lui-même : un contrôle affiché dans le bloc demanderait une vue de nœud sur mesure dans l'éditeur, plus coûteuse à rendre accessible et à tester.
  - H12 — Accessibilité du menu : le focus reste dans l'éditeur, qui garde son rôle de zone de texte (F-003-AC16) et désigne la commande active par `aria-activedescendant`.
