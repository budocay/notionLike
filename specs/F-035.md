# SPEC F-035 — Tests fiables : attente de l'état observable (D-042) et délai des tests lents (D-045)

Statut : brouillon
Tier : standard
Revue : reviewer-frontend

- Objectif (une phrase, côté métier) : le dev et la CI obtiennent le même verdict à chaque exécution des suites `apps/web` et `packages/document`, quelle que soit la charge de la machine, sans qu'aucune assertion ne soit affaiblie.
- Origine : dettes D-042 et D-045 (`MEMORY/STATE.md`, « Dettes ouvertes »), lot de correctifs de la RC1 (`MEMORY/STATE.md`, point 3 de la reprise : « D-042 en premier, D-045 »). Numéros de ligne relevés sur `origin/main` (`a64bf5f`), sauf les trois derniers tests de D-045 (`kanban-ecran.test.tsx`, `table-lecture.test.ts`, `table-convergence.test.ts`), relevés sur la branche F-035 d'après les échecs du crochet Stop.
- Vocabulaire : « lecture sans attente » : une assertion qui lit le DOM (focus, annonce, texte d'une zone) juste après une action ou un `await` qui ne garantit pas que l'état attendu est atteint ; « attente explicite » : `waitFor`, `findBy*` ou un `await` sur l'événement qui produit l'état, jamais un délai fixe (`setTimeout`, `sleep`) ni une répétition aveugle.
- Constat à l'écriture (lu dans le code de `origin/main`) :
  - `apps/web/test/espace-ajout.test.tsx`, ligne 144 : `expect(annonces(espaceOuvert("Gamma"))).toHaveLength(1)` lu juste après un `waitFor` sur le sélecteur, pas sur l'annonce ; ligne 347 : `expect(zoneDeSynchronisation().textContent).not.toContain(PREMIERE_SYNCHRONISATION)` lu après `findByRole("link", ...)`, qui ne prouve pas que la zone a fini de se mettre à jour ; ligne 393 : le même motif sur `getByRole("region", { name: "Synchronisation" })` après `findByText(INVITATION_PREMIERE_PAGE)` ; ligne 516 : `annonces(...)` lu après un `waitFor` sur le focus, pas sur l'annonce.
  - `apps/web/test/espace-changement.test.tsx`, ligne 353 : `document.activeElement` lu juste après `findByRole("alertdialog")`, avant que le focus n'ait été posé sur « Rester sur cet espace ».
  - `apps/web/test/vues-de-table/filtres-et-tris.test.ts`, ligne 289 (F-019-AC28) : 5 000 lignes, trois filtres, deux tris, comparés à un calcul de référence écrit dans le test (tri à bulles avec `indexOf`, 1,6 s sur 2,4 à 2,7 s seul) ; `apps/web/test/vues-de-table/recalcul.test.tsx`, ligne 48 (F-019-AC28) : 300 lignes, rendu d'une grande table, défilement et clavier ; `apps/web/test/vues-de-table/fenetre.test.tsx`, ligne 151 (F-018-AC47) : défilement de 3 000 rangées en mode édition. Aucun n'a de délai déclaré : ils prennent le défaut de Vitest (5 s) et le dépassent quand plusieurs suites tournent ensemble. Trois autres tests dépassent aussi le défaut sous charge : `apps/web/test/vues-de-table/kanban-ecran.test.tsx`, ligne 259 (F-020-AC8, 5 000 lignes en quatre piles) ; `packages/document/test/table-lecture.test.ts`, ligne 522 (F-017-AC20 F-017-AC21, propriété fast-check) ; `packages/document/test/table-convergence.test.ts`, ligne 108 (F-017-AC10, `it.each([2, 3])`, deux cas). `apps/web/vitest.config.ts` ne fixe pas de `testTimeout` (fichier protégé, hors de cette feature).
- Critères d'acceptation :
  - Attente de l'état observable (D-042)
    - F-035-AC1 (les cinq lectures nommées) : QUAND le test `espace-ajout.test.tsx` des lignes 144, 347, 393 et 516 ou le test `espace-changement.test.tsx` de la ligne 353 s'exécute, LE SYSTÈME DOIT attendre explicitement l'état observable avant chaque assertion citée (l'annonce, la zone de synchronisation vidée de la marque, le focus sur le bouton de la boîte d'alerte), puis faire la même assertion qu'avant : chacune est conservée, avec la même valeur attendue.
    - F-035-AC2 (aucun affaiblissement) : QUAND la feature est livrée, LE SYSTÈME DOIT conserver dans chacun des deux fichiers le nombre de tests, leurs titres et toutes leurs assertions : la comparaison au diff (`git diff origin/main...HEAD -- apps/web/test/espace-ajout.test.tsx apps/web/test/espace-changement.test.tsx`) ne montre aucune ligne `expect` supprimée ni dont le matcher ou la valeur attendue change, aucun `.skip`, `.todo`, `retry`, `waitFor` dont le corps ne contient plus l'assertion, ni délai fixe ; une assertion qui devient `waitFor(() => expect(...))` garde le même `expect`.
    - F-035-AC3 (même motif ailleurs dans les deux fichiers) : QUAND le producteur recense dans `espace-ajout.test.tsx` et `espace-changement.test.tsx` les autres lectures de même nature (focus, annonce, texte de zone, état désactivé ou description lus sans attente après une action asynchrone), LE SYSTÈME DOIT les corriger de la même façon et les lister, avec leur ligne, dans le rapport de la feature ; une lecture laissée sans attente DOIT y être justifiée (l'état est synchrone avec l'action : `act` déjà attendu).
    - F-035-AC4 (preuve de stabilité) : QUAND chacun des deux fichiers est exécuté vingt fois de suite seul, puis vingt fois pendant que `pnpm test` de la racine tourne (charge réelle), LE SYSTÈME DOIT les voir passer toutes les fois ; le nombre d'exécutions et le résultat sont relevés dans le rapport, avec le nombre d'échecs avant la feature relevé sur `origin/main` dans les mêmes conditions.
  - Délai des tests lents (D-045) — option à trancher par le dev en validant (H1)
    - F-035-AC5 (six tests, un seul changement chacun) : QUAND les tests de `filtres-et-tris.test.ts` (ligne 289), `recalcul.test.tsx` (ligne 48), `fenetre.test.tsx` (ligne 151), `kanban-ecran.test.tsx` (ligne 259), `table-lecture.test.ts` (ligne 522) et `table-convergence.test.ts` (ligne 108) s'exécutent pendant que d'autres suites tournent, LE SYSTÈME DOIT les voir passer sans dépasser leur délai, selon l'option retenue en H1 : option A, un délai explicite déclaré sur le test lui-même (troisième argument de `it`), de 30 000 ms ; option B, un calcul de référence plus rapide dans `filtres-et-tris.test.ts` (sans délai pour ce test) et, pour les cinq autres, qui n'ont pas de référence à accélérer, le même délai explicite de 30 000 ms qu'en A. Pour les trois tests ajoutés (`kanban-ecran`, `table-lecture`, `table-convergence`), le traitement est celui de l'option A quelle que soit l'option : un délai de 30 000 ms en troisième argument, sans toucher au titre, au corps, aux données ni aux assertions. Pour `it.each([2, 3])(titre, corps, délai)` de `table-convergence.test.ts`, le délai est le troisième argument de l'appel renvoyé par `it.each`, après la fonction de test, et s'applique à chacun des deux cas (2 et 3 répliques). Une seule option s'applique, celle que le dev nomme en validant ; à défaut, A.
    - F-035-AC6 (même oracle, mêmes assertions) : QUAND l'option retenue est appliquée, LE SYSTÈME DOIT garder les mêmes jeux de données, les mêmes assertions et le même résultat attendu dans les six tests ; pour l'option B, le calcul de référence reste écrit dans le test, indépendant du code de `src/` (ni `lignesAffichees` ni aucune fonction de `src/vues-de-table/` n'y est appelée pour produire le résultat attendu), et un test de contrôle du calcul plus rapide DOIT l'égaler au calcul actuel sur un jeu de 200 lignes, avant la suppression de l'ancien dans le même commit.
    - F-035-AC7 (preuve sous charge) : QUAND les six tests sont exécutés dix fois de suite pendant que `pnpm test` de la racine tourne, LE SYSTÈME DOIT les voir passer toutes les fois ; le temps le plus long relevé est consigné dans le rapport avec la marge au délai.
  - Erreurs et limites
    - F-035-AC8 (un échec réel reste un échec) : SI le comportement testé est cassé (par exemple l'annonce d'ouverture n'est plus émise, ou le focus reste hors de la boîte d'alerte), ALORS chaque test corrigé par AC1 DOIT échouer, avec un message qui nomme l'assertion et non un dépassement de délai générique ; le producteur le prouve, pour trois des cinq lectures de son choix, en cassant localement le comportement puis en rétablissant le code (relevé dans le rapport, rien de cassé n'est commité).
    - F-035-AC9 (liste fermée des fichiers touchés) : QUAND la feature est livrée, LE SYSTÈME DOIT n'avoir modifié, parmi les tests de features livrées, que les huit fichiers `apps/web/test/espace-ajout.test.tsx` et `espace-changement.test.tsx` (F-032), `apps/web/test/vues-de-table/filtres-et-tris.test.ts` et `recalcul.test.tsx` (F-019), `fenetre.test.tsx` (F-018), `apps/web/test/vues-de-table/kanban-ecran.test.tsx` (F-020), `packages/document/test/table-lecture.test.ts` et `table-convergence.test.ts` (F-017) ; tout autre fichier existant de `apps/web/test/`, `packages/` ou `e2e/` DOIT passer sans modification, comme `vitest.config.ts`, `eslint.config.*` et les clés `scripts` des `package.json` ; un helper d'attente éventuel s'écrit dans un fichier nouveau `apps/web/test/aides-attente.ts`, dans le périmètre des fichiers d'aide de `apps/web/test/` ; aucun fichier de `src/` n'est modifié. Le diff le prouve (`git diff --name-only origin/main...HEAD`).
    - F-035-AC10 (couture) : QUAND un helper d'attente est créé et employé par plus d'un fichier, LE SYSTÈME DOIT le couvrir par un test de couture qui énumère ses appelants dans `apps/web/test/` et échoue si un appelant attend sur un délai fixe ; SINON (aucun helper, attentes écrites sur place) aucun test de couture n'est requis.

- Pourquoi ce tier : aucun comportement du produit ne change, mais la feature modifie des tests de features livrées, donc des contrôles (précédent : liste fermée de F-020-AC27) ; ce n'est ni `trivial` (un test est un contrôle et ses huit fichiers sont énumérés) ni `structurel` (ni module, ni flux, ni dépendance, ni migration, ni infra). Doute entre `trivial` et `standard` : le plus élevé.
- Hypothèses à faire trancher par le dev :
  - H1 — Option pour D-045, à nommer en validant. Option A (recommandée) : un délai explicite de 30 000 ms, déclaré sur chacun des six tests. Raisons : ne touche à aucune assertion ni à aucun oracle, le correctif est lisible sur la ligne du test, et cinq des six tests (`recalcul`, `fenetre`, `kanban-ecran`, `table-lecture`, `table-convergence`) sont du rendu jsdom ou des propriétés sans calcul de référence à accélérer ; contrepartie : un test lent reste lent, et un vrai ralentissement du code ne se voit que passé 30 s. Option B : un calcul de référence plus rapide dans `filtres-et-tris.test.ts` (index précalculé au lieu de `indexOf`) ; le test de F-019-AC28 devient rapide pour de bon, mais l'oracle est réécrit (risque d'un oracle qui rejoint le code testé, borné par AC6) et les cinq autres tests reçoivent de toute façon le délai de A. Option C (écartée par la recommandation) : `testTimeout` global, fichier protégé qui touche tous les tests et masque les vraies lenteurs.
  - H2 — 30 000 ms : valeur de départ, six fois le défaut de Vitest, pour une marge d'au moins trois sur le pire temps relevé sous charge ; le producteur la relève en AC7 et propose la valeur la plus basse qui garde cette marge, que le dev peut accepter en relisant le rapport.
