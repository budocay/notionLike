# SPEC F-046 — Stabilité de synchro-document.test.ts : erreur non gérée à la fermeture des clients et délai sous charge (dette D-028)

Statut : validée
Tier : standard
Revue : reviewer-backend

- Objectif (une phrase, côté métier) : le contrôle `tests` d'un dossier de revue n'échoue plus pour une raison étrangère à la feature revue, parce que `apps/server/test/synchro-document.test.ts` passe de façon répétable, seul comme dans `pnpm test`, y compris sur une machine chargée.
- Origine : dette D-028 (`MEMORY/STATE.md`). Faits constatés, donnée non vérifiée par cette spec : sous `pnpm test`, « Unhandled Errors : Error: WebSocket was closed before the connection was established » est levée par `PriseAvecCookie.close` (ws 8.22.0), depuis `HocuspocusProviderWebsocket.destroy`, depuis `fermerLesClients` (`apps/server/test/aides-synchro.ts:363`), depuis l'`afterEach` de `synchro-document.test.ts:46`, après le test « F-012-AC38 une version 3 est refusée en entier par version-refusee… » ; lancé seul sur machine chargée, le fichier échoue 2 fois sur 3 par « Test timed out in 60000ms ». L'erreur non gérée fait échouer le contrôle `tests` de tous les dossiers de revue.
- Vocabulaire :
  - « le fichier » : `apps/server/test/synchro-document.test.ts`. « les aides » : `apps/server/test/aides-synchro.ts` et les autres fichiers d'aides de test d'`apps/server/test/` que le diagnostic désigne.
  - « erreur non gérée » : une exception ou un rejet que vitest rapporte sous « Unhandled Errors » et qui fait échouer l'exécution même quand chaque test passe.
  - « charge » : une machine dont le processeur est occupé par d'autres processus, reproduite par le producteur par un moyen qu'il décrit (par exemple plusieurs exécutions du fichier en parallèle).
  - « cause » : l'enchaînement d'événements, nommé jusqu'à la ligne de code, qui produit l'erreur non gérée ou le dépassement de délai.
- Critères d'acceptation :
  - Diagnostic
    - F-046-AC1 : QUAND la feature est livrée, LE SYSTÈME DOIT avoir, dans `MEMORY/features/F-046.md`, un diagnostic qui nomme la cause de l'erreur non gérée et la cause du dépassement de délai (fichier, ligne, enchaînement des événements), dit si chacune est dans les aides de test ou dans `apps/server/src`, et donne la commande qui reproduit chacune avant correction ; une cause énoncée sans reproduction DOIT être signalée comme hypothèse non confirmée, et la correction DOIT alors être arrêtée et remontée au dev (code 3).
    - F-046-AC2 : SI les deux symptômes ont deux causes distinctes, ALORS LE SYSTÈME DOIT les traiter et les prouver chacune, sans conclure d'une correction qu'elle règle l'autre.
  - Correction
    - F-046-AC3 : QUAND `fermerLesClients` ferme une prise dont la connexion n'est pas encore établie ou est déjà close, LE SYSTÈME DOIT terminer la fermeture sans erreur non gérée et sans laisser de prise ouverte ; un test DOIT fermer, par `fermerLesClients`, une prise encore en cours de connexion et constater qu'aucune erreur non gérée n'est rapportée et que la prise est close.
    - F-046-AC4 : QUAND le fichier s'exécute seul sous la charge définie par le producteur, LE SYSTÈME DOIT terminer chacun de ses tests sans « Test timed out » ; la correction DOIT porter sur la cause nommée par F-046-AC1 (attente remplacée par une condition observable, ressource libérée, ordre de fermeture corrigé), et NE DOIT PAS reposer sur un allongement de délai.
    - F-046-AC5 : SI la cause est dans `apps/server/src`, ALORS LE SYSTÈME DOIT la corriger dans `apps/server/src` et ajouter un test de régression qui échoue avant la correction (le producteur DOIT montrer cet échec) et passe après ; SI la cause est dans les aides, ALORS le test de F-046-AC3 tient lieu de régression pour l'erreur non gérée.
    - F-046-AC6 : LE SYSTÈME NE DOIT affaiblir aucune assertion, retirer ni désactiver aucun test (`skip`, `todo`, `only`, `retry`), ni modifier un délai global ou un fichier protégé (`vitest.config.*`, `package.json`) ; un délai propre à un appel d'attente d'une aide ne peut être changé que si le diagnostic montre qu'il n'est pas la cause, et l'écart DOIT être justifié dans `MEMORY/features/F-046.md`.
    - F-046-AC7 : QUAND une aide de test est modifiée (signature, valeur par défaut, comportement de `fermerLesClients`, `fermerLesFacades` ou d'une attente), LE SYSTÈME DOIT avoir un test de couture qui énumère les appelants de cette aide dans `apps/server/test/` et constate qu'aucun ne dépend de l'ancien comportement ; les autres fichiers de synchronisation (`synchro-arret`, `synchro-connexion`, `synchro-coutures`, `synchro-droits`, `synchro-fermetures`, `synchro-limites`, `synchro-ouverture`, `synchro-plafonds`) DOIVENT passer inchangés.
  - Preuve par répétition
    - F-046-AC8 : QUAND la feature est livrée, LE SYSTÈME DOIT avoir 20 passages consécutifs du fichier seul sans échec ni erreur non gérée, dont au moins 10 sous la charge définie, puis `pnpm test` complet sans « Unhandled Errors » ni échec, la commande et les sorties étant consignées dans `MEMORY/features/F-046.md` ; SI un seul passage échoue, ALORS la feature n'est pas terminée et l'échec est remonté avec sa sortie.
    - F-046-AC9 : QUAND le dossier de revue de F-046 est construit, LE SYSTÈME DOIT afficher `tests` en succès au contrôle `.agents/checks/dossier-revue.sh F-046`, sans dérogation.
- Hors périmètre (explicitement) : les autres fichiers de test (leur stabilité n'est pas constatée) ; tout changement de comportement observable du serveur de synchronisation ; la mise à niveau de `ws` ou d'Hocuspocus (nouvelle version de dépendance, hors de cette feature) ; `vitest.config.*`, `package.json` et le délai global ; la dette D-028 est levée par cette feature, aucune autre dette.
- Liste fermée des fichiers modifiables : `apps/server/test/synchro-document.test.ts`, `apps/server/test/aides-synchro.ts`, et, si le diagnostic l'exige, un autre fichier d'aides de `apps/server/test/` (`aides-facade.ts`, `aides-versions.ts`, `fabrique.ts`, `aides.ts`), un nouveau fichier de test `apps/server/test/aides-synchro.test.ts`, et, seulement si la cause est dans le serveur, le fichier de `apps/server/src/` que le diagnostic nomme avec son test de régression ; `MEMORY/features/F-046.md` pour le diagnostic. Tout autre fichier exige une revalidation de cette spec.
- Pourquoi ce tier : comportement de test dans la structure existante, aucun nouveau module, aucune dépendance, aucune migration ; `standard` et non `trivial` car un test et, selon la cause, du code serveur changent. Si le diagnostic désigne un changement de flux ou de dépendance, la feature remonte à `structurel` et revient à la planification.
