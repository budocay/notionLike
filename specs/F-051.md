# SPEC F-051 — CI : tests d'intégration du serveur sur un PostgreSQL réel (D-002)

Statut : validée
Tier : structurel
Revue : reviewer-devops, reviewer-backend, reviewer-bdd

- Objectif (une phrase, côté métier) : les migrations et l'échange des documents avec la base sont prouvés contre le même moteur que celui du déploiement, à chaque PR, sans que le poste d'un développeur ait besoin de Docker pour lancer ses tests.
- Origine : D-002 (tests d'intégration du serveur sur PGlite, pas sur PostgreSQL réel ; F-008 H5, étendue par F-011 H10 et F-012 H11 ; l'aller-retour d'un instantané Yjs par le pilote `pg` n'est prouvé par aucun test, `MEMORY/features/F-012.md`). La ROADMAP renvoyait cette décision à une spec de la CI ; la voici.
- Vocabulaire : « tests d'intégration du serveur » : ceux de `apps/server/test/` et `packages/db/test/` qui ouvrent une base ; « PGlite » : PostgreSQL embarqué en WebAssembly utilisé en local ; « service PostgreSQL » : conteneur de service d'un job GitHub Actions.
- À commiter par le dev (fichiers protégés, `Agent: dev`) : `.github/workflows/ci.yml` (le job ou le service ajouté), et si le sélecteur de base l'exige `vitest.config.*` ou les clés `scripts.test` de `package.json`. Les agents n'y écrivent pas : ils proposent le texte dans `MEMORY/features/F-051.md`.
- Critères d'acceptation :
  - F-051-AC1 : QUAND la CI tourne sur une PR, LE SYSTÈME DOIT démarrer un service PostgreSQL de la même version majeure et du même épinglage par empreinte que `infra/docker-compose.yml`, et y exécuter les tests d'intégration du serveur.
  - F-051-AC2 : QUAND la variable de sélection de base (H1) vaut `postgres`, LE SYSTÈME DOIT faire passer les tests d'intégration par `URL_BASE_DONNEES` vers le service ; QUAND elle est absente, ils DOIVENT utiliser PGlite comme aujourd'hui, de sorte que `pnpm test` en local n'exige pas Docker.
  - F-051-AC3 : QUAND les migrations sont appliquées sur une base vide du service, LE SYSTÈME DOIT obtenir un schéma dont les tables, colonnes, types et index sont identiques à celui de PGlite, comparés par `information_schema` et `pg_indexes` dans un test.
  - F-051-AC4 : QUAND un instantané Yjs est écrit puis relu par le pilote `pg`, LE SYSTÈME DOIT rendre les mêmes octets (aller-retour prouvé sur le vrai moteur ; F-012, « Dette et limites »).
  - F-051-AC5 : QUAND deux fichiers de test tournent en parallèle, LE SYSTÈME DOIT les isoler (une base ou un schéma par fichier), sans collision de noms.
  - F-051-AC6 : SI le service PostgreSQL ne démarre pas ou n'est pas prêt dans le délai du job, ALORS LE SYSTÈME DOIT faire échouer le job, jamais l'ignorer ni le laisser vert (un contrôle non joué est `UNVERIFIED`, pas PASS).
  - F-051-AC7 : SI la variable de sélection vaut `postgres` et que l'URL de base est absente, ALORS LE SYSTÈME DOIT échouer au démarrage des tests avec un message qui nomme la variable manquante.
  - F-051-AC8 : QUAND la CI lance le service, LE SYSTÈME DOIT n'utiliser qu'un mot de passe factice déclaré dans `ci.yml` ; `secrets.sh` ne DOIT rien trouver et aucun secret du dépôt n'est requis.
  - F-051-AC9 : QUAND le job s'exécute, LE SYSTÈME DOIT ajouter au plus 3 minutes à la durée de la CI (mesure sur trois exécutions, écrite dans `MEMORY/features/F-051.md`).
  - F-051-AC10 : QUAND la variable de sélection est ajoutée, LE SYSTÈME DOIT avoir un test de couture qui énumère les lecteurs de `URL_BASE_DONNEES` et de cette variable dans `apps/server`, `packages/db` et `infra`, et échoue sur un lecteur non attendu (cas fautif donné comme donnée).
  - F-051-AC11 : QUAND F-051 est livrée, LE SYSTÈME DOIT garder verts, sans modification d'oracle, les tests existants de `apps/server/test/` et `packages/db/test/` sur PGlite (F-008 à F-012).
- Hypothèses (recommandation de la planification) :
  - H1 — Nom de la variable : recommandation, `TESTS_BASE=postgres|pglite`, défaut `pglite`.
  - H2 — Où mettre le service : recommandation, dans le job `controles` existant, pour ne pas ajouter de check requis au ruleset de `main` (réglage `gh api` refusé aux agents) ; si le dev préfère un job `postgres` séparé, il l'ajoute aux checks requis lui-même.
  - H3 — Version de PostgreSQL et épinglage : à confirmer par `agent-veille` (rafraîchissement forcé, F-008) ; recommandation, l'image de `docker-compose.yml`, sans montée de version dans cette feature.
  - H4 — Ordre avec F-052 : F-051 d'abord (même fichier `ci.yml`) ; la seconde intègre `main` (règle de fusion en parallèle).
  - H5 — Fermer D-002 : à la livraison, quand AC1 à AC6 sont verts sur trois exécutions de la CI.
- Hors périmètre (explicitement) : le bout en bout Playwright (F-052) ; la sauvegarde et la restauration de la base ; une montée de version de PostgreSQL ; le déploiement hors du poste du dev ; la suppression de PGlite.
- Pourquoi ce tier : infrastructure de CI et nouveau flux de test contre un service externe : `structurel` (AGENTS.md).
