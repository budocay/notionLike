# SPEC F-022 — Bloc image : fichier disponible hors ligne, téléversement à la reconnexion

Statut : brouillon
Tier : structurel
Revue : reviewer-bdd, reviewer-backend, reviewer-api, reviewer-frontend

- Objectif (une phrase, côté métier) : une personne insère une image dans une page, la voit tout de suite même sans réseau, et les autres membres de l'espace la voient dès qu'elle a rejoint le serveur, sans qu'un fichier reçu puisse exécuter quoi que ce soit, dépasser une limite ou sortir de son espace.
- Vocabulaire :
  - « image » : un fichier d'un type de la liste des types, borné par les limites de F-022-AC11, désigné dans un espace par un identifiant d'image. Une image est immuable : ses octets ne changent jamais sous un identifiant donné.
  - « identifiant d'image » : un UUID au format canonique, en minuscules, tiré sur l'appareil par `crypto.randomUUID()` et par aucun autre moyen (F-002-AC26).
  - « bloc image » : le nœud `image` du schéma de l'éditeur. Il ne porte qu'une référence (l'identifiant d'image) et un texte alternatif ; jamais les octets, jamais une adresse.
  - « liste des types » : PNG, JPEG et WebP, liste fermée publiée par `packages/contrats` avec, pour chacun, sa signature (premiers octets du fichier) et le type de contenu que le serveur lui associe (`image/png`, `image/jpeg`, `image/webp`).
  - « type constaté » : le type de la liste dont la signature correspond aux premiers octets du fichier ; aucun si aucune ne correspond. Ni le nom du fichier, ni son extension, ni un type annoncé (`File.type`, en-tête `Content-Type`) n'y participent.
  - « forme nettoyée » : le résultat de la fonction de nettoyage de F-022-AC13, qui ne garde d'un fichier que les parties utiles à son affichage. « Image conforme » : un fichier dont le type constaté est dans la liste, qui respecte les limites de F-022-AC11 et qui est égal, octet pour octet, à sa forme nettoyée.
  - « module d'images » : le seul module d'`apps/web` qui appelle les routes d'images et fabrique les adresses d'affichage (F-022-AC9, AC38). « base d'images » : la base IndexedDB `notionlike:images:<idEspace>`, une par espace.
  - « image en attente » : une image de la base d'images que le serveur n'a pas encore reçue. « image transmise » : reçue par le serveur. « image reçue » : téléchargée du serveur. « envoi refusé » : le serveur a refusé l'image de façon définitive.
  - « routes d'images » : `PUT` et `GET /api/v1/espaces/:idEspace/images/:idImage`.
  - « version du document de page », « version lue », « élever la version », « table des versions », « version prise en charge » : définis par `specs/F-003.md` et `specs/F-028.md`.
  - « éditeur », « bloc », « schéma », « contenu lu », « barre de blocs », « document de page », « module d'édition » : définis par `specs/F-003.md`. « liste des commandes », « menu slash » : `specs/F-005.md`. « rattachement », « espace détaché », « zone de synchronisation », « passe de fond », « droit » : `specs/F-013.md`. « matrice des droits », rôles, « route d'espace » : `specs/F-011.md`. « enveloppe d'erreur » : `specs/F-008.md`.
- Critères d'acceptation :
  - Insertion et affichage immédiat
    - F-022-AC1 : QUAND l'utilisateur active la commande « Image » et choisit dans le sélecteur de fichiers du système de 1 à 10 fichiers, LE SYSTÈME DOIT, pour chaque fichier dans l'ordre : le contrôler et le nettoyer (F-022-AC11 à AC13), tirer son identifiant d'image, enregistrer sa forme nettoyée dans la base d'images de l'espace ouvert comme image en attente, PUIS insérer un bloc image après le bloc courant (à sa place si c'est un paragraphe vide) et l'afficher à partir des octets de l'appareil ; aucune de ces étapes NE DOIT attendre le réseau, et un test DOIT le constater avec un `fetch` qui ne répond jamais et sans compte.
    - F-022-AC2 (jamais de bloc sans octets) : LE SYSTÈME NE DOIT inscrire un bloc image dans le document qu'après la fin réussie de l'écriture de ses octets dans la base d'images ; SI cette écriture échoue (espace de stockage de l'appareil épuisé, base refusée), ALORS LE SYSTÈME NE DOIT inscrire aucun bloc ni émettre aucune mise à jour Yjs, et DOIT afficher « L'image n'a pas pu être enregistrée sur cet appareil. » ; SI la persistance est coupée pour la session (F-002-AC16, F-003-AC18), ALORS LE SYSTÈME DOIT tenir les octets en mémoire jusqu'au rechargement, insérer le bloc et conserver l'avertissement de F-002-AC16.
    - F-022-AC3 (une seule liste de commandes) : LE SYSTÈME DOIT ajouter « Image » à la barre de blocs ; SI F-005 est livrée, ALORS la commande DOIT venir de la liste des commandes de F-005-AC21 et figurer dans le menu slash, où son choix retire la séquence saisie puis ouvre le sélecteur de fichiers ; SI l'utilisateur referme le sélecteur sans rien choisir, ALORS LE SYSTÈME NE DOIT rien inscrire d'autre ; le test de F-005-AC21 DOIT passer avec le type `image` dans la dernière ligne de la table des versions.
    - F-022-AC4 (fichiers lâchés ou collés) : QUAND un dépôt dans l'éditeur ou un collage porte au moins un fichier, LE SYSTÈME DOIT empêcher l'action par défaut du navigateur, traiter les 10 premiers fichiers comme F-022-AC1 le prescrit, à l'endroit du dépôt ou du curseur, et ignorer tout le reste du contenu lâché ou collé (texte, contenu riche) ; chaque fichier refusé (F-022-AC12) DOIT donner le message de F-022-AC12 sans rien inscrire ; SI le dépôt ne porte aucun fichier accepté, ALORS aucune mise à jour Yjs NE DOIT être émise. Ce critère remplace le refus de F-006-AC35, dont le test est modifié par cette feature (H13) : un fichier qui n'est pas une image conforme reste refusé sans que le navigateur l'ouvre.
    - F-022-AC5 (aucune image née d'une adresse) : QUAND un contenu riche collé ou lâché contient un élément `img`, `picture`, `svg`, `object`, `embed` ou un style qui désigne une image, LE SYSTÈME NE DOIT en tirer aucun bloc image ni charger aucune adresse (F-028-AC14 et F-003-AC13 restent vrais) ; seule exception, pour que le couper-coller d'un bloc image dans l'application fonctionne : un élément qui porte l'attribut `data-id-image` dont la valeur est un identifiant d'image DOIT devenir un bloc image portant cet identifiant et le texte alternatif de son attribut `alt` ; son attribut `src` NE DOIT jamais être lu. Un test DOIT coller `<img src="https://exemple.invalid/a.png">`, `<img src="data:image/png;base64,…">`, `<img src="x" onerror="…">` et `<img data-id-image="../../auth/sign-out">`, et constater qu'aucun bloc image n'est inscrit et qu'aucune requête n'est émise.
    - F-022-AC6 (texte alternatif) : QUAND un bloc image est sélectionné, LE SYSTÈME DOIT afficher dans la barre de blocs un champ étiqueté « Texte alternatif de l'image » ; QUAND l'utilisateur y valide un texte de 500 caractères au plus, LE SYSTÈME DOIT l'enregistrer dans le bloc ; au-delà, il DOIT refuser, citer la limite et conserver la saisie dans le champ ; un texte alternatif reçu qui n'est pas une chaîne ou dépasse 500 caractères DOIT être rendu vide, sans mise à jour Yjs.
    - F-022-AC7 : QUAND l'utilisateur supprime, coupe, colle, annule (Mod+Z) ou, si F-006 est livrée, déplace un bloc image, LE SYSTÈME DOIT traiter ce bloc comme tout autre bloc, sans toucher à la base d'images ni émettre de requête ; les tests de F-006-AC16 et AC22 DOIVENT passer avec le bloc image ; un bloc image NE DOIT accepter ni texte ni marque.
  - Référence et rendu (rien de ce qu'un pair écrit n'est une adresse)
    - F-022-AC8 (la référence est un identifiant validé) : LE SYSTÈME DOIT décider de toute référence d'image par une seule fonction de `packages/contrats`, sans DOM ni réseau, qui l'accepte si et seulement si c'est une chaîne de 36 caractères au format canonique d'un UUID, en minuscules ; SI le bloc image d'un document porte, à l'ouverture ou après une mise à jour Yjs appliquée pendant l'affichage, une référence refusée, absente ou qui n'est pas une chaîne, ALORS LE SYSTÈME DOIT afficher à sa place « Image invalide », n'émettre aucune requête, n'ouvrir aucune base, n'émettre aucune mise à jour Yjs et afficher le reste du contenu ; un test DOIT écrire par `yjs` seul, avant l'ouverture puis pendant l'affichage, les références `https://exemple.invalid/a.png`, `//exemple.invalid/a`, `/api/auth/sign-out`, `../../moi`, `javascript:alert(1)`, `data:image/svg+xml,<svg onload=alert(1)>`, `blob:x`, un UUID en majuscules, un UUID suivi de `?x=1`, un UUID suivi de `/../..`, la chaîne vide, un nombre et un objet.
    - F-022-AC9 (adresse construite, jamais lue) : LE SYSTÈME DOIT construire l'adresse d'une route d'images par une seule fonction de `packages/contrats`, à partir de l'identifiant de l'espace ouvert, pris au registre de l'appareil et jamais dans un document, et d'une référence acceptée par F-022-AC8 ; aucun module d'`apps/web` NE DOIT assembler cette adresse autrement, ni donner à un élément `img` une adresse tirée d'un document ; un test DOIT énumérer les fichiers source d'`apps/web` et échouer si un autre module que le module d'images appelle une route d'images ou `URL.createObjectURL`.
    - F-022-AC10 (attributs imposés) : LE SYSTÈME DOIT rendre un bloc image affichable par un élément `img` qui porte exactement `src`, une adresse `blob:` créée par le module d'images à partir d'octets conformes et d'un type de contenu pris dans la liste des types d'après le type constaté, `alt`, le texte alternatif rendu comme du texte, et `draggable="false"` ; le schéma ne déclare pour le nœud `image` que les attributs `idImage` et `alt` (F-022-AC32, AC35), de sorte qu'aucun autre attribut inscrit par un autre client n'atteint le rendu ; un test DOIT écrire par `yjs` seul, avant l'ouverture puis pendant l'affichage, un bloc image qui porte en plus `src`, `srcset`, `onerror`, `onload`, `style`, `class`, `width` et `title`, et constater que l'élément rendu ne porte aucun de ces attributs ni aucune de ces valeurs. Chaque adresse `blob:` DOIT être révoquée quand son bloc cesse d'être affiché.
  - Contrôle du contenu (appliqué à l'identique par l'appareil et par le serveur)
    - F-022-AC11 (limites) : LE SYSTÈME DOIT publier depuis `packages/contrats` et appliquer partout les mêmes limites : 5 mébioctets (5 242 880 octets) par image, forme nettoyée ; 8 192 pixels au plus par côté et 25 000 000 de pixels au plus, lus dans l'en-tête du fichier sans le décoder ; 2 000 images et 500 mébioctets par espace sur le serveur ; 10 fichiers par geste d'insertion.
    - F-022-AC12 (type constaté sur le contenu) : LE SYSTÈME DOIT calculer le type constaté par une seule fonction de `packages/contrats`, sans DOM, sans réseau et sans dépendance, à partir des seuls octets ; SI un fichier choisi, lâché ou collé n'a aucun type constaté, dépasse une limite de F-022-AC11 ou a un en-tête illisible, ALORS LE SYSTÈME NE DOIT rien enregistrer ni inscrire pour lui et DOIT afficher « Cette image n'est pas acceptée : PNG, JPEG ou WebP, 5 Mo et 8 192 pixels de côté au plus. », annoncé aux technologies d'assistance. Un test DOIT soumettre à cette fonction une table de cas, tenue en un seul endroit, comprenant au moins : un SVG (avec et sans déclaration XML, avec un script), un document HTML, un GIF, un PDF, un fichier vide, un fichier de 3 octets, un PNG nommé `photo.jpg`, un fichier HTML nommé `photo.png` et annoncé `image/png`, un fichier qui commence par la signature PNG suivie d'un document HTML, un fichier RIFF qui n'est pas un WebP (tous refusés ou, pour le PNG mal nommé, constaté PNG), et un PNG, un JPEG et un WebP valides (acceptés).
    - F-022-AC13 (métadonnées retirées par l'appareil) : LE SYSTÈME DOIT passer tout fichier accepté par une seule fonction de nettoyage de `packages/contrats`, sans DOM, sans réseau et sans dépendance, AVANT tout enregistrement sur l'appareil et tout envoi : elle reconstruit le fichier en ne gardant que les parties d'une liste fermée propre à chaque type, nécessaires à l'affichage (données de l'image, palette, transparence, profil de couleur, images d'une animation), et retire tout le reste : données EXIF dont la géolocalisation, la date et le modèle de l'appareil, XMP, IPTC, commentaires, blocs de texte, vignette incorporée, parties inconnues, et tout octet placé après la fin de l'image ; pour un JPEG dont l'orientation EXIF n'est pas l'orientation normale, elle DOIT réinscrire une seule donnée EXIF, l'orientation, construite par l'application (H7). La fonction DOIT être idempotente (la forme nettoyée d'une forme nettoyée lui est égale), prouvé par un test de propriété, et un test DOIT nettoyer un fichier de chaque type portant une position GPS, un commentaire, un bloc XMP et des octets témoins après la fin de l'image, puis constater qu'aucun de ces octets témoins ne figure dans le résultat, que le type constaté et les dimensions sont inchangés et, pour le JPEG, que l'orientation est conservée.
    - F-022-AC14 (le serveur n'accepte qu'une image conforme) : QUAND le serveur reçoit le corps d'un `PUT`, LE SYSTÈME DOIT lui appliquer les mêmes fonctions (type constaté, limites, nettoyage) ; SI le corps n'est pas une image conforme (aucun type constaté, limite dépassée, en-tête illisible, ou corps différent de sa forme nettoyée : des métadonnées y subsistent), ALORS LE SYSTÈME DOIT répondre 400 avec le code `image-refusee` sans rien stocker ; le serveur NE DOIT ni transformer ni réencoder une image, et aucune dépendance native ni bibliothèque de traitement d'image NE DOIT être ajoutée (ADR-0006). Le test DOIT rejouer la table de F-022-AC12 par la route, ainsi qu'un JPEG valide portant une position GPS.
  - Routes d'images : autorisation par espace
    - F-022-AC15 (téléversement) : QUAND un membre dont le rôle permet `ecrire-contenu` envoie `PUT /api/v1/espaces/:idEspace/images/:idImage` avec l'en-tête `Content-Type: application/octet-stream` et pour corps une image conforme, et qu'aucune image de cet espace ne porte cet identifiant, LE SYSTÈME DOIT stocker ses octets, son type constaté, sa taille, ses dimensions et son empreinte SHA-256 sous la clé (espace, identifiant), et répondre 201 sans corps ; SI le type annoncé n'est pas exactement `application/octet-stream`, ALORS LE SYSTÈME DOIT répondre 400 `requete-invalide` sans lire le corps ; le type annoncé NE DOIT jamais servir à décider du type de l'image.
    - F-022-AC16 (immuable et rejouable) : QUAND un `PUT` vise un identifiant déjà stocké dans cet espace, LE SYSTÈME DOIT répondre 200 sans rien modifier si l'empreinte du corps est celle de l'image stockée, et 409 `identifiant-indisponible` sinon ; aucune route NE DOIT remplacer, modifier ni supprimer les octets d'une image stockée.
    - F-022-AC17 (lecture) : QUAND un membre dont le rôle permet `lire-contenu` envoie `GET` sur la même adresse et que l'image existe dans cet espace, LE SYSTÈME DOIT répondre 200 avec les octets stockés, identiques octet pour octet à ceux reçus ; SI aucune image de cet espace ne porte cet identifiant, ALORS LE SYSTÈME DOIT répondre 404 `ressource-introuvable`.
    - F-022-AC18 (aucune fuite d'existence, aucun passage entre espaces) : LE SYSTÈME DOIT traiter les routes d'images comme des routes d'espace : 401 `non-authentifie` sans session valide, avant toute lecture (F-011-AC8) ; pour un non-membre, un espace inexistant ou supprimé, ou un identifiant d'espace ou d'image qui n'est pas un UUID canonique, le même 404 `ressource-introuvable` que F-011-AC12, que l'image existe ou non ; 403 `acces-refuse` pour un `lecteur` qui envoie un `PUT` ; l'ordre d'évaluation de F-011-AC9 (adhésion, rôle, validité, état), adhésion et rôle relus en base à chaque requête ; les tests de F-011-AC8, AC10, AC12 et AC32, qui énumèrent les routes, DOIVENT couvrir les deux routes d'images. QUAND un membre de l'espace A demande dans A l'identifiant d'une image stockée dans un espace B dont il n'est pas membre, LE SYSTÈME DOIT répondre 404 sans un octet de l'image de B, prouvé par test ; la même réponse DOIT être faite, corps de la requête non lu, à un non-membre qui envoie un `PUT`.
    - F-022-AC19 (origine) : SI un `PUT` porte un en-tête `Origin` qui n'est ni l'origine de `URL_PUBLIQUE` ni une entrée de `ORIGINES_AUTORISEES`, ALORS LE SYSTÈME DOIT répondre 403 `origine-refusee` sans lire le corps, dans les conditions de F-011-AC26 ; aucune réponse des routes d'images NE DOIT porter d'en-tête `Access-Control-Allow-*`, et une requête `OPTIONS` sur ces routes DOIT recevoir le 404 de F-009-AC32.
  - Réponses du serveur : rien ne s'exécute
    - F-022-AC20 (en-têtes d'une image servie) : LE SYSTÈME DOIT servir une image avec un `Content-Type` égal au type de contenu que la liste des types associe au type constaté enregistré à la réception, et jamais avec une valeur venue du client ; `X-Content-Type-Options: nosniff` ; `Content-Disposition: attachment; filename="image"`, nom fixe, de sorte qu'une navigation vers cette adresse télécharge le fichier au lieu de l'afficher dans l'origine de l'application ; `Content-Security-Policy` qui contient `default-src 'none'`, `sandbox` et `frame-ancestors 'none'` ; `Cross-Origin-Resource-Policy: same-origin` ; `Cache-Control: no-store` ; et `Content-Length` égal à la taille stockée ; les autres en-têtes de F-008-AC4 et F-008-AC9 restent posés. Un test DOIT lire ces en-têtes sur une réponse 200 et constater qu'aucune réponse de ces routes n'a un type `text/html`, `image/svg+xml` ou `application/xhtml+xml`.
    - F-022-AC21 (le client ne se fie pas à la réponse) : QUAND le module d'images reçoit les octets d'une image, LE SYSTÈME DOIT leur appliquer les contrôles de F-022-AC14 avant de les enregistrer ou de les afficher, et prendre le type de contenu de l'adresse `blob:` dans la liste des types d'après le type constaté, jamais dans l'en-tête de la réponse ; SI les octets reçus ne sont pas une image conforme, ALORS LE SYSTÈME DOIT afficher « Image illisible », ne rien enregistrer et ne créer aucune adresse `blob:` ; un test DOIT servir un document HTML et un SVG sous `Content-Type: image/png` et le constater.
  - Limites du serveur
    - F-022-AC22 (limite de corps propre à la route) : LE SYSTÈME DOIT lire le corps d'un `PUT` d'image avec une limite de 5 242 880 octets, propre à cette route ; SI l'en-tête `Content-Length` annonce davantage, ALORS LE SYSTÈME DOIT répondre 413 `corps-trop-grand` sans lire le corps ; SI le corps dépasse la limite en cours de lecture, ALORS LE SYSTÈME DOIT cesser de le lire, répondre 413 et ne rien stocker ; SI le corps n'est pas reçu en entier 60 secondes après le début de la requête, ALORS LE SYSTÈME DOIT fermer la connexion sans rien stocker. La limite de 100 kilo-octets de F-008-AC6 DOIT rester celle de toute autre route : un test de couture DOIT énumérer les routes enregistrées et constater que chacune, hors le `PUT` d'image, répond 413 à un corps de 101 kilo-octets, et que le `PUT` d'image n'accepte un corps que sous `application/octet-stream`.
    - F-022-AC23 (quotas par espace) : SI l'espace compte déjà 2 000 images, ou si l'image porterait le volume de ses images au-delà de 500 mébioctets, ALORS LE SYSTÈME DOIT répondre 409 `quota-atteint` sans rien stocker ; la vérification et l'écriture DOIVENT se faire dans une même transaction qui verrouille l'espace, pour que deux téléversements simultanés ne dépassent pas le quota (limite de preuve : H12) ; un `PUT` rejoué de F-022-AC16 NE DOIT PAS compter deux fois.
    - F-022-AC24 (débit) : SI un même compte dépasse 60 requêtes `PUT` d'image en 60 secondes, réussies ou non, ALORS LE SYSTÈME DOIT répondre 429 aux requêtes en excès avec l'enveloppe `trop-de-requetes` et un en-tête `Retry-After` (entier de 1 à 60), sans lire le corps, quelle que soit la valeur de `NODE_ENV`, prouvé par un test à horloge injectée.
    - F-022-AC25 (journal) : QUAND une image est stockée ou refusée, LE SYSTÈME DOIT écrire une ligne de journal avec le type d'événement, l'identifiant de requête, l'identifiant du compte, celui de l'espace, celui de l'image, la taille reçue et le motif du refus, et NE DOIT y écrire ni un octet de l'image, ni son empreinte, ni un nom de fichier ; SI le stockage ou la lecture échoue, ALORS LE SYSTÈME DOIT répondre 500 `erreur-interne` dans les conditions de F-008-AC8, sans que le message de l'erreur de la base, qui porte les octets en paramètre, atteigne le journal ou la réponse (comme F-012-AC26).
  - Stockage
    - F-022-AC26 (table des images) : QUAND les migrations de `packages/db` sont appliquées sur une base à l'état laissé par F-012, LE SYSTÈME DOIT créer la table des images avec une clé primaire (espace, identifiant d'image), les octets en colonne binaire (`bytea`, par le type personnalisé de F-012-AC28), le type contraint en base aux trois valeurs de la liste, la taille, la largeur, la hauteur, l'empreinte SHA-256 et la date de réception, et la suppression en cascade des images d'un espace supprimé (F-011-AC6) ; elle NE DOIT porter ni identifiant de compte, ni nom de fichier (H5) ; un test DOIT constater qu'une image de 5 242 880 octets écrite puis relue est identique octet pour octet, et qu'après la suppression de son espace les deux routes répondent 404 et la table ne compte plus aucune de ses lignes ; les critères F-008-AC15 et AC16, F-009-AC21, F-011-AC30 et F-012-AC28 DOIVENT rester vrais.
    - F-022-AC27 (base d'images de l'appareil) : LE SYSTÈME DOIT enregistrer les images d'un espace dans la base IndexedDB `notionlike:images:<idEspace>`, nommée par la fonction de F-002-AC25 et ouverte par le seul module de persistance, dont l'interface exige l'identifiant de l'espace ; chaque entrée porte l'identifiant d'image, les octets, le type constaté et son état (en attente, transmise, reçue, envoi refusé) ; SI l'identifiant d'espace n'est pas un UUID canonique, ALORS LE SYSTÈME DOIT refuser sans ouvrir de base ; un test DOIT enregistrer une image dans un espace A, la demander sous le même identifiant dans un espace B et n'y rien trouver ; QUAND la copie locale d'un espace est effacée (F-013-AC24, et tout autre effacement d'un espace de l'appareil livré à la date du commit), LE SYSTÈME DOIT effacer aussi sa base d'images, prouvé par un test qui énumère les modules qui effacent les bases d'un espace.
  - Téléversement différé et réception
    - F-022-AC28 (envoi dès que possible) : QUAND une image est en attente et que le rattachement de son espace est `adopte`, l'état du compte `connecte` et le droit connu celui d'écrire, LE SYSTÈME DOIT l'envoyer par `PUT`, une image à la fois, à l'insertion, à l'ouverture de l'application, au retour du réseau et au passage du compte à `connecte`, puis l'inscrire comme transmise sur un 201 ou un 200 ; un test DOIT insérer trois images hors ligne, recharger, rétablir le réseau et constater les trois sur le serveur, identiques octet pour octet, sans geste de l'utilisateur. TANT QUE l'une de ces conditions manque, LE SYSTÈME NE DOIT émettre aucune requête d'image (F-013-AC7 reste vrai : un test DOIT énumérer les requêtes dans chaque combinaison de rattachement et d'état du compte), et l'image reste en attente sans limite de durée.
    - F-022-AC29 (échecs de l'envoi) : SI un envoi échoue par le réseau, par un 5xx ou par un 429, ALORS LE SYSTÈME DOIT le retenter après 1 seconde, puis en doublant l'attente jusqu'à 60 secondes au plus (au moins le délai de `Retry-After` pour un 429), sans limite de nombre ; SI la réponse est 401, ALORS il DOIT faire revérifier l'état du compte (F-010-AC28) et suspendre les envois ; SI elle est 403 ou 404, ALORS il DOIT suspendre les envois de cet espace jusqu'au prochain changement de droit ou de rattachement, les images restant en attente ; SI elle est 400 `image-refusee`, 413 ou 409 `identifiant-indisponible`, ALORS il DOIT inscrire l'image en envoi refusé et ne plus l'envoyer ; SI elle est 409 `quota-atteint`, ALORS il DOIT suspendre les envois de cet espace jusqu'au rechargement ou à l'action « Réessayer » ; dans tous les cas l'image DOIT rester affichée sur l'appareil qui la détient, et aucune erreur non interceptée ni rejet non géré NE DOIT être émis.
    - F-022-AC30 (ce que voit un autre membre) : QUAND un bloc image d'identifiant valide est affiché et que l'appareil n'en détient pas les octets, LE SYSTÈME DOIT, si les conditions de lecture sont réunies (rattachement `adopte`, compte `connecte`), demander l'image par `GET`, et sur un 200 conforme (F-022-AC21) l'enregistrer comme image reçue et l'afficher, sans rechargement ; sur un 404, il DOIT afficher « Image pas encore envoyée par l'appareil qui l'a insérée » et redemander après 5 secondes, puis en doublant l'attente jusqu'à 60 secondes, tant que le bloc est affiché ; hors ligne ou sans ces conditions, il DOIT afficher « Image indisponible hors ligne » sans émettre de requête, et redemander quand elles reviennent. Chaque état DOIT être un texte lisible par les technologies d'assistance, à la place de l'image, et NE DOIT émettre aucune mise à jour Yjs. Une image reçue DOIT ensuite s'afficher réseau coupé et après rechargement.
    - F-022-AC31 (état visible de l'envoi) : LE SYSTÈME DOIT indiquer sur un bloc image dont l'image est en attente « En attente d'envoi », et en envoi refusé « Envoi refusé : cette image reste sur cet appareil et les autres membres ne la verront pas », avec le message que la table d'`apps/web` associe au code reçu ; TANT QU'une image de l'espace ouvert est en attente et que l'espace est `adopte`, LE SYSTÈME NE DOIT PAS afficher « Synchronisé » dans la zone de synchronisation, mais « Images en attente d'envoi : <nombre> », et un envoi refusé ou suspendu par quota DOIT y figurer comme une cause de « Synchronisation en erreur » ; la liste fermée de F-013-AC31 et la condition de F-013-AC32 sont étendues en ce sens, et leurs tests modifiés par cette feature (H13).
  - Version du format et montée de version (règle de F-028 H1 à H3 et F-005 H1 à H3, socle de F-003)
    - F-022-AC32 (numéro et ligne) : LE SYSTÈME DOIT ajouter à la table des versions une ligne dont le numéro est la version prise en charge par `main` au premier commit de code de cette feature, plus un, et qui ajoute à la ligne précédente le nœud `image`, bloc de premier niveau sans contenu, avec les attributs `idImage` et `alt` et eux seuls ; le test de F-003-AC22 (numéros sans trou, chaque ligne contient la précédente, schéma de l'éditeur égal à la dernière ligne, version prise en charge égale à son numéro) DOIT passer.
    - F-022-AC33 (lecture d'une version antérieure, écriture de la version) : QUAND un document de page d'une version antérieure prise en charge est ouvert, LE SYSTÈME DOIT afficher tout son contenu sans émettre de mise à jour Yjs ni changer sa version, pour chaque ligne antérieure de la table ; QUAND une modification locale inscrit pour la première fois un bloc image dans un document dont la version est inférieure à celle de F-022-AC32, LE SYSTÈME DOIT élever la version à ce numéro avant, ou dans, la transaction Yjs qui inscrit le bloc, par la seule opération de F-003-AC31, quel que soit le chemin (commande, menu slash, dépôt, collage d'un fichier, collage d'un bloc image) ; un test DOIT, pour chaque chemin, constater qu'aucune mise à jour portant un nœud `image` n'est émise avant celle qui porte la version, puis annuler une fois et constater que le bloc est retiré ; SI l'élévation et l'inscription partagent une transaction, ALORS elle DOIT porter l'origine de la liaison de l'éditeur (F-028-AC21).
    - F-022-AC34 (la version ne baisse jamais, refus d'une version supérieure) : QUAND l'utilisateur annule jusqu'à épuiser l'historique après avoir inséré un bloc image dans un document de version antérieure, LE SYSTÈME DOIT avoir retiré le bloc du contenu lu et lire toujours la version de F-022-AC32, sur ce document et sur un document vierge qui en reçoit les mises à jour (F-003-AC23 et AC31 ne sont ni réécrits ni doublés ; la forme stockée de la version reste hors de la portée de tout historique d'annulation) ; SI la version d'un document dépasse la version prise en charge, ALORS LE SYSTÈME DOIT se comporter comme F-003-AC19 et AC29 le prescrivent, prouvé par un test sur un document de la version prise en charge plus un.
    - F-022-AC35 (couture du format et de `@notionlike/document`) : LE SYSTÈME DOIT enregistrer un bloc image dans le fragment XML du document de page comme un nœud `image` sans enfant, avec les seuls attributs `idImage` et `alt`, sans nouveau type racine ; un test DOIT insérer une image par chaque chemin de F-022-AC33, lire le fragment par `yjs` seul et constater ces deux clés et aucune autre, aucun octet de l'image et aucune adresse ; relever la version prise en charge par `@notionlike/document` sans nouvel export, sans retoucher les lignes précédentes de la table ni les exports livrés (les tests de couture des exports passent sans que leurs listes changent) ; un test DOIT énumérer les appelants du format du document de page et de la lecture, de la vérification et de l'élévation de la version (module d'édition, module de persistance, façade, module de synchronisation, et tout autre module qui s'en sert) et échouer si l'un d'eux n'est couvert par aucun test qui lui présente un document de chaque ligne de la table et un document de la version prise en charge plus un ; un document qui contient un bloc image, enregistré par la persistance puis relu dans un document vierge, DOIT donner le même contenu lu. Deux répliques qui insèrent chacune une image dans la même page hors ligne puis convergent DOIVENT lire les deux blocs, dans le même ordre.
  - Structure, contrats et coutures
    - F-022-AC36 (contrat) : LE SYSTÈME DOIT publier depuis `packages/contrats` : les chemins des deux routes et la fonction qui les construit (F-022-AC9) ; la liste des types, leurs signatures et leurs types de contenu ; les limites de F-022-AC11 ; les fonctions de F-022-AC8, AC12 et AC13 ; le code d'erreur `image-refusee`, ajouté à la liste fermée, les autres codes étant ceux déjà publiés ; le rattachement des deux routes aux actions `lire-contenu` et `ecrire-contenu` de la matrice, qui n'est pas modifiée ; `packages/contrats` DOIT rester conforme à F-008-AC23 (importable dans un navigateur, `zod` pour seule dépendance d'exécution directe), les fonctions de cette feature étant pures, sans dépendance et exécutées à l'identique sous Node et dans le navigateur (H8).
    - F-022-AC37 (un code, un message) : LE SYSTÈME DOIT associer au code `image-refusee`, dans la table de messages d'`apps/web` (F-010-AC16), le message « Le serveur a refusé cette image : PNG, JPEG ou WebP, 5 Mo et 8 192 pixels de côté au plus. », et afficher pour `quota-atteint` reçu d'une route d'images « L'espace a atteint sa limite d'images : celle-ci reste sur cet appareil. » ; aucun code brut ni champ `message` du serveur NE DOIT être affiché (F-010-AC18).
    - F-022-AC38 (confinement côté client) : LE SYSTÈME DOIT réserver au module d'images les appels des routes d'images, par des chemins relatifs vers l'origine qui sert l'application, authentifiés par le seul cookie de session (F-010-AC20, AC21) ; le module d'édition NE DOIT émettre aucune requête : il reçoit du module d'images, par une interface qui n'expose ni `fetch` ni type de Tiptap, l'état d'affichage d'une image et l'enregistrement d'un fichier ; F-003-AC21 DOIT rester vrai pour le module d'édition (suite où `fetch`, `XMLHttpRequest`, `WebSocket` et `EventSource` font échouer le test, images fournies par une doublure), F-003-AC27 pour Tiptap et sa vue de nœud, et F-002-AC19 pour l'application entière ; le module d'images NE DOIT importer ni le module d'édition ni le fournisseur de synchronisation ; `pnpm contrats` DOIT finir sans violation.
    - F-022-AC39 (couture de F-003 à F-013) : QUAND cette feature est livrée, LE SYSTÈME DOIT conserver à l'identique le comportement livré, prouvé par un test de couture qui énumère ce qu'elle touche : toutes les routes HTTP et le point de synchronisation gardent leurs statuts, leurs corps, leurs en-têtes et leur limite de corps (F-022-AC22) ; le serveur n'ouvre aucun document, n'en lit aucun et n'y écrit jamais du fait d'une image (F-012-AC17 reste vrai) ; `SIGTERM` reste tenu dans le délai de F-008-AC7 avec un téléversement en cours ; les scénarios de bout en bout livrés passent sans modification ; le collage et le dépôt sans fichier se comportent comme avant (F-003-AC13, F-028-AC13 et AC14, F-006-AC21) ; un `lecteur` (F-013-AC25) ne peut ni insérer d'image ni en envoyer, mais les lit ; le test de F-010-AC19 passe avec la base d'images pour seule entrée nouvelle du stockage du navigateur, sans jeton ni donnée de compte.
    - F-022-AC40 (accessibilité) : LE SYSTÈME DOIT rendre « Image », le champ du texte alternatif et « Réessayer » atteignables et déclenchables au clavier seul avec un nom accessible en français ; un bloc image DOIT pouvoir être sélectionné et supprimé au clavier ; une image sans texte alternatif DOIT être rendue avec un `alt` vide, et ses états de F-022-AC30 et AC31 lus par les technologies d'assistance ; si F-004 est livrée, seuls ses jetons sont employés et toute animation respecte F-004-AC11 à AC13.

  - Image désignée par une adresse web, aperçu d'un lien, capture d'une page : aucune image ne naît d'une adresse (F-022-AC5).

- Hypothèses tranchées par agent-planif en l'absence du dev, que la validation de cette spec entérine :
  - H1 — Le bloc image ne porte qu'une référence, comme F-003 H1 le pose : un identifiant d'image et un texte alternatif. Ni octets (un document Yjs ne s'allège jamais : une image inscrite y pèserait pour toujours, et dépasserait les limites de F-012-AC22 et AC23), ni adresse (un pair en écriture peut inscrire n'importe quoi dans le fragment : une adresse lue dans le document ferait émettre à chaque lecteur une requête vers l'hôte de son choix, avec son adresse IP, ou vers une route de l'application). La référence est donc validée comme identifiant (F-022-AC8), l'adresse construite par l'application avec l'espace ouvert (F-022-AC9), et la route est rangée par espace (F-022-AC18). Les dimensions ne sont pas dans le bloc : la mise en page se cale à l'affichage. Difficile à défaire : c'est le format stocké.
  - H2 — Nœud écrit avec le seul noyau de Tiptap, déjà présent, et non avec l'extension d'image de la bibliothèque, dont le modèle est une adresse (`src`) : tout ce qu'elle apporte serait à désactiver. Aucune dépendance directe nouvelle côté client. Le nœud est un bloc de premier niveau, sans contenu, rendu par une vue de nœud du module d'édition, qui affiche l'état donné par le module d'images. À confirmer par la veille, non couvert par `MEMORY/VEILLE.md` : la forme d'un nœud sans contenu dans le fragment Yjs et sa convergence ; une vue de nœud React sous jsdom et Vitest ; le dépôt et le collage de fichiers (`DataTransfer.files`, `clipboardData.files`) sous jsdom et dans Chromium ; l'ouverture du sélecteur de fichiers depuis une commande du menu slash (activation par l'utilisateur) ; `URL.createObjectURL` et `Blob` sous jsdom ; l'enregistrement d'un tableau d'octets de 5 mébioctets sous `fake-indexeddb` ; le comportement de la poignée de F-006 sur un tel nœud.
  - H3 — Identifiant d'image tiré par l'appareil (`crypto.randomUUID()`, 122 bits d'aléa), et non attribué par le serveur ni dérivé du contenu : l'insertion doit réussir hors ligne, donc avant tout échange ; un identifiant dérivé du contenu permettrait à un membre de vérifier si un fichier donné existe dans l'espace sans l'ouvrir et ne serait pas « imprévisible ». L'imprévisibilité n'est pas la barrière d'accès : c'est l'adhésion à l'espace, relue à chaque requête (F-022-AC18). Le `PUT` à identifiant choisi par le client est rejouable sans doublon (F-022-AC16), et l'immuabilité empêche un membre en écriture de remplacer l'image d'un autre sous le même identifiant.
  - H4 — Stockage côté serveur : une colonne binaire dans PostgreSQL, et non le système de fichiers du conteneur ni un stockage d'objets. Pesé ainsi : la criticité est « interne » et l'équipe petite ; aucune feature ne couvre le déploiement ni la sauvegarde, et une seule base à sauvegarder vaut mieux qu'une base plus un volume de fichiers à garder cohérents ; la suppression d'un espace emporte ses images par la cascade, dans la même transaction (F-011-AC6), et le quota se vérifie sous le même verrou ; aucun service ni volume nouveau dans Docker Compose, donc aucun travail d'`agent-devops` ; le type personnalisé `bytea` existe depuis F-012-AC28. Ce qu'on y perd : la base grossit (au plus 500 mébioctets par espace), chaque image traverse la mémoire du serveur (d'où 5 mébioctets au plus et le débit de F-022-AC24), et un vidage de la base contient les images. Un stockage d'objets est noté comme évolution : il ne change ni les routes ni le format du document, seulement le module de stockage ; se défait par une migration des lignes, sans toucher aux appareils. À confirmer par la veille : lecture et écriture d'un `bytea` de 5 mébioctets par PGlite et par le pilote `pg` (F-012-AC28 n'a été éprouvé qu'à 256 kibioctets).
  - H5 — Aucun identifiant de compte dans la table des images : une image est un contenu de l'espace, comme le texte d'une page, qui ne porte pas d'auteur ; ne pas lier l'image à un compte évite une donnée personnelle de plus à exporter et à effacer (F-025). Le journal garde qui a téléversé (F-022-AC25), le temps de sa conservation.
  - H6 — Une image dont le bloc est supprimé, dont l'insertion est annulée ou dont la page est supprimée définitivement reste stockée, sur le serveur et sur l'appareil, jusqu'à la suppression de l'espace : le serveur ne lit aucun document (F-012-AC17) et ne peut donc pas savoir qu'une image n'est plus désignée ; un appareil ne le sait pas davantage tant qu'il n'a pas relu toutes les pages. Le ramasse-miettes, qui demande une route de suppression et un parcours des pages par un appareil, est reporté sur F-025 avec le reste de l'effacement. Conséquence acceptée : le quota de 2 000 images se remplit aussi d'images abandonnées. Une image en attente est envoyée même si son bloc a été annulé entre-temps : rétablir la modification doit retrouver l'image.
  - H7 — Les métadonnées sont retirées, par l'appareil qui insère, avant tout enregistrement, et le serveur vérifie sans transformer (F-022-AC13, AC14). Raisons : une photo de téléphone porte la position, la date et le modèle de l'appareil, données personnelles que l'auteur ne sait pas qu'il partage (RGPD) ; un traitement côté serveur demanderait une bibliothèque d'image à module natif, que l'image Alpine (musl) de l'ADR-0006 rend coûteuse et que rien d'autre ne justifie ; un réencodage par le navigateur (canevas) dégraderait l'image, ne se prouverait pas sous Vitest et laisserait le serveur sans moyen de vérifier. Le nettoyage est donc une réécriture au niveau des octets, par liste fermée de parties gardées, sans décodage : ce qu'elle ne connaît pas est retiré, octets ajoutés après la fin de l'image compris (parade aux fichiers à double lecture). Le serveur refuse un corps qui n'est pas égal à sa forme nettoyée : un client défectueux ne peut pas déposer de métadonnées par mégarde. Limite acceptée : un client malveillant peut cacher des données dans les données mêmes de l'image, comme dans le texte d'une page ; ce n'est pas le risque visé. Orientation : un JPEG de téléphone s'appuie sur l'orientation EXIF ; la retirer coucherait la photo ; elle est donc la seule donnée EXIF réinscrite, sous une forme construite par l'application. PNG et WebP : toutes les données EXIF sont retirées ; à confirmer par la veille que les navigateurs visés n'appliquent pas, ou appliquent rarement, une orientation EXIF à ces deux types (sinon la même réinscription s'y ajoute, sans changer cette spec autrement). Listes exactes des parties gardées par type : fixées par la conception, en un seul endroit.
  - H8 — Les trois fonctions pures (référence, type constaté, nettoyage) vivent dans `packages/contrats`, seul paquet importé à la fois par le serveur et par le navigateur et situé dans le périmètre d'un producteur. C'est une seconde précision de F-008 H2 (« aucune logique »), après le codec du nom de document de F-012 H2, limitée à ces fonctions sans dépendance : appliquer la même règle des deux côtés est précisément ce qu'un contrat doit garantir, et deux copies divergeraient. Un paquet dédié a été écarté : aucun périmètre d'agent ne le couvrirait sans modifier un fichier protégé. À consigner par un ADR de la conception.
  - H9 — Types : PNG, JPEG et WebP. PNG pour les captures d'écran, JPEG pour les photos, WebP parce que c'est ce qu'un navigateur enregistre désormais d'une page. GIF et AVIF sont écartés pour tenir la feature dans une session (chaque type demande son nettoyage), SVG parce que c'est un document actif. Limites de F-022-AC11 : garde-fous arbitraires, relevables sans toucher au format ; celles de dimensions protègent le navigateur des autres membres d'une image de quelques kilo-octets qui se décode en plusieurs giga-octets.
  - H10 — Base d'images par espace, sur l'appareil, par l'interface IndexedDB du navigateur sans bibliothèque, derrière le module de persistance (F-002-AC22, AC25). Elle sert trois choses : l'affichage immédiat, la file d'attente du téléversement (l'état « en attente » est la seule mémoire de ce qui reste à envoyer), et la copie hors ligne des images reçues. Le service worker de F-023 ne met rien en cache sous `/api/` : c'est cette base, et non un cache HTTP, qui rend une image lisible hors ligne, d'où `Cache-Control: no-store` (F-022-AC20), qui évite aussi qu'une image survive dans un cache que « Effacer la copie locale » ne vide pas. Une image jamais affichée sur un appareil n'y est pas disponible hors ligne : la précharger demanderait de lire toutes les pages pendant la passe de fond ; écarté ici, à rouvrir si l'usage le demande.
  - H11 — Sur un appareil partagé, une image insérée hors ligne part sous le compte suivant s'il est membre en écriture de l'espace : même limite que F-013 H3 et H5, pour la même raison (le registre ne porte aucun compte). Un espace `local` garde ses images en attente sans durée limite ; elles partent à l'adoption.
  - H12 — Deux niveaux de test. Sous Vitest, dans les hooks : les fonctions pures (tables de cas, test de propriété), les routes contre la base embarquée (F-008-AC18), le module d'images en environnement Node contre le serveur réel de la fabrique d'essai (F-012-AC36), l'éditeur sous DOM simulé avec une doublure du module d'images, les documents reçus écrits par `yjs` seul. Limites : sous jsdom, aucune image n'est décodée ni affichée, et le dépôt comme le collage sont des événements construits par le test ; PGlite n'exerce ni la concurrence du quota (F-022-AC23 n'est prouvé que par la présence du verrou) ni le pilote `pg` sur une colonne binaire de 5 mébioctets : la dette D-002 proposée s'étend à cette feature. Sous Playwright, hors des hooks tant que D-003 n'est pas levée : F-022-AC41, seule preuve qu'une image s'affiche réellement, que rien ne s'exécute et que la navigation vers une image télécharge.
  - H13 — Cette feature modifie des tests de features livrées, comme F-028 H8 le fait : le test de F-006-AC35 (un fichier image conforme lâché est désormais inséré, tout autre fichier reste refusé) ; ceux de F-013-AC31 et AC32 (un état de plus, une condition de plus à « Synchronisé ») ; la liste attendue de F-010-AC19 (une base de plus) ; la table des versions et la version prise en charge. F-003-AC21 se lit désormais ainsi : le module d'édition n'émet aucune requête ; l'affichage d'une image peut en faire émettre une au module d'images, vers la seule origine de l'application et sous les conditions de F-022-AC28 et AC30. F-003-AC13 se lit ainsi : du presse-papiers ne survivent que ce que décrit le schéma, dont un bloc image désigné par `data-id-image` (F-022-AC5).
  - H14 — Aucune politique de contenu n'est posée sur la coquille par une spec à ce jour. Si l'une en pose une, sa directive d'images devra admettre `blob:` et rien d'autre que l'origine : à porter par cette feature-là.
