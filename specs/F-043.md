# SPEC F-043 — Administrateur d'instance : voir et gérer tous les espaces

Statut : validée
Tier : structurel
Revue : reviewer-backend, reviewer-api, reviewer-bdd, reviewer-frontend

- Objectif (une phrase, côté métier) : un administrateur de l'instance voit tous les espaces du serveur, même sans en être membre, et les gère (création, renommage, suppression, membres et rôles), tandis qu'un simple utilisateur ne voit que les espaces dont il est membre.
- Origine : décision du dev du 2026-10-30 : « Un admin peut tout gérer en terme d'espace et tout voir ». Reprend la question de panneau d'administration de la ROADMAP (« À prévoir », « Manques signalés »).
- Dépend de : F-037 (le dev l'a demandée avec l'écran d'accès ; l'écran d'administration s'ouvre derrière lui) ; F-011, F-012, F-014, F-032 (livrées).
- Vocabulaire :
  - « administrateur » : un compte inscrit dans la table `administrateur` (H1, H2). « Simple utilisateur » : tout autre compte.
  - « droit d'administration » : sur tout espace, que l'administrateur en soit membre ou non, les actions `lire-espace`, `lister-membres`, `renommer-espace`, `supprimer-espace`, `inviter`, `retirer-membre`, `changer-role` de la matrice de F-011, et elles seules (H3). `lire-contenu`, `ecrire-contenu` et `quitter-espace` n'en font pas partie.
  - « module d'autorisation » : `apps/server/src/autorisation.ts`, seul module du serveur qui décide (F-011-AC9). « matrice des droits », « rôle », « membre » : F-011. « synchronisation » : F-012.
- Critères d'acceptation :
  - Désignation de l'administrateur
    - F-043-AC1 : QUAND la commande serveur `administrateur:ajouter <courriel>` est lancée avec le courriel d'un compte existant, LE SYSTÈME DOIT inscrire ce compte dans la table `administrateur` (une ligne par compte, idempotent : pour un compte déjà administrateur, sortir avec le code 0 sans rien écrire ni journaliser), journaliser l'événement `administrateur-ajoute` avec l'identifiant du compte, et sortir avec le code 0 ; QUAND `administrateur:retirer <courriel>` est lancée, LE SYSTÈME DOIT retirer la ligne et journaliser `administrateur-retire`.
    - F-043-AC2 : SI le courriel ne désigne aucun compte, ALORS la commande DOIT sortir avec un code non nul, sans rien écrire, et dire « Aucun compte avec ce courriel » ; SI `administrateur:retirer` désigne un compte qui n'est pas administrateur, ALORS elle DOIT sortir avec le code 1, sans rien écrire ni journaliser, et dire « Ce compte n'est pas administrateur » ; la commande NE DOIT afficher ni mot de passe, ni jeton, ni empreinte.
    - F-043-AC3 : LE SYSTÈME NE DOIT offrir aucune route REST, aucune route d'authentification et aucun écran qui désigne ou retire un administrateur : seule la commande serveur le fait (H1) ; un test DOIT énumérer les routes publiées par `packages/contrats` et n'y trouver aucune qui écrive dans la table `administrateur`.
    - F-043-AC4 : QUAND un compte administrateur est supprimé (F-025, à venir) ou que sa ligne `compte` disparaît, LE SYSTÈME DOIT retirer sa ligne `administrateur` (clé étrangère avec suppression en cascade, comme `adhesion`).
  - Identité exposée à l'application
    - F-043-AC5 : QUAND un compte connecté appelle `GET /api/v1/moi`, LE SYSTÈME DOIT ajouter à la réponse le champ booléen `administrateur`, vrai si et seulement si le compte figure dans la table `administrateur`, relu en base à chaque requête (aucun cache) ; le schéma strict de `packages/contrats` le déclare obligatoire.
    - F-043-AC6 (couture de F-009, F-010, F-027) : LE SYSTÈME DOIT, puisque le schéma de `moi` change de forme, énumérer par un test de couture tous les appelants et consommateurs du schéma (le module d'état du compte d'`apps/web`, F-010-AC27 et AC28, le client de gestion du compte de F-027, les réponses simulées des tests d'`apps/web`, les tests de `GET /api/v1/moi` du serveur) et constater qu'aucun ne casse ; un champ `administrateur` absent d'une réponse reçue DOIT être traité par le client comme un échec de conformité (F-010-AC2, état `inconnu`), jamais comme `false`.
    - F-043-AC7 : LE SYSTÈME NE DOIT jamais décider un droit d'après la valeur `administrateur` reçue par le client : l'interface s'en sert pour montrer ou masquer des commandes seulement, et le serveur décide seul à chaque requête (F-014-AC28 reste vrai).
  - Voir tous les espaces
    - F-043-AC8 : QUAND un administrateur appelle `GET /api/v1/administration/espaces`, LE SYSTÈME DOIT répondre 200 avec tous les espaces non supprimés, chacun avec son identifiant, son nom, le nombre de ses membres, le nombre de ses propriétaires et le rôle de l'administrateur s'il en est membre (absent sinon), dans un ordre stable (nom, puis identifiant, en collation « C », l'ordre des codes ; l'écran peut retrier pour l'affichage), sans pagination tant que le total reste sous 500 ; au-delà, la réponse porte les 500 premiers et un indicateur `tronque` vrai.
    - F-043-AC9 : SI un simple utilisateur, ou une requête sans session, appelle une route de `/api/v1/administration/`, ALORS LE SYSTÈME DOIT répondre 403 `acces-refuse` (sans session : 401 `non-authentifie`, F-009-AC25), sans corps qui révèle l'existence d'un espace ni le nombre d'espaces ; l'origine est vérifiée comme pour toute route à effet (F-009-AC16), et aussi en `GET`, comme pour toutes les routes d'espace.
    - F-043-AC10 : LE SYSTÈME DOIT garder `GET /api/v1/espaces` (liste des espaces du compte) inchangée, y compris pour un administrateur : seuls les espaces dont le compte est membre y figurent ; un test DOIT constater qu'un administrateur non membre d'un espace ne le trouve pas dans cette liste (les espaces que l'appareil ouvre, F-032, restent ceux dont le compte est membre).
    - F-043-AC11 : QUAND un administrateur appelle `GET /api/v1/espaces/:idEspace` ou `GET /api/v1/espaces/:idEspace/membres` sur un espace dont il n'est pas membre, LE SYSTÈME DOIT répondre 200 avec le contenu de ces routes, le rôle rendu étant « absent » (l'administrateur n'est pas membre) et non un rôle inventé, et la liste des membres comportant leur courriel (comme pour un propriétaire : l'administrateur voit tout en matière d'espace) ; un non-membre simple utilisateur continue de recevoir le refus uniforme de F-011-AC12.
  - Gérer tous les espaces
    - F-043-AC12 : QUAND un administrateur renomme (`PATCH /api/v1/espaces/:idEspace`), supprime (`DELETE`), invite (`POST …/invitations`, `GET`, `DELETE …/invitations/:idInvitation`), change le rôle (`PATCH …/membres/:idCompte`) ou retire un membre (`DELETE …/membres/:idCompte`) d'un espace, qu'il en soit membre ou non et quel que soit son rôle de membre (y compris `lecteur`), LE SYSTÈME DOIT l'autoriser comme s'il était propriétaire pour ces actions seules, appliquer les règles de F-011 inchangées (dernier propriétaire : `dernier-proprietaire`, quotas, jeton d'invitation affiché une seule fois) et journaliser `action-administrateur` avec l'action, l'identifiant de l'espace et celui du compte administrateur.
    - F-043-AC13 : QUAND un administrateur crée un espace (`POST /api/v1/espaces`), LE SYSTÈME DOIT le traiter comme tout compte : il en devient `proprietaire`, avec le quota de F-011 (H8 de F-011) ; l'administrateur ne crée pas d'espace au nom d'un autre compte (H5).
    - F-043-AC14 : SI un administrateur demande une action hors du droit d'administration sur un espace dont il n'est pas membre (`lire-contenu`, `ecrire-contenu`, `quitter-espace`), ALORS LE SYSTÈME DOIT la refuser comme à un non-membre : l'ouverture d'un document par la synchronisation (F-012-AC5, AC6) reste décidée par l'adhésion seule ; un test de couture DOIT énumérer les appelants du module d'autorisation (routes de F-011, synchronisation de F-012, présence de F-015 si elle est livrée avant) et constater que seuls les appelants des actions du droit d'administration reçoivent la décision étendue.
    - F-043-AC15 : QUAND un administrateur veut lire ou écrire le contenu d'un espace dont il n'est pas membre, LE SYSTÈME DOIT l'y laisser entrer par les moyens existants et journalisés : créer une invitation (`editeur` ou `lecteur`, F-011) et l'accepter avec son compte (F-014-AC22, AC23) ; aucune route nouvelle n'ajoute un membre sans son consentement ni sans journal.
    - F-043-AC16 : QUAND un administrateur est retiré (`administrateur:retirer`) ou qu'un espace est supprimé, LE SYSTÈME DOIT appliquer les effets de F-011 et F-012 sans changement (fermeture des ouvertures de synchronisation de l'espace supprimé) ; retirer l'administrateur ne ferme aucune connexion de synchronisation, parce qu'il n'en tenait aucune au titre de son rôle.
    - F-043-AC17 (limite) : SI un administrateur change le rôle du dernier propriétaire d'un espace ou le retire, ALORS LE SYSTÈME DOIT répondre 409 `dernier-proprietaire` comme à un propriétaire (F-011-AC13) ; seule la suppression de l'espace est possible pour l'administrateur dans ce cas.
  - Interface d'administration (minimale)
    - F-043-AC18 : QUAND l'état du compte est `connecte` et que `moi` porte `administrateur: true`, LE SYSTÈME DOIT afficher dans la barre latérale une entrée « Administration » qui mène à `#/administration` ; pour tout autre compte l'entrée et l'adresse NE DOIVENT ni être rendues ni être atteignables (l'adresse affiche « Page introuvable », F-002-AC13, sans appeler la route d'administration).
    - F-043-AC19 : QUAND `#/administration` est ouvert, LE SYSTÈME DOIT lister les espaces de `GET /api/v1/administration/espaces` (nom, nombre de membres, rôle de l'administrateur ou « non membre »), mener de chacun à son écran `#/espaces/<idEspace>` de F-014 (où les commandes de membres, rôles, renommage et suppression se montrent d'après le droit d'administration, F-043-AC20), afficher « Liste tronquée » quand `tronque` est vrai, et dire « Demande une connexion au serveur » hors ligne, avec les actions désactivées et leur raison (F-014-AC29).
    - F-043-AC20 : QUAND un administrateur ouvre l'écran d'un espace dont il n'est pas membre, LE SYSTÈME DOIT afficher la mention « Vous consultez cet espace en tant qu'administrateur, sans en être membre » et les commandes du droit d'administration (F-043-AC12) seulement ; il NE DOIT afficher ni « Quitter cet espace », ni « Ouvrir cet espace » (le contenu reste réservé aux membres, F-043-AC14), ni éditeur ; SI le serveur répond 403 `acces-refuse` (droit retiré depuis), ALORS le message de F-014-AC28 s'applique.
    - F-043-AC21 : LE SYSTÈME DOIT rendre l'écran d'administration réalisable au clavier seul, avec titres, listes et états annoncés aux technologies d'assistance (F-014-AC27 à AC29 repris), et sans écrire ni nom d'espace, ni liste, ni drapeau d'administrateur dans le stockage du navigateur (F-010-AC19, H3 de F-010 et H10 de F-014 restent vrais) ; un test DOIT énumérer le stockage après visite de l'écran.
  - Coutures et bout en bout
    - F-043-AC22 (couture de F-011, F-012, F-014) : QUAND cette feature est livrée, LE SYSTÈME DOIT conserver à l'identique le comportement livré pour tout compte qui n'est pas administrateur : les suites de tests de F-011, F-012 et F-014 passent sans modification hors de la liste fermée de H7, et un test DOIT rejouer la matrice des droits (trois rôles, dix actions, plus non-membre) pour un simple utilisateur et constater les mêmes décisions qu'avant.
    - F-043-AC23 (migration) : QUAND la migration `0003` est appliquée à une base existante contenant des comptes, espaces, adhésions et documents, LE SYSTÈME DOIT ajouter la table `administrateur` sans modifier ni supprimer aucune ligne existante, aucun compte n'étant administrateur (la commande de F-043-AC1 est la seule amorce) ; un test DOIT appliquer la migration sur une base peuplée par `0000` à `0002` et constater les lignes inchangées, sur PGlite et, hors des hooks, sur PostgreSQL (D-002).
    - F-043-AC24 (bout en bout) : QUAND la commande de test de bout en bout est lancée avec la pile de F-031, LE SYSTÈME DOIT dérouler dans un navigateur réel, avec trois comptes (A, B simples utilisateurs, C administrateur désigné par la commande serveur) : A crée un espace et y invite B ; C voit les deux, ouvre l'écran de l'espace de A, change le rôle de B en `lecteur` ; B constate la lecture seule ; C ne peut pas ouvrir le contenu de l'espace de A tant qu'il n'en est pas membre ; A et B ne voient aucune entrée « Administration » et `#/administration` leur affiche « Page introuvable » ; C supprime l'espace, A ne le voit plus.
  - Sécurité transverse
    - F-043-AC25 : LE SYSTÈME DOIT décider tout droit d'administration côté serveur, par le module d'autorisation, à chaque requête REST et pour la synchronisation, par une relecture en base de la table `administrateur` sans cache de session (F-011-AC28 : droits lus à chaque requête) ; SI la lecture échoue (base indisponible), ALORS LE SYSTÈME DOIT refuser comme aujourd'hui (503 `base-indisponible` ou refus), aucun accès par défaut (F-012-AC15).
    - F-043-AC26 : LE SYSTÈME NE DOIT journaliser ni courriel, ni nom, ni jeton d'invitation dans les événements d'administration : identifiants (UUID) seulement (F-011 H12 repris).
- Hors périmètre (explicitement) :
  - Liste ou gestion des comptes (désactiver, supprimer un compte, réinitialiser un mot de passe, voir les courriels de comptes qui ne sont membres d'aucun espace consulté ; les courriels des membres d'un espace que l'administrateur consulte lui sont montrés, F-043-AC11) : F-025 et une feature à demander ; recommandé : non (H6).
  - Accès au contenu (pages, tables) des espaces dont l'administrateur n'est pas membre : non livré (H3).
  - Fermeture ou restriction de l'inscription, invitation obligatoire à l'inscription : non livré, l'inscription reste ouverte (H4) ; limite de débit et audit consultable par écran : non livrés.
  - Création d'un espace au nom d'un autre compte, transfert de propriété autre que le changement de rôle de F-011 (H5).
  - Commande de désignation par l'interface, par route REST, par variable d'environnement ou par premier compte créé (H1).
  - Tout changement des routes d'authentification, de la synchronisation (hors décision d'autorisation) et de la présence de F-015.
- Hypothèses tranchées par agent-planif, que le dev valide (ou change) en validant cette spec :
  - H1 — Comment devient-on administrateur : options (a) le premier compte créé (aucune action, mais sur une instance déjà peuplée il n'y a plus de « premier », et sur une instance exposée n'importe qui l'est en arrivant le premier) ; (b) une commande sur le serveur (`administrateur:ajouter <courriel>`, F-043-AC1) : désignation explicite, auditable, seul celui qui a la main sur le serveur peut la lancer ; (c) une variable d'environnement listant des courriels (relue au démarrage : pas de trace en base, et `.env*` est un fichier que les agents ne lisent pas, donc difficile à prouver). Recommandation : (b), seule compatible avec une instance déjà peuplée (comptes de la RC1) et sans effet de bord au premier lancement. Difficile à défaire : l'amorce choisie conditionne l'exploitation.
  - H2 — Représentation : une table dédiée `administrateur(idCompte PK, FK cascade, créé le)` en migration `0003_administrateurs.sql`, plutôt qu'une colonne sur `user` (table de better-auth : la modifier toucherait le schéma natif, F-009 H2) ou le plugin « admin » de better-auth (dépendance et routes nouvelles à fort périmètre, bannissement et usurpation d'identité inutiles ici). Recommandation : table dédiée. Migration : oui (additive, sans donnée à reprendre), `agent-bdd`, `reviewer-bdd`.
  - H3 — « Tout voir » : l'administrateur voit tous les espaces et leurs membres et gère noms, membres, rôles, invitations et suppression, mais ne lit pas leur contenu sans en être membre ; pour le lire, il s'invite lui-même (F-043-AC15), ce qui laisse une trace et un consentement à l'écran du propriétaire (liste des membres). Raison : le contenu est une donnée de collègues que le serveur ne lit jamais pour eux (F-012 objectif) ; un accès implicite à tout le contenu serait une capacité de lecture invisible des intéressés. Option (B) du dev si « tout voir » inclut le contenu : étendre `lire-contenu` et `ecrire-contenu` à l'administrateur dans le module d'autorisation et la synchronisation, avec un bandeau permanent de l'éditeur et un journal de chaque ouverture : plus coûteux (F-012, F-013, F-015) et plus sensible. Recommandation : option (A), métadonnées seulement.
  - H4 — Inscription : reste ouverte (F-011 H4, risque accepté pour une criticité « interne », serveur non exposé). Fermer l'inscription touche la route native de F-009 et le client de F-010, et n'est pas demandé. Recommandation : ne rien changer maintenant ; à rouvrir avec le déploiement (ROADMAP, « Manques signalés »).
  - H5 — Un simple utilisateur peut encore créer un espace (quota de 20, F-011 H8), comme aujourd'hui : l'administrateur n'est pas un goulot. Alternative : réserver la création aux administrateurs ; elle modifie F-011-AC1, F-014-AC7 et F-013-AC12 (adoption d'un espace de l'appareil par son créateur, F-013 H1), donc la synchronisation d'un espace de l'appareil. Recommandation : ne rien changer.
  - H6 — Panneau d'administration : oui, minimal (F-043-AC18 à AC21), une liste et le renvoi vers l'écran d'un espace existant, parce que sans lui l'administrateur ne verrait les espaces d'autrui que par leur identifiant. Pas de liste de comptes (H6 hors périmètre). Alternative : sans écran, route REST seule : l'administrateur n'a alors aucun moyen de voir à l'application. Recommandation : panneau minimal.
  - H7 — Liste fermée des fichiers de test de features livrées que cette feature modifie (constat sur `origin/main` `a64bf5f`, à reconfirmer par la conception) : `apps/server/test/` : le fichier des tests de `GET /api/v1/moi` (nouveau champ, F-043-AC5 et AC6) et celui des tests du module d'autorisation de F-011 (la matrice reste, un cas d'administrateur s'ajoute : ajout, pas de retouche) ; `apps/web/test/` : les tests qui simulent la réponse de `moi` (aides de tests `aides-compte.tsx` et `compte-client.test.ts`, F-010-AC27) ; écarts constatés par la conception, ajoutés à la liste : E1 `apps/server/test/aides-comptes.ts` (`compteDe` lit le schéma de `moi`) ; E2 `apps/server/test/couture-espaces.test.ts` (F-011-AC33, schéma strict du corps de `moi`) ; E3 `apps/server/test/gestion-du-compte.test.ts` (F-027-AC1, même lecture) ; E4 `apps/server/test/coutures.test.ts` (F-008-AC23 et suivants : noms importés par fichier ; F-031-AC14 : fichiers qui touchent `process`) ; E5 `packages/db/test/structure.test.ts` (F-008-AC17 et suivants : noms de l'entrée publique) ; E6 `packages/db/test/documents-migration.test.ts` (F-012-AC28 : tables publiques après la montée complète) ; `packages/contrats` : test de forme de `moi` et liste des routes (`ROUTES_ESPACES`, ajout de `/api/v1/administration/`). Les noms exacts de fichiers sont constatés par la conception avant le premier bloc, la liste reste fermée : toute autre retouche impose de retoucher cette spec.
  - H8 — Conflits avec les branches en cours (constat du 2026-10-30) : F-036 modifie `apps/web/src/interface/EcranDUnEspace.tsx`, que F-043 retouche pour F-043-AC20 : à fusionner après F-036, ou conflit à résoudre par le propriétaire du fichier ; F-035 et F-036 modifient des tests `espace-*` et `vues-de-table` que F-043 ne touche pas ; F-021 (`vues-de-table/`) et F-034 (`packages/document`) : aucun fichier commun ; F-015 (présence, serveur) : le module d'autorisation est partagé si la présence l'appelle (F-043-AC14 énumère les appelants au moment de la livraison). F-043 dépend de F-037 pour `apps/web/src/main.tsx` et le formulaire d'accès (barre latérale et zone de compte).
  - H9 — Contrat : nouveau champ de `moi`, nouvelle route `GET /api/v1/administration/espaces`, nouvelle entrée d'`ACTIONS` ? Non : le droit d'administration est une liste fermée (`ACTIONS_D_ADMINISTRATION`) de sous-ensemble de `ACTIONS`, publiée par `packages/contrats` et lue par le serveur et le client ; `MATRICE_DES_DROITS` ne change pas. `reviewer-api` relit le contrat.
  - H10 — Aucune nouvelle dépendance directe. La commande serveur est un script de `apps/server/package.json` (fichier partagé : à signaler au dev) qui appelle `packages/db`.
- Pourquoi ce tier : migration (nouvelle table), changement du contrat de `moi` et nouvelle route, extension du module d'autorisation dont dépendent la synchronisation et la présence, nouveau rôle global ; doute : le plus élevé.
