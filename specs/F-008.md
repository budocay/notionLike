# SPEC F-008 — Socle serveur : `apps/server`, PostgreSQL sous Docker Compose, `packages/db`, `packages/contrats`

Statut : brouillon
Tier : structurel
Revue : reviewer-devops, reviewer-bdd, reviewer-backend, reviewer-api

- Objectif (une phrase, côté métier) : l'équipe dispose d'un serveur qui démarre d'une seule commande avec sa base de données, dit s'il est en état de servir, et refuse proprement tout ce qu'il ne connaît pas, pour que les comptes (F-009), les espaces (F-011) et la synchronisation (F-012) se posent dessus sans rouvrir la question du socle.
- Vocabulaire :
  - « serveur » : l'application `apps/server` (Express). Dans cette feature il ne porte aucune donnée métier : ni compte, ni espace, ni document.
  - « base » : l'instance PostgreSQL décrite par le fichier Compose.
  - « migration » : un fichier SQL versionné dans `packages/db`, appliqué une seule fois par base et consigné dans une table de suivi.
  - « enveloppe d'erreur » : le corps JSON de toute réponse d'erreur du serveur, `{ "code": <chaîne stable>, "message": <phrase en français>, "idRequete": <chaîne> }`, sans autre champ. Son schéma est publié par `packages/contrats`.
  - « configuration » : les variables d'environnement lues une seule fois au démarrage, validées avant toute écoute réseau.
  - « secret » : toute valeur de configuration qui donne un accès (mot de passe de la base, URL de connexion qui le contient).
- Critères d'acceptation :
  - Serveur HTTP
    - F-008-AC1 : QUAND le serveur reçoit `GET /sante`, LE SYSTÈME DOIT répondre 200 avec le corps `{ "etat": "ok" }` conforme au schéma publié par `packages/contrats`, sans interroger la base.
    - F-008-AC2 : QUAND le serveur reçoit `GET /pret` et que la base répond à une requête de sonde en moins de 2 secondes, LE SYSTÈME DOIT répondre 200 avec le corps `{ "etat": "pret" }`.
    - F-008-AC3 : SI la base est injoignable ou ne répond pas à la sonde en 2 secondes, ALORS LE SYSTÈME DOIT répondre 503 à `GET /pret` avec une enveloppe d'erreur de code `base-indisponible`, continuer de répondre 200 à `GET /sante`, et ne pas s'arrêter ; le délai de 2 secondes DOIT être imposé par le code (et non par un réglage de la base tel que `statement_timeout`), de sorte que `GET /pret` réponde 503 en moins de 3 secondes même quand la requête de sonde ne revient jamais, prouvé par un test dont la sonde reste sans réponse.
    - F-008-AC4 : QUAND le serveur répond à une requête, quelle qu'elle soit, LE SYSTÈME DOIT poser un en-tête `X-Request-Id` qu'il a généré lui-même (jamais repris de la requête) et, si la réponse est une erreur, reporter la même valeur dans le champ `idRequete` de l'enveloppe.
    - F-008-AC5 : SI une requête vise un chemin ou une méthode que le serveur ne connaît pas, ALORS LE SYSTÈME DOIT répondre 404 avec une enveloppe d'erreur de code `ressource-introuvable`.
    - F-008-AC6 : SI le corps d'une requête JSON est syntaxiquement invalide, ALORS LE SYSTÈME DOIT répondre 400 avec une enveloppe d'erreur de code `requete-invalide` ; SI ce corps dépasse 100 kilo-octets, ALORS LE SYSTÈME DOIT répondre 413 avec le code `corps-trop-grand` sans le traiter.
    - F-008-AC7 : QUAND le processus reçoit `SIGTERM`, LE SYSTÈME DOIT cesser d'accepter de nouvelles connexions, laisser finir les requêtes en cours, fermer ses connexions à la base, puis sortir explicitement avec le code 0 (la sortie est demandée par le code une fois la base fermée, elle n'attend pas que plus rien ne retienne le processus), le tout en moins de 10 secondes ; une base figée (connectée mais muette, qui ne ferme jamais son côté des connexions) NE DOIT PAS retenir le processus, prouvé par un test qui envoie `SIGTERM` au processus relié à un faux serveur PostgreSQL qui ne ferme pas ses connexions et constate le code 0 dans le délai.
  - Sécurité du socle
    - F-008-AC8 : SI un traitement lève une erreur non prévue, ALORS LE SYSTÈME DOIT répondre 500 avec une enveloppe d'erreur de code `erreur-interne` et un message générique, dont le corps ne contient ni message de l'erreur d'origine, ni pile d'appels, ni requête SQL, ni chemin de fichier, ni nom de table, et DOIT consigner l'erreur complète dans son journal avec le même `idRequete`.
    - F-008-AC9 : QUAND le serveur répond à une requête, LE SYSTÈME DOIT poser `X-Content-Type-Options: nosniff`, une politique `Content-Security-Policy` qui contient `default-src 'none'` et `frame-ancestors 'none'`, et `Referrer-Policy: no-referrer`, et NE DOIT PAS émettre d'en-tête `X-Powered-By` ni révéler dans un en-tête ou un corps la version d'Express, de Node ou de PostgreSQL.
    - F-008-AC10 : SI une requête porte un en-tête `Origin` absent de la liste `ORIGINES_AUTORISEES` de la configuration, ALORS LE SYSTÈME DOIT répondre sans aucun en-tête `Access-Control-Allow-Origin` ni `Access-Control-Allow-Credentials` ; avec une liste vide (valeur par défaut), aucune origine n'est autorisée et le joker `*` est refusé au démarrage au titre de F-008-AC12.
    - F-008-AC11 : QUAND le serveur écrit une ligne de journal, LE SYSTÈME DOIT l'émettre en JSON sur la sortie standard avec l'identifiant de requête, la méthode, le chemin sans chaîne de requête, le statut et la durée, et NE DOIT PAS y écrire la valeur des en-têtes `Cookie`, `Set-Cookie` et `Authorization`, le corps des requêtes, ni aucun secret de la configuration.
    - F-008-AC12 : SI une variable de configuration obligatoire manque ou est invalide au démarrage, ALORS LE SYSTÈME DOIT se terminer avec un code différent de 0 avant d'écouter sur le réseau, en nommant la variable fautive sur la sortie d'erreur sans en afficher la valeur.
    - F-008-AC13 : LE SYSTÈME DOIT ne contenir aucun secret dans les fichiers suivis par git : le fichier Compose DOIT exiger le mot de passe de la base par une variable sans valeur par défaut (`docker compose config` échoue si elle manque), les fichiers d'exemple (`infra/.env.example`, `apps/server/.env.example`) DOIVENT ne porter que des valeurs factices marquées comme telles, et `secrets.sh` DOIT finir sans constat sur la plage de la feature.
    - F-008-AC14 : SI `NODE_ENV` vaut `production` et qu'un secret de la configuration est égal à une valeur factice des fichiers d'exemple, ALORS LE SYSTÈME DOIT refuser de démarrer dans les conditions de F-008-AC12.
    - F-008-AC25 : SI l'écoute réseau échoue au démarrage (port déjà pris), ALORS LE SYSTÈME DOIT fermer ses connexions à la base, écrire sur la sortie d'erreur une phrase fixe, sans pile d'appels ni objet d'erreur, et se terminer avec un code différent de 0, prouvé par un test qui lance le processus sur un port déjà occupé et constate qu'il finit de lui-même avec un code différent de 0, que la sortie d'erreur ne porte que la phrase attendue et qu'aucune des deux sorties ne contient l'URL de connexion ni le mot de passe.
    - F-008-AC26 : SI l'arrêt du serveur ou la fermeture de la base échoue pendant l'arrêt de F-008-AC7, ALORS LE SYSTÈME DOIT écrire sur la sortie d'erreur une phrase fixe et se terminer avec le code 1, et NE DOIT JAMAIS écrire l'objet d'erreur, ni sur la sortie d'erreur ni dans le journal (il peut porter l'URL de connexion), prouvé par un test où la fermeture de la base rejette avec une erreur qui porte une URL de connexion, et qui constate le code 1, la phrase fixe et l'absence de cette URL sur les deux sorties.
  - Base et migrations (`packages/db`)
    - F-008-AC15 : QUAND la commande de migration de `packages/db` est lancée sur une base vide, LE SYSTÈME DOIT appliquer toutes les migrations versionnées dans leur ordre, consigner chacune dans la table de suivi et finir avec le code 0 ; relancée sur la même base, elle DOIT n'en réappliquer aucune et finir avec le code 0.
    - F-008-AC16 : SI une migration échoue pendant un lancement de la commande de migration, ALORS LE SYSTÈME DOIT annuler toutes les migrations de ce lancement, celles qui avaient réussi avant elle comprises (aucun objet issu de ce lancement dans la base, aucune ligne de ce lancement dans la table de suivi), finir avec un code différent de 0 et laisser intactes les migrations appliquées par les lancements précédents ; relancée après correction, la commande DOIT appliquer toutes les migrations en attente.
    - F-008-AC17 : QUAND un appelant demande à `packages/db` un accès à la base à partir d'une URL de connexion, LE SYSTÈME DOIT fournir un accès Drizzle typé, une sonde de disponibilité bornée par un délai que le code impose lui-même (elle échoue par une erreur typée à l'échéance, que la base ait répondu ou non, sans dépendre de `statement_timeout`) et une fermeture explicite, idempotente (un second appel se résout sans effet et sans erreur) et qui coupe les requêtes encore en vol au lieu de les attendre : l'appelant a fini son travail avant de l'appeler ; la fermeture est prouvée par un test qui ferme alors que la requête d'une sonde hors délai est encore en vol, puis ferme une seconde fois ; SI la connexion échoue, ALORS LE SYSTÈME DOIT lever une erreur typée dont le message ne contient ni l'URL de connexion ni le mot de passe, prouvé par un test qui ouvre le pilote `pg` vers un port local fermé (H5).
    - F-008-AC18 : LE SYSTÈME DOIT permettre d'exécuter tous les tests de `packages/db` et de `apps/server` par `pnpm test` sans Docker ni base externe, chaque fichier de test qui a besoin d'une base disposant d'une base PostgreSQL embarquée qui lui est propre (H5), de sorte que deux exécutions simultanées dans le même arbre ne partagent aucun état ; les fichiers de test qui n'en ont pas besoin n'en ouvrent pas (à ce jour `configuration.test.ts`, `coutures.test.ts` et `processus.test.ts` d'`apps/server`, `commande.test.ts` de `packages/db`), prouvé par un test qui ouvre deux bases embarquées dans le même fichier et constate que ce que l'une reçoit est absent de l'autre.
  - Infrastructure (Docker Compose)
    - F-008-AC19 : QUAND le dev lance `docker compose up` avec les fichiers `.env` copiés des exemples et renseignés, LE SYSTÈME DOIT démarrer la base, appliquer les migrations par un service à exécution unique, puis démarrer le serveur seulement après que la base est déclarée saine et que les migrations ont réussi ; `GET /pret` DOIT alors répondre 200. Le script de fumée de H12, qui lance la pile par `docker compose up -d --wait`, DOIT en outre constater, sur cette pile réelle, ce que la base embarquée des tests ne prouve pas (H5), dans l'ordre des constats 1 à 8 de l'ADR-0006 (`docs/decisions/0006-execution-node-natif-et-conteneurs.md`) : (1) `up -d --wait` finit avec le code 0 et `GET /pret` répond 200 ; (2) le service de migration a fini avec le code 0 et la table de suivi existe ; (3) la version de PostgreSQL servie est celle de H1 et son répertoire de données est celui du volume de F-008-AC20 ; (4) une fois la base arrêtée, `GET /pret` répond 503 en moins de 3 secondes et `GET /sante` répond 200 ; (5) une fois la base redémarrée, `GET /pret` répond de nouveau 200, sans redémarrage du serveur ; (6) une fois la base figée (connectée mais muette), `GET /pret` répond 503 en 1,9 à 3 secondes, puis 200 une fois la base relâchée ; (7) la pile arrêtée puis relancée sans supprimer le volume, la table de suivi est toujours là ; (8) le service serveur, arrêté, sort avec le code 0 en moins de 10 secondes. Le même script porte deux constats rattachés à d'autres critères : la migration en échec qui laisse le serveur non démarré (constat 9, F-008-AC21) et l'analyse de l'image du serveur (constat 10, F-008-AC20) ; il finit par le nettoyage de sa propre pile, volume et images construites compris (constat 11 de l'ADR-0006, qui ne prouve aucun critère). Vaut seule preuve de ce critère : la sortie d'`infra/fumee.sh`, lancé par le dev sur le dernier commit de code de la feature et finie par `FUMEE: OK`, versée dans `MEMORY/features/F-008.md` ; sans elle, ce critère reste `UNVERIFIED` et F-008 n'est pas DONE (H12).
    - F-008-AC20 : LE SYSTÈME DOIT décrire, dans le fichier Compose et le Dockerfile du serveur : une image PostgreSQL et une image Node de base épinglées par version et par empreinte (`@sha256:`), l'image Node étant la variante Alpine désignée par son étiquette complète, suffixe de variante compris (H10) ; des ports de la base et du serveur publiés sur `127.0.0.1` uniquement, cette adresse étant écrite en dur et seul le port du poste étant réglable (H11) ; un volume nommé pour les données de la base, monté sur `/var/lib/postgresql` (H1) ; un contrôle de santé pour la base, qui l'interroge par `pg_isready` sur son adresse TCP et non par la socket Unix, et un contrôle de santé pour le serveur ; un serveur qui s'exécute sous un utilisateur non root posé explicitement par le Dockerfile (`USER node`) ; une image finale dont `npm` est retiré. Ces exigences de forme sont prouvées par les tests statiques de H12. Le contrôle `CONTENEURS` du socle (`trivy fs` lancé sur le dépôt) DOIT finir sans constat HIGH ni CRITICAL : il prouve que les dépendances du verrou `pnpm-lock.yaml` n'ont aucune faille HIGH ou CRITICAL connue et que les fichiers du dépôt ne portent aucun secret ; il ne lit ni le Dockerfile, ni le fichier Compose, ni aucune image, et ne prouve donc rien sur l'image de base Node, sur l'image construite ni sur l'image PostgreSQL. L'image du serveur construite DOIT en outre finir sans constat HIGH ni CRITICAL à `trivy image`, lancé par le script de fumée de H12 (constat 10 de l'ADR-0006), hors des hooks, par le dev ; vaut preuve de cette dernière exigence la sortie de ce script versée dans `MEMORY/features/F-008.md` (H12), sans laquelle elle reste `UNVERIFIED` et F-008 n'est pas DONE, quand bien même les tests statiques et le contrôle `CONTENEURS` passent. L'image officielle PostgreSQL n'est pas tenue à cette exigence : ses failles connues sont un risque accepté (H15).
    - F-008-AC21 : SI le service de migration échoue, ALORS LE SYSTÈME DOIT ne pas démarrer le service serveur ; la forme du fichier Compose qui l'impose est prouvée par un test statique (H12), le comportement par le constat 9 du script de fumée, dont la sortie versée dans `MEMORY/features/F-008.md` vaut seule preuve dynamique : sans elle, ce critère reste `UNVERIFIED` et F-008 n'est pas DONE.
    - F-008-AC24 : LE SYSTÈME DOIT, dans le fichier Compose, fournir au service serveur toutes les variables du fichier `apps/server/.env` (chargement du fichier entier, et non une liste de variables recopiées une à une), de sorte qu'une variable ajoutée à ce fichier par une feature ultérieure (F-009 : `BETTER_AUTH_SECRET`, `URL_PUBLIQUE`) parvienne au serveur sans modification du fichier Compose ; SI ce fichier manque, ALORS `docker compose config` DOIT échouer. Un test statique d'`infra/tests/` DOIT le vérifier (H12).
  - Contrats et structure
    - F-008-AC22 : LE SYSTÈME DOIT publier depuis `packages/contrats` le schéma de validation et le type de l'enveloppe d'erreur, la liste fermée des codes d'erreur de cette feature (`requete-invalide`, `ressource-introuvable`, `corps-trop-grand`, `base-indisponible`, `erreur-interne`), tous en minuscules sans accent séparées par des tirets, convention commune avec les codes d'erreur de `@notionlike/document` (H3), les schémas des réponses de `GET /sante` et `GET /pret` et les chemins de ces routes ; chaque réponse émise par le serveur dans les tests de F-008-AC1 à AC8 DOIT être validée contre ces schémas ; SI un code ne suit pas cette convention (tiret bas, majuscule, accent, tiret en tête, en fin ou doublé), ALORS le schéma de l'enveloppe d'erreur DOIT le refuser, prouvé par un test qui lui soumet un code de la liste dont un tiret est remplacé par un tiret bas.
    - F-008-AC23 : LE SYSTÈME DOIT garder `packages/contrats` importable dans un navigateur (aucun module natif de Node, aucune dépendance vers Express, `packages/db` ou `packages/document`, `zod` pour seule dépendance d'exécution directe), garder `packages/db` sans dépendance vers `packages/contrats` ni vers Express, réserver `packages/db` au serveur, et `pnpm contrats` DOIT finir sans violation avec les règles demandées au dev ci-dessous ; un test énumère les fichiers d'`apps/server/src` qui importent `@notionlike/contrats` et `@notionlike/db`, et les noms importés (`apps/server/test/coutures.test.ts`), de sorte qu'un appelant ou un nom de plus le fasse échouer tant qu'il n'y est pas déclaré.
- Hors périmètre (explicitement) :
  - Comptes, sessions, cookies, limitation de débit : F-009. Aucune route de cette feature n'exige d'authentification, et aucune ne renvoie de donnée.
  - Espaces, membres, invitations, droits : F-011. Aucune table métier n'est créée ici (H6).
  - Hocuspocus, WebSocket, stockage des instantanés Yjs, nommage des documents côté serveur : F-012 (ADR-0001 laisse ce nommage à F-012). `packages/contrats` naît ici comme lieu des contrats REST et WebSocket, mais ne reçoit dans cette feature que l'enveloppe d'erreur et le point de santé.
  - `apps/web` et tout ce qui sert le client : F-002, F-023. Le serveur ne sert aucun fichier statique. Une exception, nommée : `apps/web/test/coutures.test.ts`, retouché par `agent-frontend` sous cette feature (commit `11f32bf`). L'énumération de F-002-AC31 (les fichiers de `src/` qui nomment le type des codes du document ou lisent le champ `code` d'une erreur) se borne désormais aux paquets dont un fichier de `src/` importe `@notionlike/document` ; pour `apps/web`, la liste attendue est inchangée et reste comparée en entier. Aucune assertion n'est retirée ; les cas conformes et fautifs de l'énumération sont ajoutés comme données du test ; aucun analyseur n'est ajouté. Motif : `packages/db` et `apps/server` portent leurs propres erreurs à `code` (`ErreurBase`), qui ne sont pas des codes du document et faisaient échouer l'énumération. Aucun fichier d'`apps/web/src` n'est touché.
  - TLS, proxy inverse, nom de domaine, déploiement hors du poste du dev, sauvegarde et restauration de la base, supervision et métriques : couverts par aucune feature à ce jour (manque signalé dans `ROADMAP.md`).
  - CI : dette D-001, toujours ouverte ; cette feature ne la résorbe pas. Ses contrôles restent ceux des hooks git.
  - Séparation des rôles PostgreSQL (rôle de migration et rôle applicatif distincts) : H8.
  - Test de couture des appelants hors d'`apps/server` : l'enveloppe d'erreur, les schémas de santé et l'accès à la base naissent ici et n'ont qu'un appelant, `apps/server`, dont la couture est dans le périmètre (F-008-AC23, `apps/server/test/coutures.test.ts`). F-009, F-011 et F-012 tiendront cette énumération à jour dès qu'elles y touchent ; la couture du client avec `packages/contrats` arrive avec F-010.
- Hypothèses tranchées par agent-planif en l'absence du dev, que la validation de cette spec entérine :
  - H1 — PostgreSQL 18, majeure épinglée, mineure 18.6 (confirmée par la veille du 2026-10-08 : stable, supportée jusqu'en novembre 2030, la 19 n'existe qu'en bêta). Image officielle `postgres:18.6`, épinglée par étiquette et par empreinte (`@sha256:`). L'empreinte lue par la veille n'est pas recopiée ici : l'étiquette est reconstruite régulièrement, donc l'empreinte est relue au registre le jour où l'image est épinglée, et c'est celle-là qui est commitée. À partir de la majeure 18, l'image range ses données sous `/var/lib/postgresql/18/docker` et déclare son volume sur `/var/lib/postgresql` : le volume nommé se monte là, et non sur `/var/lib/postgresql/data` comme avec les majeures précédentes (veille des conteneurs du 2026-10-08 ; rejoué par la conception, où le conteneur refuse de démarrer sur l'ancien point de montage). Difficile à défaire une fois des données en base (montée de version majeure = migration des données).
  - H2 — Frontière de `packages/contrats` : il contient des schémas de validation (`zod`), les types qui en sont déduits, les codes d'erreur, les chemins de routes, et des fonctions pures : sans entrée-sortie (ni réseau, ni système de fichiers, ni base, ni DOM, ni horloge), sans état et sans autre dépendance que `zod`, importables dans un navigateur. Une telle fonction n'y a sa place que si le serveur et le client doivent appliquer la même règle à l'identique, deux copies pouvant diverger : c'est ce qu'y placent le nommage des documents (F-012 H2, F-012-AC27) et les trois fonctions d'image de F-022 H8 (validation d'une référence d'image, type constaté par les octets de signature, nettoyage des métadonnées). La formule d'origine, « aucune logique », est remplacée par celle-ci : elle visait la logique métier et les effets, pas une règle de validation partagée. Restent exclus : tout accès réseau, toute logique qui dépend d'un état, tout type Express ou Drizzle ; la règle de dépendances de F-008-AC23 est inchangée (`zod` pour seule dépendance d'exécution directe, aucun module natif de Node, aucune dépendance vers Express, `packages/db` ou `packages/document`). Dans cette feature, le serveur type ses sorties par les types déduits de ces schémas, et ce sont les tests qui valident les réponses contre les schémas (F-008-AC22) : le serveur n'exécute aucun schéma de `packages/contrats` sur ce qu'il émet. Aucune route de F-008 n'a d'entrée (ni corps, ni paramètre, ni chaîne de requête lus), donc aucune entrée n'est à valider ici ; la validation des entrées par ces schémas commence avec la première route qui en reçoit (F-009). Le client (F-010 et suivantes) les importe tels quels. Difficile à défaire : c'est le seul lien de compilation entre `apps/web` et `apps/server`.
  - H3 — Format d'erreur maison (`code`, `message`, `idRequete`) plutôt que RFC 9457 : trois champs suffisent, le client ne branche que sur `code`. Les codes sont en français, en minuscules sans accent, les mots séparés par des tirets (jamais de tiret bas, de majuscule ni de point), et la liste est fermée par feature. Cette convention est commune à tout le dépôt : c'est celle des codes d'erreur de `@notionlike/document` (`page-introuvable`, `titre-trop-long`, voir `docs/decisions/0003-paquet-document-interface-publique.md`), pour que le client n'affiche et ne branche que sur une seule famille de codes ; F-008-AC22 la fait vérifier par le schéma. Elle ne vaut que pour les codes de notre enveloppe : les codes natifs d'une bibliothèque tierce que le serveur laisse passer tels quels (ceux de better-auth dans F-009, par exemple `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`) ne sont pas les nôtres et gardent leur forme. Difficile à défaire dès que F-010 l'affiche.
  - H4 — Chemins : les points de santé sont à la racine (`/sante`, `/pret`), hors préfixe ; les routes métier à venir vivront sous `/api/v1/`, et l'authentification sous `/api/auth/` (F-009).
  - H5 — Tests sans Docker : `pnpm test` est lancé par les hooks de tous les agents, y compris ceux du client ; une base externe obligatoire bloquerait leurs commits. Les tests utilisent donc PGlite (PostgreSQL compilé en WebAssembly, pris en charge par Drizzle), une instance par fichier de test. En production, le pilote est `pg` (node-postgres). Le choix est maintenu après la veille, qui a mesuré les écarts de PGlite 0.5.8 ; ils sont assumés et listés : (1) les requêtes sont sérialisées sur une connexion unique, donc aucune concurrence réelle, ni pool, ni verrou entre connexions n'est exercé ; (2) `statement_timeout` est accepté mais pas appliqué, d'où le délai imposé par le code (F-008-AC3, AC17) ; (3) les rôles et les droits ne sont pas représentatifs (H8 n'y est pas testable) ; (4) le pilote `pg` n'est pas exercé : pool, authentification, erreurs de connexion, URL de connexion ; (5) le moteur embarqué est un PostgreSQL 18.3, pas la 18.6 de l'image ; (6) extensions, collations, `LISTEN/NOTIFY` et verrous consultatifs n'ont pas été testés. Ce qui reste couvert par `pnpm test` : le DDL transactionnel de F-008-AC16 (constaté par la veille sur PGlite, et le migrateur Drizzle est le même code pour les deux pilotes), et le message d'erreur de connexion de F-008-AC17, testé avec le vrai pilote `pg` vers un port local fermé, ce qui ne demande aucune base. Tout le reste n'est couvert que par la vérification manuelle de F-008-AC19, hors des hooks : dette D-002 proposée dans `ROADMAP.md`. Ce que la conception a essayé sur une pile réelle le 2026-10-08 (`docs/decisions/F-008-conception.md`, « Essais », J à L) l'a été sur un squelette écrit pour l'essai, pas sur le code de F-008, qui n'existe pas encore : ces essais fondent les choix d'infrastructure (H1, H10, F-008-AC20) et la liste des constats du script de fumée, ils ne prouvent aucun critère. Le script de fumée est écrit (`infra/fumee.sh`, constats 1 à 11) mais n'a jamais été lancé, Docker étant indisponible sur le poste jusqu'ici ; pendant la conception, ses constats 1 à 9 ont été joués à la main et dans un autre ordre, le constat 10 sur une image construite à part. La preuve dynamique de F-008-AC19 reste donc entièrement à apporter, par le script de fumée que le dev lance sur le dernier commit de code (H12).
  - H6 — Aucune table métier dans cette feature : la chaîne de migration est prouvée sur un jeu de migrations d'essai propre aux tests ; la première migration réelle arrive avec F-009. La conception décide si le dossier de migrations réel naît vide ou avec une migration sans objet.
  - H7 — Les migrations ne sont jamais appliquées par le serveur au démarrage : une commande dédiée de `packages/db`, lancée par un service Compose à exécution unique. Un serveur qui migre en démarrant rend un retour arrière impossible à maîtriser.
  - H8 — Un seul rôle PostgreSQL, propriétaire de la base applicative, sert aux migrations et au serveur. La séparation en deux rôles est reportée : criticité « interne », base non exposée hors de `127.0.0.1`.
  - H9 — Bibliothèques : `helmet` pour les en-têtes de sécurité, `pino` pour le journal, `zod` pour la validation, `pg` pour le pilote. `drizzle-kit` n'est pas installé par cette feature : elle ne crée aucun schéma (H6), donc rien n'est à générer ; il entre avec F-009, qui le porte dans ses prérequis (son hypothèse H19). Chacune est le choix majoritaire de son rôle ; la veille du 2026-10-08 a fixé les versions (prérequis ci-dessous) et n'a trouvé aucune CVE ouverte sur elles. Elle n'a pas lu les valeurs par défaut de `helmet`, de `pino` ni d'`express.json()` : les en-têtes de F-008-AC9, la limite de 100 kilo-octets de F-008-AC6 et les champs exclus du journal par F-008-AC11 sont donc réglés explicitement et prouvés par test, jamais laissés au défaut d'une bibliothèque.
  - H10 — Mode d'exécution du TypeScript côté serveur et forme du Dockerfile : tranchés par la conception (ADR-0006, statut « proposé » tant que cette spec est en brouillon), la forme exacte du Dockerfile restant la sienne tant que F-008-AC19 à AC21 tiennent. Le TypeScript est exécuté nativement par Node 26, sans compilation préalable. L'image de base est l'image officielle Node 26 en variante Alpine, épinglée par son étiquette complète avec le suffixe de variante et par empreinte ; l'étiquette et l'empreinte sont relues au registre le jour où l'image est épinglée, comme pour H1. L'image livrée est `node:26.11.1-alpine3.24`, étiquette du jour du bloc d'infrastructure (2026-10-09), empreinte figée dans le Dockerfile ; l'étiquette `26.10.0-alpine3.24` que citent la veille et l'ADR-0006 est celle de leurs essais. `npm` est retiré de l'image finale, où rien ne s'installe après la construction ; l'utilisateur `node` est posé par un `USER node` explicite, l'image tournant en root par défaut ; pnpm est installé par `npm` dans l'étape de dépendances seulement, `corepack` étant absent de l'image. Raison du choix : à `trivy image`, la variante `slim` (Debian) porte des constats HIGH sans version corrigée que le Dockerfile ne peut pas lever, alors que ceux de la variante Alpine sont tous dans le `npm` embarqué et disparaissent avec lui (veille des conteneurs du 2026-10-08, rejoué par la conception sur un squelette). Conséquence : la bibliothèque C de l'image est musl et non glibc. Aucune dépendance d'exécution de cette feature n'a de module natif ; toute future dépendance native est à essayer dans l'image avant d'être retenue, faute de quoi il faut revenir à la variante `slim` et à ses constats sans correctif.
  - H11 — Noms des paquets : `@notionlike/server`, `@notionlike/db`, `@notionlike/contrats`. Port d'écoute `PORT` (3000 par défaut), adresse d'écoute `HOTE` (`127.0.0.1` par défaut, `0.0.0.0` dans le conteneur). Dans le fichier Compose, le port du poste sur lequel la base et le serveur sont publiés est réglable par deux variables facultatives (`PORT_PUBLIE_BASE`, `PORT_PUBLIE_SERVEUR` ; 5432 et 3000 sans elles), pour que le script de fumée tourne à côté de la pile de travail et pour un poste dont le port est déjà pris. Le fichier Compose fixe le nom du projet de la pile de travail (`name: notionlike`), pour que ses conteneurs et son volume ne dépendent pas du dossier d'où il est lancé ; le script de fumée lance la sienne sous un autre nom de projet (`notionlike-fumee`, H12). Cela ne contredit pas F-008-AC20 (« publiés sur `127.0.0.1` uniquement ») : ces variables ne règlent que le numéro de port, l'adresse `127.0.0.1` est écrite en dur dans le fichier et aucune variable ne permet de publier sur une autre adresse ; le test statique d'AC20 le vérifie sur chaque port publié.
  - H12 — Preuve des critères d'infrastructure : F-008-AC13, AC20 et AC21 sont vérifiés par des tests statiques qui lisent le fichier Compose et le Dockerfile (`infra/tests/*.test.ts`, périmètre d'`agent-devops`), exécutables sans Docker ; F-008-AC19 est vérifié par un script de fumée `infra/` que le dev lance une fois Docker démarré, et dont le test cite l'identifiant. Ce script lance la pile par `docker compose up -d --wait`, sous un nom de projet et sur des ports du poste distincts de ceux de la pile de travail ; il n'utilise pas `up --abort-on-container-exit`, qui arrête toute la pile dès que le service de migration finit, même avec le code 0. Il apporte aussi la seule preuve dynamique de F-008-AC21 (constat 9 de l'ADR-0006 : avec un mauvais mot de passe donné au seul service de migration, `up -d --wait` finit avec un code différent de 0, la migration sort avec le code 1 et le serveur n'est jamais démarré) et la seule preuve de la dernière exigence de F-008-AC20 (constat 10 : `trivy image` sur l'image du serveur construite) ; ce dernier résultat dépend de la base de failles du jour où le script est lancé. Aucun de ces constats n'est rejoué par les hooks. Docker a été indisponible sur le poste pendant toute la production du code : le script n'a donc jamais tourné, et rien d'autre ne le remplace. Vaut preuve de F-008-AC19, de F-008-AC21 (volet dynamique) et de la dernière exigence de F-008-AC20 : la sortie complète d'`infra/fumee.sh`, lancé par le dev sur le dernier commit de code de la feature, finie par `FUMEE: OK`, versée dans `MEMORY/features/F-008.md` avec le hachage de ce commit. Sans elle, ces trois critères restent `UNVERIFIED`, et F-008 n'est pas DONE (`UNVERIFIED` n'est jamais un PASS) ; un commit de code postérieur à la sortie versée la périme. Le reviewer-devops juge si cette preuve suffit. F-008-AC24 rejoint les tests statiques.
  - H13 — Migrations : le migrateur d'exécution de Drizzle (`drizzle-orm@0.45.3`) applique toutes les migrations en attente d'un lancement dans une seule transaction ; F-008-AC16 décrit ce comportement plutôt que d'exiger une transaction par migration, qui demanderait de réécrire le migrateur. Conséquence : une migration ne doit contenir aucune instruction qui refuse de s'exécuter dans une transaction. Limite connue, non couverte ici : le migrateur ne compare que l'horodatage de la dernière migration appliquée, donc une migration versionnée avec un horodatage antérieur est ignorée sans erreur. Le risque est nul tant que les migrations sont produites en séquence sur une seule branche ; il est à reprendre dès que deux branches en produisent en parallèle.
  - H14 — Le service serveur du fichier Compose reçoit le fichier `apps/server/.env` entier (F-008-AC24) : c'est ce qui permet à F-009 et aux features suivantes d'ajouter une variable de configuration sans rouvrir l'infrastructure. Le mot de passe de la base reste exigé séparément par F-008-AC13. `NODE_ENV` est laissée en commentaire dans `apps/server/.env.example` : la fixer dans le fichier chargé déferait le mode de production sous Compose. Elle est fixée à `production` dans l'environnement du service `serveur` du fichier Compose, qui l'emporte sur le fichier chargé, comme `HOTE`, `PORT` et `URL_BASE_DONNEES` ; un mot de passe factice y est donc refusé (F-008-AC14). Ce réglage du fichier Compose est une correction d'`agent-devops` à venir : au commit `502aa0d`, seul le Dockerfile fixe `NODE_ENV=production` (`ENV`), et le fichier Compose ne la nomme pas.
  - H15 — Risque accepté : failles connues de l'image officielle `postgres:18.6`, consigné dans l'ADR-0006 (`docs/decisions/0006-execution-node-natif-et-conteneurs.md`, « Conséquences »). `trivy image --severity HIGH,CRITICAL --scanners vuln` y trouve 84 constats (rejoué par la conception le 2026-10-08, trivy 0.75.0) : 62 dans des paquets Debian 13 (61 HIGH et 1 CRITICAL, CVE-2026-6653 dans `libxml2`), tous sans version corrigée, et 22 dans le binaire `gosu` (21 HIGH et 1 CRITICAL, CVE-2025-68121, dans la bibliothèque standard de Go avec laquelle il est compilé ; corrigées dans des versions de Go plus récentes, mais le binaire est celui de l'image). Soit 2 CRITICAL et 82 HIGH ; la veille résume « 1 CRITICAL et 83 HIGH » pour les mêmes 84 constats. PostgreSQL lui-même n'y figure pas. L'image n'est ni reconstruite ni modifiée, et aucune variante sans ces paquets n'a été évaluée (`18.6-alpine` existe, non analysée). Parades : port publié sur `127.0.0.1` seulement (F-008-AC20, test statique) ; base non exposée, jointe par le seul réseau du projet Compose ; image épinglée par étiquette et par empreinte, donc relue à chaque mise à jour, avec un `trivy image` à refaire ce jour-là. Ce qui n'est pas paré : un attaquant qui exécute déjà du code dans le conteneur de la base. Le risque est accepté pour un outil interne servi sur le poste ; il est à rouvrir avant tout déploiement hors du poste, que ne couvre aucune feature. Aucun critère de cette spec n'exige donc que cette image soit sans constat, et aucun contrôle des hooks ne la lit.
